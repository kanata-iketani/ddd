# 第15章 モデリング実践 — イベントストーミングとECサイト設計

ここまで学んだ戦略的設計と戦術的設計を、ECサイトという1つの題材で通しで使う実践章です。イベントストーミングで業務を可視化し、コンテキストを切り、注文集約を設計するまでの「判断の連続」を体験してください。正解の丸暗記ではなく「なぜその判断か」を自分の言葉で言えるようになるのがゴールです。

## 1. イベントストーミング — 出来事から設計を始める

### なぜ「出来事」から始めるのか

モデリングをいきなりテーブル設計(ER図=テーブルとその関係を描いた図、を描くこと)や「商品」「注文」という**名詞**から始めると、データの形に思考が引きずられ、業務の流れやルールが抜け落ちます。

**イベントストーミング (Event Storming)** は、業務で起きる**出来事 (L10 で見たドメインイベント)** を時系列に並べることから始める、付箋ベースのワークショップ(関係者が集まって一緒に手を動かす会議)手法です。壁や大きな紙、オンラインのホワイトボードに付箋を貼っていきます。

出来事は「注文が確定した」のように過去形で書くため、「本当に何が起きるのか」をドメインエキスパート(L1 で見た、業務に詳しい人)と開発者が同じ目線で洗い出せます。

### 付箋の文法

色で役割を分けるのが約束事です。

| 色 | 意味 | 例 |
|---|---|---|
| 🟠 オレンジ | ドメインイベント (過去形) | 「注文が確定した」 |
| 🔵 青 | コマンド (起点となる操作) | 「注文を確定する」 |
| 🟡 黄 | 集約 (コマンドを受けて状態を変える) | 「注文」 |
| 🩷 ピンク | 外部システム | 「決済ゲートウェイ」 |
| 🟣 紫 | ポリシー (〜したら〜する) | 「支払いが完了したら出荷を指示する」 |
| 🔴 赤 | ホットスポット (疑問・対立・未決事項) | 「在庫が無いときは?」 |

- **コマンド**: 誰かが「〜する」と指示する操作。L14 で見た「状態を変える指示」と同じ意味です
- **集約**: L8 で見た、不変条件を一緒に守るまとまり。コマンドを受け取り、ルールを確かめて状態を変え、イベントを生みます
- **外部システム**: 自分たちが作らない、外のサービス。**決済ゲートウェイ**はクレジットカード決済などを代わりに処理してくれる外部サービスです
- **ポリシー**: 「イベント A が起きたら、コマンド B を出す」という業務の決まりごと
- **ホットスポット**: まだ答えが出ていない疑問や、人によって言うことが違う所

### 並べた例

ECサイトの受注を付箋で並べると、たとえば次のように左から右へつながります。

| 順 | 色 | 付箋 |
|---|---|---|
| 1 | 🔵 青 | 注文を確定する |
| 2 | 🟡 黄 | 注文 |
| 3 | 🟠 オレンジ | 注文が確定した |
| 4 | 🟣 紫 | 注文が確定したら決済を依頼する |
| 5 | 🩷 ピンク | 決済ゲートウェイ |
| 6 | 🟠 オレンジ | 支払いが完了した |
| 7 | 🟣 紫 | 支払いが完了したら出荷を指示する |
| 8 | 🔵 青 | 出荷を指示する |
| 9 | 🔴 赤 | 在庫が無いときは? |

「コマンド → 集約 → イベント → ポリシー → 次のコマンド」という流れが繰り返されるのが、読むときの基本の型です。

### 3段階で深めていく

1. **ビッグピクチャ**: まず業務全体のイベントをとにかく貼り出し、時系列に並べる
2. **プロセスモデリング**: コマンド・ポリシー・外部システムを足し、「何がきっかけで次に何が起きるか」を繋ぐ(上の表の形)
3. **ソフトウェア設計**: 集約を特定し、境界づけられたコンテキスト(L3)の候補を描く

> 💡 コツ: 🔴赤い付箋 (ホットスポット) は宝の山です。「ここで在庫が足りなかったら?」「キャンセルは誰が承認する?」といった赤は、暗黙のルールや見落とされた仕様が隠れている場所。急いで消さず、むしろ増やす気持ちで進めます。

全員参加であることも重要です。開発者だけでやると技術都合に、エキスパートだけだと実装不可能な理想論に寄ります。両者が同じ壁の前に立つことで、ユビキタス言語 (Ubiquitous Language、L2 で見た、会話とコードで共有する言葉) が自然と育ちます。

なお、最初に API のエンドポイント(`POST /orders` のような、外から呼べる URL ごとの入口)の一覧を決めるやり方も、出来事より先に技術の形を決めてしまう点でテーブル設計から始めるのと同じ問題を持ちます。

### 確認問題

**問1.** ECサイトの受注フローをチームでモデリングすることになりました。イベントストーミングの最初のステップとして最も適切なのはどれでしょう?

1. 「注文が確定した」「支払いが完了した」など業務で起きる出来事を過去形で貼り出し、時系列に並べる
2. 「商品」「注文」「顧客」といった主要な名詞(エンティティ候補)をまず洗い出して並べる
3. 注文テーブルと商品テーブルのER図を描いてカラムを決める
4. APIのエンドポイント一覧を先に定義する

<details><summary>答えと解説</summary>

正解: **1**

イベントストーミングは出来事(ドメインイベント)を時系列に並べるビッグピクチャから始めます。過去形の出来事から始めることで、データの形ではなく業務の流れとルールに注目できるのが利点です。名詞から始めたりER図やテーブルのカラムを先に決めると、データ構造に思考が縛られて業務知識が抜け落ちます。APIエンドポイントの定義は実装寄りの決定で、業務理解が固まる前に行うのは早すぎます。

</details>

**問2.** イベントストーミング中、「支払いが完了したら、出荷を指示する」という業務ルールが見つかりました。この付箋は何色(どの要素)で表すのが適切でしょう?

1. 🟠 オレンジ(ドメインイベント)
2. 🟣 紫(ポリシー)
3. 🔵 青(コマンド)
4. 🩷 ピンク(外部システム)

<details><summary>答えと解説</summary>

正解: **2**

「〜したら〜する」という、ある出来事をきっかけに次の行動を引き起こす業務ルールはポリシー(紫)で表します。ドメインイベント(オレンジ)は「支払いが完了した」という出来事そのもの、コマンド(青)は「出荷を指示する」という操作そのもので、両者を繋ぐ因果のルールがポリシーです。外部システム(ピンク)は決済ゲートウェイのような自分たちの管理外のシステムを指し、ここでのルールとは別物です。

</details>

**問3.** ワークショップで「在庫が足りないときの注文はどう扱うのか、その場で誰も即答できない」という論点が出ました。DDDのイベントストーミングにおいて、この状況の最も望ましい扱い方はどれでしょう?

1. 決まっていないことは混乱のもとなので、ひとまず「在庫は常にある前提」にして話を先に進める
2. その場でエンジニアが実装しやすい仕様を決めてしまい、付箋には残さない
3. 🔴赤い付箋(ホットスポット)として明示的に貼り、重要な検討ポイントとして残す
4. 議事録のテキストにだけメモして、壁の付箋からは外しておく

<details><summary>答えと解説</summary>

正解: **3**

即答できない対立や疑問はホットスポット(赤付箋)として可視化するのがイベントストーミングの要です。赤は暗黙のルールや見落とされた仕様が潜む「宝の山」で、消さずに残すことで後の深い議論につながります。「前提」にして飛ばすと重要な仕様が闇に消え、エンジニアが独断で決めるとエキスパートの知識が反映されません。壁から外してテキストに埋もれさせると、全員で見る価値が失われます。

</details>

**問4.** ECの受注プロセスをプロセスモデリングの段階まで進めたところ、「注文を確定する」というコマンドを受けて状態が変わる対象が見えてきました。この黄色い付箋(集約候補)として最も自然なのはどれでしょう?

1. 決済ゲートウェイ
2. 出荷通知メール
3. 「注文が確定した」というイベントそのもの
4. 注文(Order)

<details><summary>答えと解説</summary>

正解: **4**

集約(黄)はコマンドを受け取り、不変条件を守りながら自身の状態を変え、結果としてドメインイベントを生む対象です。「注文を確定する」コマンドの受け手は注文(Order)集約が自然です。決済ゲートウェイは外部システム(ピンク)、「注文が確定した」はコマンドの結果生まれるイベント(オレンジ)であって状態を持つ集約ではありません。出荷通知メールはポリシーの先で起きる副次的なアクションにすぎません。

</details>

**問5.** イベントストーミングを「開発者だけ」で実施しようとしています。DDDの観点でこの進め方の最大の問題はどれでしょう?

1. ドメインエキスパートの持つ暗黙知や例外ルールが抜け落ち、ユビキタス言語が育たない
2. 付箋の色の使い分けが正確にならない
3. ワークショップにかかる時間が長くなる
4. イベントを過去形で書けなくなる

<details><summary>答えと解説</summary>

正解: **1**

イベントストーミングの核心は、ドメインエキスパートと開発者が同じ壁の前で知識を突き合わせ、ユビキタス言語を育てることにあります。開発者だけだと業務の暗黙知や例外ケース(エキスパートしか知らない「こういうときはこうする」)が抜け落ち、技術都合に寄ったモデルになります。付箋の色使いや所要時間、過去形の記法は参加者構成とは本質的に無関係で、最大の問題ではありません。

</details>

**問6.** イベントストーミングで「出荷を指示する」と書いた付箋を貼ります。この付箋は何色(どの要素)が適切でしょう?

1. 🟠 オレンジ(ドメインイベント)
2. 🟡 黄(集約)
3. 🔵 青(コマンド)
4. 🔴 赤(ホットスポット)

<details><summary>答えと解説</summary>

正解: **3**

「〜する」という、状態を変える指示なのでコマンド(青)です。ドメインイベント(オレンジ)なら「出荷が指示された」「出荷された」のように過去形になります。集約(黄)は「出荷」のような、コマンドを受けて状態を変えるまとまりの名前です。ホットスポット(赤)は疑問や未決事項に使います。

</details>

## 2. ECサイトのコンテキスト分割 — 言葉の変化で境界を切る

### 題材: 中規模ECサイト

ch01 のイベントストーミングで洗い出したイベントを時系列に並べると、こうなります。

```text
商品が公開された → カートに追加された → 注文が確定した
→ 支払いが完了した → 在庫が引き当てられた → 出荷された → 配達が完了した
```

**在庫の引き当て**とは、注文された数の在庫を「この注文用」として確保し、他の注文に使われないようにすることです。

この一本の流れを、どこで区切って別々の境界づけられたコンテキスト (Bounded Context、L3) にするかを考えます。

### 言葉の意味が変わる場所に境界がある

分割の最大の手がかりは、**同じ言葉が文脈で別物になる場所**です。

| 言葉 | カタログでは | 在庫では | 配送では |
|---|---|---|---|
| 商品 | 説明・画像・価格を持つ「商品 (Product)」 | 数量と棚を持つ「在庫単位 (SKU)」 | 重量とサイズを持つ「荷物 (Package)」 |

**SKU**(Stock Keeping Unit)は在庫を数える最小の単位で、同じTシャツでも色やサイズが違えば別の SKU になります。

同じ商品 p-1 を、各コンテキストは次のように持ちます。ID だけが共通です。

| コンテキスト | 持っている値 |
|---|---|
| カタログ | ID=p-1、名前=白Tシャツ、価格=2,000円、画像=tshirt.jpg |
| 在庫 | ID=p-1、SKU=p-1-M、数量=35、棚=A-12 |
| 配送 | ID=p-1、重量=200g、サイズ=60サイズ |

「商品」を1つのクラスに統一しようとすると、全部門の属性が集まった神クラス(何でも抱え込んだ巨大なクラス)になります。意味が変わる場所で切るのが正解です。

### 分割案と各コンテキストの重要度

L5 で見たサブドメインの分類(コア=競争力の源泉、支援=必要だが差別化しない自社業務、汎用=どの会社でも同じで外部の製品で済む)で整理します。

| コンテキスト | 役割 | 分類 |
|---|---|---|
| カタログ | 商品情報の管理・検索 | 支援 |
| 注文 | 受注・注文のライフサイクル | **コア** |
| 決済 | 支払い処理 | 汎用(外部ゲートウェイ) |
| 在庫 | 引当・入出庫 | 支援 |
| 配送 | 出荷・配達追跡 | 支援 |

このECの競争力が「スムーズで信頼できる受注体験」なら、**注文がコアドメイン**です。決済は外部のPSP(Payment Service Provider、決済代行会社)に任せる汎用サブドメインになりがちです。

### コンテキストマップ

L4 で見たコンテキストマップ(コンテキスト同士のつながり方を描いた図)として、つながりを決めます。

- **注文 → 在庫**: 注文確定イベントを在庫が購読して引き当てる(イベント連携・疎結合)。**購読**は「このイベントが起きたら知らせて」と登録しておくことで、L10 で見たイベントの配り方です。**疎結合**は、相手の中身を知らなくても動ける、つながりの弱い状態です
- **注文 → 決済**: 外部決済ゲートウェイとは**腐敗防止層 (ACL、L4)** を挟み、相手のAPIモデル(相手の JSON の形やステータスコード)を自分のモデルに変換する
- **カタログ → 注文**: 注文時は商品IDと確定価格をスナップショット(その時点の値のコピー。L3 で見た形)でコピー(カタログの価格変更が過去の注文を汚さない)

価格のスナップショットの具体例です。

| 時点 | カタログの価格 | 注文 o-7 の明細の単価 |
|---|---|---|
| 5/1 注文確定 | 2,000円 | 2,000円(この時点の値をコピー) |
| 5/10 値下げ | 1,500円 | 2,000円(変わらない) |

在庫がイベントを購読する代わりに、在庫側が注文テーブルを定期的に見に行く(**ポーリング**)方法もありますが、在庫が注文の DB の中身を知ることになり、つながりが強くなります。

> 💡 コツ: 「1つのエンティティに見えるもの」が複数コンテキストに分かれるのは失敗ではなく、むしろ健全な設計です。各コンテキストは同じ商品をIDで参照し、自分に必要な属性だけを持ちます。

### 確認問題

**問1.** ECサイトで「商品」をモデリングしています。カタログでは説明・画像・価格、在庫では棚番号と数量、配送では重量とサイズが必要です。設計として最も適切なのはどれでしょう?

1. カタログ・在庫・配送それぞれのコンテキストに、同じ商品IDを参照する別々のモデルを持たせる
2. 全属性を持つ単一の「商品」クラスを全コンテキストで共有する
3. 最も属性の多いカタログの「商品」を正とし、在庫と配送はそれを継承する
4. 商品を1つの共有データベーステーブルにまとめ、各コンテキストがそのテーブルを直接読み書きする

<details><summary>答えと解説</summary>

正解: **1**

「商品」は文脈ごとに意味(必要な属性と振る舞い)が変わるため、各コンテキストが同じIDを参照しつつ別々のモデルを持つのが正解です。全属性を1クラスに統一すると神クラス化し、どの部門の変更も全体に波及します。継承で共有すると結合が強すぎて独立して変更できず、共有テーブルの直接読み書きは境界を壊してデータ結合を生みます。同じものが複数モデルに分かれるのはDDDでは健全です。

</details>

**問2.** このECサイトの競争力の源泉は「他社より速く確実な受注・配送体験」だとします。コアドメイン(最も投資を集中すべき領域)として最も妥当なのはどれでしょう?

1. 決済処理(クレジットカードの課金)
2. 注文(受注とそのライフサイクル管理)
3. ユーザー認証・ログイン
4. 商品説明文のCMS編集機能

<details><summary>答えと解説</summary>

正解: **2**

競争力が「速く確実な受注・配送体験」にあるなら、その中核を担う注文コンテキストがコアドメインで、最良の人材とDDDのフルセットを投じるべきです。決済は外部の決済代行に任せられる汎用サブドメイン、認証はどの会社も同じ汎用サブドメインで、自作より既製品が定石です。CMS編集機能は支援サブドメインで、差別化要因にはなりません。

</details>

**問3.** 注文コンテキストが外部の決済ゲートウェイ(PSP)と連携します。PSPのAPIは独自のJSON構造とステータスコードを返します。最も適切な連携設計はどれでしょう?

1. PSPのレスポンス構造を注文コンテキストのドメインモデルにそのまま取り込んで使う
2. PSPのモデルに合わせて注文コンテキストのドメインモデルを作り直す
3. 注文とPSPの間に腐敗防止層(ACL)を置き、PSPのモデルを自分たちのモデルに変換する
4. 注文の集約から直接PSPのSDKを呼び、戻り値をそのままエンティティに保存する

<details><summary>答えと解説</summary>

正解: **3**

外部サービスの独自モデルが自分たちのドメインに侵食するのを防ぐため、腐敗防止層(ACL)で変換するのが定石です。PSPの構造をそのまま取り込んだり、相手に合わせてモデルを作り直すと、外部の都合でコアである注文モデルが汚染・振り回されます。集約から直接SDKを呼んで戻り値を保存するのも、ドメイン層にインフラの関心事が漏れ、ベンダーロックインと変更の波及を招きます。

</details>

**問4.** 注文確定時、在庫を引き当てる必要があります。注文コンテキストと在庫コンテキストの連携方法として最も疎結合で望ましいのはどれでしょう?

1. 注文集約の確定処理の中から、在庫テーブルを直接UPDATEして引き当てる
2. 在庫コンテキストが注文テーブルを常時ポーリングし、新しい注文を見つけたら引き当てる
3. 注文集約の中に在庫集約への参照を保持し、同一トランザクションで両方を更新する
4. 注文確定で「注文が確定した」イベントを発行し、在庫コンテキストがそれを購読して引き当てる

<details><summary>答えと解説</summary>

正解: **4**

コンテキストを跨ぐ連携は、ドメインイベントの発行と購読で疎結合に行うのが望ましい設計です。相手のテーブルを直接UPDATEするのは境界を壊し、注文集約が在庫集約を抱えて同一トランザクションで更新するのは「1トランザクション1集約」の原則に反してロック競合を招きます。相手テーブルの常時ポーリングは密結合かつ非効率で、注文側のスキーマ変更に在庫側が巻き込まれます。

</details>

**問5.** カタログの商品価格は時々変更されます。注文確定後にカタログ側で値下げがあっても、過去に確定した注文の金額は変わってはいけません。注文コンテキストでの価格の扱いとして最も適切なのはどれでしょう?

1. 注文確定時点の価格を注文明細にスナップショットとしてコピーして保持する
2. 注文は商品IDだけ保持し、表示や集計のたびにカタログから現在の価格を取得する
3. カタログの商品エンティティへの参照を注文明細が直接保持する
4. 価格は注文には持たず、カタログ側の価格履歴テーブルを都度照会して再計算する

<details><summary>答えと解説</summary>

正解: **1**

確定時の価格は注文明細にスナップショットとして保存し、カタログの後の変更から独立させるのが正解です。商品IDだけ持って毎回カタログの現在価格を引くと、値下げが過去の注文金額を書き換えてしまいます。カタログのエンティティを直接参照するのはコンテキスト境界を越えた結合で、価格履歴を都度再計算するのは複雑でカタログへの依存も残ります。過去の事実は確定時点の値で固定するのが鉄則です。

</details>

## 3. 注文コンテキストの戦術設計 — 集約・値・整合性を組む

### 注文集約の形

注文コンテキストの中を戦術的設計の道具で組み立てます。

| 要素 | 種類 | 役割 |
|---|---|---|
| `Order` | 集約ルート(エンティティ) | 注文全体の入口・不変条件の番人 |
| `OrderLine` | 内部エンティティ | 1明細(商品ID・数量・単価) |
| `Money` | 値オブジェクト | 金額(最小単位の整数+通貨) |
| `Quantity` | 値オブジェクト | 数量(1以上の制約を内包) |

集約ルートは L8、エンティティは L6、値オブジェクトは L7 で見たものです。**内部エンティティ**は、集約の中にだけいて外から直接は触らせないエンティティです。

**不変条件 (invariant、L8)** は集約ルートが守ります。

- 明細の小計の合計 = 注文の合計金額(常に一致)
- 確定(confirmed)後は明細の追加・変更ができない
- 明細は1件以上なければ確定できない

```go
func (o *Order) Confirm() error {
    if len(o.lines) == 0 {
        return errors.New("明細が空の注文は確定できません")
    }
    o.status = Confirmed
    o.events = append(o.events, OrderPlaced{OrderID: o.id})
    return nil
}
```

| 行 | 意味 |
|---|---|
| `func (o *Order) Confirm() error` | Order の確定メソッド。失敗したら error を返す |
| `if len(o.lines) == 0` | 明細の数が0なら(`len` は要素の数) |
| `return errors.New(...)` | 確定せずにエラーを返す(3つ目の不変条件) |
| `o.status = Confirmed` | 状態を「確定」にする |
| `o.events = append(o.events, OrderPlaced{...})` | 「注文が確定した」イベントを、注文の中のリストに足しておく |
| `return nil` | 成功(エラーなし) |

イベントはここで直接送らず、いったん `o.events` にためます。L10 で見たとおり、保存が成功した後でまとめて購読者へ配ります。

### 動かして確かめる

明細の追加(`AddLine`)と確定(`Confirm`)を持つ、動く完全版です。説明のため金額は `int`(円)で書いています。

```go
package main

import (
	"errors"
	"fmt"
)

type Status string

const (
	Draft     Status = "Draft"
	Confirmed Status = "Confirmed"
)

// ドメインイベント: 「注文が確定した」
type OrderPlaced struct {
	OrderID string
}

type OrderLine struct {
	ProductID string
	Quantity  int
	UnitPrice int
}

type Order struct {
	id     string
	lines  []OrderLine
	total  int
	status Status
	events []OrderPlaced
}

func NewOrder(id string) *Order {
	return &Order{id: id, status: Draft}
}

func (o *Order) AddLine(l OrderLine) error {
	if o.status == Confirmed {
		return errors.New("確定済みの注文には明細を追加できません")
	}
	o.lines = append(o.lines, l)
	o.total += l.Quantity * l.UnitPrice // 明細と合計を必ず一緒に更新する
	return nil
}

func (o *Order) Confirm() error {
	if len(o.lines) == 0 {
		return errors.New("明細が空の注文は確定できません")
	}
	o.status = Confirmed
	o.events = append(o.events, OrderPlaced{OrderID: o.id})
	return nil
}

func main() {
	empty := NewOrder("o-100")
	fmt.Println("空の注文を確定:", empty.Confirm())

	o := NewOrder("o-101")
	o.AddLine(OrderLine{ProductID: "p-1", Quantity: 2, UnitPrice: 500})
	o.AddLine(OrderLine{ProductID: "p-2", Quantity: 1, UnitPrice: 1200})
	fmt.Println("合計:", o.total)
	err := o.Confirm()
	fmt.Println("確定:", err, o.status)
	fmt.Println("たまったイベント:", o.events)
	fmt.Println("確定後に追加:", o.AddLine(OrderLine{ProductID: "p-3", Quantity: 1, UnitPrice: 300}))
	fmt.Println("合計(変わらない):", o.total)
}
```

実行結果:

```text
空の注文を確定: 明細が空の注文は確定できません
合計: 2200
確定: <nil> Confirmed
たまったイベント: [{o-101}]
確定後に追加: 確定済みの注文には明細を追加できません
合計(変わらない): 2200
```

- `AddLine` は明細を足すときに合計も同じメソッドの中で足すので、「明細の小計の合計 = 合計金額」が崩れません(500円×2 + 1200円×1 = 2200円)
- `確定: <nil>` の `<nil>` は、error が nil(エラーなし)であることを `fmt.Println` が表示した形です
- 確定後の `AddLine` はエラーになり、合計も 2200 のままです
- `o.total` を main から直接読めるのは、この例が1つのパッケージ(main)にまとめてあるからです。実際には `order` パッケージに分け、小文字のフィールドは外から触れないようにします(L8)

### 在庫引当は同一トランザクションにしない

注文確定と在庫引当を1つのDBトランザクション(L8 で見た「まとめて成功か、まとめて失敗か」の単位)でまとめたくなりますが、両者は**別コンテキスト=別集約**です。「1トランザクションで変更するのは1集約まで」の原則に従い、結果整合性 (eventual consistency、L9) で繋ぎます。

```text
Order.Confirm() → OrderPlaced イベント発行
  → 在庫コンテキストが購読 → 引当を試みる
      成功 → StockAllocated
      失敗 → StockAllocationFailed
          → 注文コンテキストが補償 → Order を Rejected に
```

引当に失敗したら `OrderRejected` で注文を取り消す**補償 (compensation)** を行います。補償は L9 で見たとおり、すでに確定した処理を、後から打ち消す業務の処理で元に戻すことです。時間の流れで見ると次のようになります。

| 時刻 | 起きること | 注文 o-8 の状態 |
|---|---|---|
| 10:00:00 | 注文を確定。OrderPlaced を発行 | Confirmed |
| 10:00:01 | 在庫コンテキストが引当を試み、在庫不足で StockAllocationFailed | Confirmed |
| 10:00:02 | 注文コンテキストがそれを受けて取り消す。OrderRejected | Rejected |

10:00:00〜10:00:02 の間は「確定済みだが在庫は未確保」という途中の状態があります。これが結果整合性で受け入れる遅れです。

### カートは注文とは別の集約

カート(Cart)と注文(Order)は一見近いですが、**ライフサイクル(生まれてから役目を終えるまでの流れ)が違います**。カートは何度も増減し放棄もされる一時的なもの、注文は確定したら不変の記録です。同じ集約にすると不変条件がぶつかるため、別集約にして「カートを確定すると注文が生まれる」と繋ぎます。

合計の計算を DB のトリガー(行が変わったときに DB が自動で動かす処理)に任せる方法もありますが、それでは「合計は明細と一致する」というルールがドメインのコードから見えなくなります。

> 💡 コツ: 「画面で一緒に見える」ことは集約をまとめる理由になりません。まとめる基準はあくまで**一緒に守るべき不変条件があるか**です。表示の都合はCQRS(L14)の読み取りモデルで解決します。

### 確認問題

**問1.** 注文集約には「明細の小計の合計は注文の合計金額と常に一致する」という不変条件があります。この不変条件を守る責務を置く場所として最も適切なのはどれでしょう?

1. 集約ルートであるOrderのメソッド(AddLineなど)の中で、明細操作と合計更新を一体で行う
2. 明細を追加するアプリケーションサービスのメソッド内で合計を再計算する
3. OrderLineの各インスタンスが自分で注文合計を更新する
4. DBのトリガーで合計カラムを自動更新する

<details><summary>答えと解説</summary>

正解: **1**

不変条件は集約ルート(Order)のメソッド内で、明細の変更と合計の更新を一体で行って守ります。こうすれば合計が崩れた中間状態が外から見えません。アプリケーションサービスに置くとルールがドメインの外に漏れ、別の経路で明細を変えたときに守られません。内部エンティティのOrderLineが全体の合計を触るのは責務の逆転、DBトリガーはビジネスルールがコードから見えなくなり移植性も失います。

</details>

**問2.** 注文確定(Order.Confirm)と在庫引当を、同じDBトランザクションでまとめて処理する案が出ました。DDDの観点で最も適切な判断はどれでしょう?

1. 整合性が確実になるので、1トランザクションでまとめるべき
2. 注文と在庫は別集約なので、同一トランザクションにせず、イベントによる結果整合性で繋ぐべき
3. 在庫集約を注文集約の内部に取り込んで、1つの集約として常に一緒に更新すべき
4. トランザクションは使わず、注文確定後に在庫を別スレッドで即座に書き換えればよい

<details><summary>答えと解説</summary>

正解: **2**

注文と在庫は別コンテキストの別集約なので、「1トランザクション1集約」の原則に従い、ドメインイベントによる結果整合性で繋ぐのが正解です。1トランザクションでまとめると集約境界を跨いだロックで競合やデッドロックを招きます。在庫を注文に取り込むのは神集約化し、別スレッドでトランザクション無しに書き換えるのは失敗時の整合性が保証されません。整合性の要求はイベント+補償で満たします。

</details>

**問3.** 注文確定イベントを受けた在庫引当が「在庫不足」で失敗しました。注文コンテキスト側の扱いとして最も適切なのはどれでしょう?

1. 失敗を無視し、注文は確定済みのまま残す
2. 在庫が復活するまで、注文確定処理のトランザクションをブロックして待ち続ける
3. StockAllocationFailedを受けて、OrderRejectedなどで注文を取り消す補償処理を行う
4. 在庫テーブルをマイナス値にしてでも強制的に引き当てる

<details><summary>答えと解説</summary>

正解: **3**

結果整合性のもとで下流の処理が失敗したら、上流が補償(compensation)で状態を戻すのが定石です。在庫引当失敗を受けて注文をRejectedにすれば、全体の整合性が回復します。失敗を無視すると在庫の裏付けのない注文が残り、トランザクションでブロックし続けるのは分散した集約では成立せずリソースを枯渇させます。在庫をマイナスにする強制引当は在庫の不変条件を破壊します。

</details>

**問4.** カート(Cart)と注文(Order)を同じ集約にまとめるべきか検討しています。DDDの観点で最も妥当な判断はどれでしょう?

1. 画面上で連続した操作なので、同じ集約にまとめるべき
2. カートは一時的だから集約にせず、ただのDTOとして注文集約の一部フィールドにすべき
3. どちらも商品を扱うので、共通の親集約を作って継承させるべき
4. ライフサイクルと不変条件が異なる(カートは可変で放棄されうる、注文は確定後不変)ため、別集約にすべき

<details><summary>答えと解説</summary>

正解: **4**

集約をまとめる基準は「一緒に守るべき不変条件があるか」であり、ライフサイクルの異なるカートと注文は別集約にします。カートは何度も増減・放棄される可変な存在、注文は確定後不変の記録で、同居させると相反する不変条件がぶつかります。画面上の連続性はまとめる理由になりません(表示はCQRSの読み取りモデルで解決)。共通の親による継承や、カートを注文のフィールドに埋め込むのも、別個のライフサイクルを無視した設計です。

</details>

**問5.** 注文明細の数量を表現するのに、これまでint型の生の値を使っていました。「数量は1以上でなければならない」というルールを最も堅牢に守る設計はどれでしょう?

1. 生成時に1以上を検証するQuantity値オブジェクトを作り、不正な数量は存在できないようにする
2. 明細を追加する各所で、呼び出し側がintの値を1以上かチェックする
3. DBのCHECK制約だけで数量>=1を保証する
4. 数量が0以下なら例外ではなく自動的に1に補正するヘルパー関数を用意する

<details><summary>答えと解説</summary>

正解: **1**

ルールを持つ値はQuantityのような値オブジェクトにして生成時に検証し、不正な状態を表現できないようにするのが最も堅牢です(make illegal states unrepresentable)。呼び出し側の各所でチェックするとルールが散らばり、1箇所でも漏れると不正値が混入します。DBのCHECK制約はアプリ内のロジックまでは守れず、0以下を黙って1に補正するのはデータを歪める危険な挙動で、本来は不正入力を拒否すべきです。

</details>

**問6.** この章の完全版で、明細「500円×2」「1200円×1」を追加して確定した注文に、さらに `AddLine` で「300円×1」を追加しようとしました。どうなるでしょう?

1. 明細が追加され、合計は 2500 になる
2. エラー「確定済みの注文には明細を追加できません」が返り、合計は 2200 のまま
3. 明細だけ追加され、合計は 2200 のまま
4. 注文の状態が Draft に戻ってから明細が追加される

<details><summary>答えと解説</summary>

正解: **2**

AddLine は最初に `o.status == Confirmed` を確認し、確定済みならエラーを返して何も変えません。そのため明細も合計も変わらず 2200 のままです。明細だけ増えて合計が変わらない、という状態は「明細の小計の合計 = 合計金額」の不変条件が崩れた状態で、合計の更新を同じメソッドの中で行っているので起こりません。確定を取り消して Draft に戻すような処理もありません。

</details>
