# 第5章 サブドメインと蒸留 — コアドメインに投資する

DDD は「すべてを丁寧に設計する」手法ではなく、**勝負どころ（コアドメイン）を見極めて投資を集中させる**手法です。この章ではサブドメインの3分類と、作る・買う・薄く作るの投資判断、そしてコアを雑味から分離する「蒸留」を学びます。設計の腕前よりも先に、この経営的な視点が DDD の土台になります。

## 1. サブドメインの3分類 — コア・支援・汎用

### ドメインは一枚岩ではない

「EC サイトのドメイン」とひとくくりに言っても、中身にはレコメンド、商品管理、決済、メール送信……と性質の違う領域が混ざっています。この一つひとつを**サブドメイン (Subdomain)** と呼び、DDD では重要度によって3つに分類します。

| 分類 | 定義 | 例（EC サイトの場合） |
|---|---|---|
| **コアドメイン (Core Domain)** | 競争優位の源泉。他社との差別化を生む勝負どころ | 独自のレコメンドエンジン、価格最適化 |
| **支援サブドメイン (Supporting Subdomain)** | 事業に必要で自社固有の業務だが、差別化はしない | 商品マスタ管理、自社ルールの在庫引当 |
| **汎用サブドメイン (Generic Subdomain)** | どの会社でもほぼ同じ。既製品で置き換え可能 | 認証、メール配信、会計 |

### 「何がコアか」は会社によって変わる

同じ機能でも、**事業の勝ち筋がどこにあるか**で分類は変わります。配送ルート最適化は、物流会社にとっては利益を直接左右するコアドメインですが、EC サイトにとっては「ちゃんと届けばよい」支援サブドメイン（あるいは外部委託する汎用）かもしれません。つまりこの分類は技術の問題ではなく、**ビジネス戦略の問題**です。

### なぜ分類するのか

チームの時間と優秀なエンジニアは有限です。すべての領域に同じ密度の設計を施すと、肝心のコアが薄まります。分類は「どこに DDD の重厚な道具立てを使い、どこは簡素に済ませるか」を決めるための地図です。

💡 コツ: 迷ったら「この機能が競合より優れていたら、顧客はうちを選ぶか？」と自問してください。Yes ならコア候補、No なら支援か汎用です。

### 確認問題

**問1.** コアドメイン (Core Domain) の説明として最も適切なものはどれでしょう？

1. システムの中で最もコード量が多い領域
2. どの会社でも共通に必要となる基盤機能
3. 競争優位の源泉となり、他社との差別化を生む領域
4. 障害が起きると最も損害が大きい領域

<details><summary>答えと解説</summary>

正解: **3**

コアドメインは「他社との差別化を生む勝負どころ」であり、ビジネス戦略上の重要度で決まります。コード量の多さは重要度と無関係です（汎用機能が巨大なこともあります）。どの会社でも共通に必要な機能はむしろ汎用サブドメインの定義です。障害時の損害の大きさは可用性の話であり、決済のような汎用寄りの領域でも損害は大きいため、コアの判定基準にはなりません。

</details>

**問2.** あなたは EC サイトの開発チームにいます。自社は「好みを先回りする独自レコメンド」を売りにして競合と差別化しており、実際にレコメンド経由の売上が大半を占めます。このレコメンドエンジンの分類として最も適切なものはどれでしょう？

1. コアドメイン — 差別化の源泉であり投資を集中すべき領域
2. 支援サブドメイン — 売上を支えるが本業ではない領域
3. 汎用サブドメイン — レコメンドは既製の SaaS が多数あるため
4. サブドメインではなく境界づけられたコンテキストとして扱う

<details><summary>答えと解説</summary>

正解: **1**

「それで顧客がうちを選んでいる」機能はコアドメインの典型です。支援サブドメインは「必要だが差別化しない」領域なので、差別化の主役であるこのレコメンドには当てはまりません。既製 SaaS が存在するかどうかは判断材料の一つですが、自社の勝ち筋そのものを既製品に置き換えたら差別化が消えるため、汎用とは言えません。サブドメインは問題空間の分類、境界づけられたコンテキストは解空間の区切りで、層の違う概念なので置き換えにはなりません。

</details>

**問3.** 「配送ルート最適化」という同じ機能について、A社（物流会社）と B社（EC サイト）での分類を考えます。最も適切な組み合わせはどれでしょう？

1. A社・B社ともにコアドメイン — 物を届ける機能はどの会社でも最重要のため
2. A社・B社ともに汎用サブドメイン — 地図 API など既製品があるため
3. A社は支援サブドメイン、B社はコアドメイン
4. A社はコアドメイン、B社は支援または汎用サブドメイン

<details><summary>答えと解説</summary>

正解: **4**

物流会社にとって配送ルート最適化は利益率と納期を直接左右する勝負どころ、つまりコアドメインです。一方 EC サイトにとっては「きちんと届けばよい」機能であり、自社固有の運用があれば支援、外部の配送サービスに任せるなら汎用です。このように**同じ機能でも事業の勝ち筋によって分類が変わる**のがポイントです。「どの会社でも最重要」「既製品があるから汎用」という一律の決め方は、分類がビジネス戦略で決まるという原則に反します。

</details>

**問4.** 自社サービスのログイン・ユーザー認証基盤の分類として、通常最も適切なものはどれでしょう？（認証技術そのものを売る会社ではないものとします）

1. コアドメイン — セキュリティは事業の信頼の根幹だから
2. 汎用サブドメイン — どの会社でもほぼ同じ機能であり、既製品で置き換え可能だから
3. 支援サブドメイン — 自社ユーザー固有の情報を扱うから
4. 分類不能 — 全サブドメインから利用されるため

<details><summary>答えと解説</summary>

正解: **2**

認証は「重要だが、どの会社でも中身はほぼ同じ」機能の代表例で、汎用サブドメインです。重要性・セキュリティ上の深刻さと、差別化に効くかどうかは別の軸です（認証が優れているからという理由でそのサービスを選ぶ顧客はまずいません）。自社ユーザーの情報を扱うこと自体はどの汎用機能にも言えるため、支援の根拠にはなりません。多くの領域から使われることと分類できないことも無関係です。ひっかけどころは「重要そうなものをコアと呼びたくなる」心理です。

</details>

**問5.** 支援サブドメイン (Supporting Subdomain) の特徴として最も適切なものはどれでしょう？

1. 既製のパッケージや SaaS でそのまま置き換えられる
2. 事業価値が低いため、将来的に廃止すべき領域である
3. 事業に必要で自社固有の業務を含むが、競争上の差別化はしない
4. コアドメインの候補であり、投資すればコアに昇格する

<details><summary>答えと解説</summary>

正解: **3**

支援サブドメインは「自社固有のやり方があるので既製品がそのまま使えないが、そこで勝負しているわけでもない」領域です。既製品でそのまま置き換えられるのは汎用サブドメインで、支援はまさに置き換えきれない自社固有部分がある点で汎用と区別されます。差別化しない＝価値がない・廃止すべき、ではありません（止まれば事業も止まります）。また投資すればコアになるわけではなく、コアかどうかはビジネス戦略上の勝ち筋で決まります。

</details>

## 2. 投資判断 — 作る・買う・薄く作る

### 分類は投資判断のためにある

サブドメインを3分類したら、それぞれに**かける力の配分**を変えます。

| 分類 | 基本方針 | 体制・実装 |
|---|---|---|
| コアドメイン | **内製で作り込む (Build)** | 最良の人材を投入し、DDD の道具立て（ユビキタス言語・集約・ドメインモデル）をフルに使う |
| 汎用サブドメイン | **買う (Buy)** | SaaS・パッケージ・OSS を採用。内製は原則しない |
| 支援サブドメイン | **薄く作る** | 必要十分のシンプルな実装。CRUD やトランザクションスクリプトで足りることも多い |

支援サブドメインに重厚なドメインモデルは不要なことが多く、「DDD を学んだから全部に集約を作る」のは典型的な過剰設計です。**DDD の戦術パターンはコアにこそ効く**と覚えてください。

### ありがちな失敗パターン

- **汎用の作り込み**: 認証基盤や通知基盤の内製にエースを投入し、コアが手薄になる。エンジニアには「作りたい基盤」ほど汎用寄りという罠があります
- **コアの外注**: 勝負どころを外部ベンダーに丸投げし、ドメイン知識が社内に残らない。外注してよいのは汎用、次点で支援です

### サブドメインと境界づけられたコンテキスト

サブドメインは**問題空間 (problem space)**＝ビジネスをどう分けて捉えるか、境界づけられたコンテキストは**解空間 (solution space)**＝モデルとコードをどう区切るか、という別レイヤーの概念です。理想は1対1対応ですが、レガシーシステムが複数サブドメインを抱えているなど、現実にはズレます。ズレを認識できること自体が、分類を行う価値のひとつです。

💡 コツ: 投資判断は「機能の重要度」ではなく「差別化への寄与」で下します。重要でも差別化しないなら、買うか薄く作るのが正解です。

### 確認問題

**問1.** 経理部門から「会計処理をシステム化したい」と要望がありました。会計は自社の差別化要素ではありません。アーキテクトとしての判断として最も適切なものはどれでしょう？

1. 自社の業務に完全に合わせるため、ドメインモデルを設計して内製する
2. 汎用サブドメインなので、実績のある会計 SaaS やパッケージの導入を第一候補にする
3. コアドメインに昇格させ、最良の人材を投入する
4. 重要な機能なので、外部ベンダーに新規開発を発注する

<details><summary>答えと解説</summary>

正解: **2**

会計は「どの会社でもほぼ同じ」汎用サブドメインの代表例であり、買う (Buy) が基本方針です。内製は開発・保守コストに見合う差別化を生みません。重要性が高いことはコアの根拠にならず（重要度と差別化は別の軸）、昇格という考え方も誤りです。新規開発の外注は「作る」選択肢の変形であり、既製品がある汎用にゼロから作る理由がありません。ひっかけどころは「自社の業務に完全に合わせる」という一見正しい動機で、汎用領域では業務側をパッケージ標準に合わせる方が総コストは低いのが定石です。

</details>

**問2.** チームで最も設計力のあるエンジニアが「社内通知基盤を汎用的に作り直したい。腕の見せどころだ」と提案しています。一方、差別化の核である与信モデルの改善は人手不足です。マネジメントとして最も適切な判断はどれでしょう？

1. 本人のモチベーションを尊重し、通知基盤の内製を任せる
2. 通知基盤と与信モデルを並行で担当してもらう
3. 通知基盤を先に完成させてから与信モデルに移ってもらう
4. 通知は既製サービスの採用を検討し、そのエンジニアはコアである与信モデルに投入する

<details><summary>答えと解説</summary>

正解: **4**

最良の人材はコアドメインに投入するのが DDD の投資原則です。通知基盤は典型的な汎用サブドメインで、既製サービスで十分置き換えられます。「エンジニアが作りたがる基盤ほど汎用寄り」という罠があり、モチベーション尊重だけで任せるとコアが手薄になります。並行担当は一見バランスが良さそうですが、勝負どころへの集中を薄める中途半端な策です。「先に基盤」も、差別化に直結しない作業でコアの改善を遅らせる点で優先順位が逆です。

</details>

**問3.** 支援サブドメインにあたる「自社ルールでの備品貸出管理」を実装します。実装方針として最も適切なものはどれでしょう？

1. 必要十分なシンプルな実装にとどめる。CRUD やトランザクションスクリプトで足りるならそれでよい
2. 将来コアになる可能性に備え、集約とドメインイベントを備えたフルのドメインモデルで作る
3. 自社固有ルールは諦め、市販の備品管理パッケージに業務を完全に合わせる
4. コアドメインと同じコードベースに同居させ、設計の一貫性を保つ

<details><summary>答えと解説</summary>

正解: **1**

支援サブドメインの方針は「薄く作る」です。DDD の重厚な戦術パターンはコアにこそ効くもので、差別化しない領域への適用は過剰設計になり保守コストだけが残ります。「将来に備えてフル装備」は典型的な YAGNI 違反で、コアかどうかはビジネス戦略で決まるため先回り投資は根拠がありません。市販品への完全な置き換えは汎用サブドメインの定石であり、自社固有ルールが必要だからこそ支援に分類されている点と矛盾します。コアと同居させると、コアの変更が支援の都合に引きずられ、蒸留と逆行します。

</details>

**問4.** サブドメインと境界づけられたコンテキスト (Bounded Context) の関係の説明として最も適切なものはどれでしょう？

1. 同じ概念の新旧の呼び名であり、使い分ける必要はない
2. 境界づけられたコンテキストを先に設計し、それに合わせてサブドメインを定義する
3. サブドメインは問題空間、境界づけられたコンテキストは解空間の概念で、理想は1対1だが現実にはズレることがある
4. サブドメイン1つに対し、境界づけられたコンテキストを必ず複数作るべきである

<details><summary>答えと解説</summary>

正解: **3**

サブドメインは「ビジネスという問題をどう分けて捉えるか」（問題空間）、境界づけられたコンテキストは「モデルとコードをどう区切るか」（解空間）で、レイヤーの違う概念です。理想は1対1対応ですが、レガシーが複数サブドメインを抱えるなどズレは起こります。同じ概念の別名ではありません。順序も逆で、問題空間の把握（サブドメイン）が先にあり、解空間（コンテキスト）をそれに寄せていくのが筋です。「必ず複数作る」という規則も存在しません。

</details>

**問5.** 経営層から「差別化の核である独自の価格決定ロジックの開発を、コスト削減のため外部ベンダーへ全面委託したい」と相談されました。DDD の観点から最も適切な助言はどれでしょう？

1. ドキュメントを整備すれば知識は残るため、全面委託に賛成する
2. コアドメインの外注はドメイン知識が社内に蓄積されなくなるため避け、委託するなら汎用・支援領域を候補にする
3. 価格決定ロジックを汎用サブドメインに分類し直し、委託を正当化する
4. 全サブドメインを等しく内製すべきであり、いかなる委託にも反対する

<details><summary>答えと解説</summary>

正解: **2**

コアドメインは競争優位の源泉であり、そこで得られるドメイン知識とモデルの改善サイクルこそが資産です。外注すると知識がベンダー側に溜まり、差別化の進化が止まります。委託でコストを下げたいなら汎用（さらに言えば購入）や支援が先です。ドキュメントは知識の一部しか写せず、モデルを育てる日々の対話は委託先に移ってしまいます。分類はビジネス戦略で決まるものなので、委託の都合で汎用に「分類し直す」のは本末転倒です。一方、すべてを内製すべきという主張も誤りで、汎用は買うのが原則です。

</details>

## 3. 蒸留とドメインビジョン — コアを雑味から分離する

### 蒸留 (Distillation) とは

コアドメインは、放っておくと支援・汎用の関心事（通知、帳票、権限チェック……）と絡み合い、雑味に埋もれていきます。**蒸留**とは、モデルやコードからコアの価値を分離・抽出し続ける活動です。ウイスキーの蒸留と同じで、一度やって終わりではなく繰り返し行います。

代表的な蒸留の道具:

- **ドメインビジョン声明文 (Domain Vision Statement)**: コアドメインの価値と方向性を1枚程度の短い文章で言語化したもの。「このシステムは何で勝つのか」を新旧メンバーと経営が共有するための文書です
- **セグリゲートされたコア (Segregated Core)**: コアのモデルを独立したパッケージ／モジュールに隔離し、支援・汎用のコードから切り離すリファクタリング。コアの変更が雑味に邪魔されなくなります
- **汎用サブドメインの切り出し**: モデルに紛れ込んだ汎用的な概念（カレンダー計算、金額換算など）を外に出し、コアを軽くします

### 「何がコアか」を決めるのは誰か

コアの判定は技術ではなく**ビジネス戦略の判断**なので、エンジニアだけで決めてはいけません。経営・事業責任者との対話を通じて「どこで勝つのか」を確認し、ドメインビジョン声明文に落とします。逆に言えば、この対話ができることが DDD を名乗る最低条件です。

### コアは移ろう

競合が追いついた機能はもはや差別化を生まず、コアから支援・汎用へ格下げされることがあります。逆に新しい勝ち筋が生まれればコアが移ります。分類と蒸留は**定期的に見直す**ものだと覚えておきましょう。

💡 コツ: 新しく入ったメンバーに「このプロダクトは何で勝ってるの？」と聞かれて1分で答えられないなら、ドメインビジョン声明文を書くタイミングです。

### 確認問題

**問1.** DDD における蒸留 (distillation) の説明として最も適切なものはどれでしょう？

1. データベースを正規化して冗長なテーブルを除去すること
2. リリース前にコードから不要なログ出力やデバッグコードを除去すること
3. コアドメインの価値を支援・汎用の関心事から分離・抽出し続ける活動のこと
4. サブドメインをすべて同じ粒度のマイクロサービスに分割すること

<details><summary>答えと解説</summary>

正解: **3**

蒸留はコアを雑味（支援・汎用の関心事）から分離し、価値を際立たせ続ける活動です。一度きりの作業ではなく繰り返し行う点も特徴です。データベースの正規化やデバッグコードの除去は一般的なエンジニアリング衛生であり、コアの分離という戦略的な目的を持ちません。マイクロサービス分割は実装手段の話で、しかも「すべて同じ粒度」は投資配分を変えるという蒸留の思想と逆行します。

</details>

**問2.** ドメインビジョン声明文 (Domain Vision Statement) の説明として最も適切なものはどれでしょう？

1. コアドメインの価値と方向性を短い文章で言語化し、チームと経営で共有する文書
2. システムの全機能を網羅した要件定義書
3. 各マイクロサービスの API 仕様を記述した技術文書
4. 四半期ごとの開発ロードマップとリリース計画

<details><summary>答えと解説</summary>

正解: **1**

**問3.** コアである価格計算モデルのコードが、通知・帳票・権限チェックのコードと同じパッケージで絡み合い、小さな変更にも時間がかかっています。この状況への対処として最も適切なものはどれでしょう？

1. 変更を速くするため、価格計算のテストコードを削減する
2. セグリゲートされたコアを適用し、価格計算モデルを独立したパッケージに隔離する
3. 絡み合いを受け入れ、全体を一括で書き直す日のために現状を凍結する
4. 通知・帳票・権限チェックを価格計算モデルの内部に取り込み、1か所にまとめる

<details><summary>答えと解説</summary>

正解: **2**

コアが雑味と絡み合って変更しづらい、という症状への DDD の処方箋がセグリゲートされたコア (Segregated Core) です。コアを独立パッケージに隔離すれば、コアの進化が周辺の都合に邪魔されなくなります。テスト削減は変更の安全性を壊すだけで分離の代わりになりません。「いつかの全面書き直し」待ちの凍結は、その間コアの改善が止まる最悪手です。周辺関心事をさらに取り込む案は絡み合いを強める方向で、蒸留と真逆です。

</details>

**問4.** 「何がコアドメインか」を決める進め方として最も適切なものはどれでしょう？

1. 最も技術的に複雑なモジュールをアーキテクトがコアと認定する
2. コード量と変更頻度のメトリクスから機械的に判定する
3. チームのエンジニアだけで投票して決める
4. 経営・事業責任者との対話で「どこで勝つのか」を確認して決める

<details><summary>答えと解説</summary>

正解: **4**

コアの判定はビジネス戦略の判断であり、「どこで勝つか」を知っているのは経営・事業側です。だからこそ対話が必須で、結果をドメインビジョン声明文に落とします。技術的な複雑さはコアの証拠ではありません（汎用領域が複雑なこともよくあります）。コード量や変更頻度も実装の事情を映すだけで、差別化への寄与は測れません。エンジニアだけの投票は、戦略情報を持たないメンバーで戦略判断をすることになり、的を外しやすい進め方です。

</details>

**問5.** 3年前はコアだった「即日配送の独自物流網」機能に、競合各社がほぼ追いつきました。今後の扱いとして最も適切な判断はどれでしょう？

1. 分類を見直し、差別化に効かなくなったなら支援・汎用側へ格下げして投資配分を変える
2. 過去にコアだった実績を尊重し、今後もコアとして最優先投資を続ける
3. 一度決めた分類を変えると混乱するため、見直しは行わない
4. 機能ごと廃止する — コアでなくなった機能に価値はないため

<details><summary>答えと解説</summary>

正解: **1**

コアドメインは固定ではなく、競合のキャッチアップや戦略転換で移ろいます。差別化に効かなくなったなら格下げし、浮いた投資を新しい勝ち筋に回すのが正しい動きです。「過去の実績」での継続投資は、差別化を生まない領域にエースを張り付ける失敗パターンそのものです。分類の見直しをしないのは、分類がビジネス戦略を映す生きた地図であるという前提に反します。格下げ＝廃止でもありません。即日配送は依然事業に必要であり、支援サブドメインとして薄く維持するのが妥当です。

</details>
