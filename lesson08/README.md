# 第8章 集約① — 不変条件とトランザクション境界

DDDの戦術的設計でいちばん重要なのが集約です。この章では「不変条件を守る単位」「トランザクションの境界」という集約の2つの顔を理解し、Goでの実装の型まで一気に身につけます。

## 1. 集約とは — 不変条件を守る単位

### 集約 (Aggregate) — 「一緒に守る」ものをひとまとめにする

L6 のエンティティ(ID で区別するオブジェクト)と L7 の値オブジェクト(値で区別する不変のオブジェクト)を、バラバラに操作できてしまうと、「オブジェクト同士の整合性を誰が守るのか」が曖昧になります。**整合性**とは、データ同士が矛盾していないことです。

**集約 (Aggregate)** は、**一緒に変更され、一緒に整合性を守るべきオブジェクトのまとまり**です。

鍵になるのが**不変条件 (invariant)** — 変更の前後で**常に**満たされていなければならないビジネスルールです。「不変」は値が変わらないという意味ではなく、「このルールが成り立っている」という事実が変わらない、という意味です。

| 用語 | 意味 |
|---|---|
| 集約 (Aggregate) | 整合性を一緒に守るオブジェクトの塊 |
| 集約ルート (Aggregate Root) | 外部から集約へアクセスする**唯一の入口**となるエンティティ |
| 不変条件 (invariant) | 「明細の合計 = 注文の合計金額」「明細は10行まで」のような常時成立ルール |

### 例: 注文と注文明細

注文 o-001 の中身を、値を入れて見てみます。

| 注文明細 (OrderLine) | 商品 | 単価 | 数量 | 小計 |
|---|---|---|---|---|
| 1行目 | マグカップ | 1,200円 | 2 | 2,400円 |
| 2行目 | コースター | 300円 | 4 | 1,200円 |
| **注文 (Order) の合計金額** | | | | **3,600円** |

「注文明細の小計の合計は、注文の合計金額と常に一致する」というルールがあるなら、注文 (Order) をルート、注文明細 (OrderLine) を内部エンティティとする1つの集約にします。もし外のコードが2行目の数量だけを 4 から 10 に直接書き換えると、明細の合計は 5,400円 なのに注文の合計金額は 3,600円 のまま、という矛盾が生まれます。そこで明細の追加・削除・変更は必ずルート (Order) のメソッド経由にし、Order が合計金額も一緒に直すようにします。

```go
order := NewOrder(customerID)
if err := order.AddItem(productID, 2); err != nil { // ルート経由 → 内部で不変条件を検証
    return err
}
// order.items = append(order.items, ...) ← 外部からの直接操作は許さない
```

| 行 | 意味 |
|---|---|
| `order := NewOrder(customerID)` | 会員の ID を渡して、新しい注文(集約ルート)を作る(L6 で見たコンストラクタ関数) |
| `if err := order.AddItem(productID, 2); err != nil {` | 商品を2個、ルートの AddItem メソッド経由で追加する。`if 文1; 条件 {` は「文1 を実行してから条件を調べる」書き方で、ここで作った err は if の中だけで使える。追加に失敗したら(err が nil でなければ) |
| `return err` | エラーをそのまま呼び出し元に返す |
| `// order.items = append(...)` | 明細のスライスに外から直接追加するのは禁止。コメントアウト(`//` で無効化)して「書いてはいけない例」として示している |

このコードを動く形にしたものは ch03 で実行します。

外部のコードが OrderLine を直接取得して書き換えられると、ルートが守っているルールを**迂回**できてしまいます。だから**リポジトリ**(集約を保存・取り出しする役目の部品。詳しくは L11)も集約ルート単位にしか作りません。

💡 コツ: 集約の境界は「クラス図(オブジェクト同士の関係を描いた図)で関連があるか」ではなく、**「どのデータが同時に変わるか」「どのルールを一瞬たりとも破れないか」**で決めます。会員と注文のように、変更のタイミングも守るルールも別なものは、関連があっても**別集約**にして ID で参照します(注文は会員そのものを抱えず、会員 ID `c-001` だけを持つ。詳しくは L9)。

### 確認問題

**問1.** ECサイトの注文には「明細の合計金額は注文の合計金額と常に一致する」というルールがあります。注文(Order)と注文明細(OrderLine)の設計として最も適切なのはどれでしょう?

1. OrderとOrderLineをそれぞれ独立した集約にし、別々のリポジトリで保存する
2. Orderを集約ルート、OrderLineをその内部に置き、明細の追加・削除はOrderのメソッド経由にする
3. OrderLineを集約ルートにし、Orderをその内部エンティティにする
4. オブジェクト側では関連を持たせず、合計一致はDBの制約だけで守る

<details><summary>答えと解説</summary>

正解: **2**

「常に一致」という不変条件を一緒に守るべきオブジェクトは同じ集約に入れ、変更をルート経由に限定するのが集約の基本です。独立した集約+別リポジトリにすると、明細だけ更新されて合計が崩れる瞬間を防げません。OrderLineをルートにするのは主従が逆で、明細は注文の文脈でしか意味を持ちません。「合計の一致」のような計算を伴うルールはDB制約では表現しにくく、ルールがコードから見えなくなる点でも不適切です。

</details>

**問2.** 集約ルート (Aggregate Root) の説明として正しいものはどれでしょう?

1. 集約の中で最も多くのデータを持つオブジェクト
2. 性能向上のために集約の内容をキャッシュするオブジェクト
3. DBの主キーを持つテーブルに対応するオブジェクト
4. 外部から集約へアクセスする唯一の入口となるエンティティ

<details><summary>答えと解説</summary>

正解: **4**

集約ルートは「唯一の入口」です。外部は必ずルートのメソッドを通して集約を操作するため、ルートが不変条件の番人になれます。データ量の多さやキャッシュは無関係です。「主キーを持つテーブル」という説明はDB視点であり、集約はドメインモデル上の概念です(内部エンティティも主キーを持ち得ます)。

</details>

**問3.** 同僚が「OrderLineRepository を作って明細を直接取得・更新できるようにしたい」と提案しました。DDDの観点で最も適切な指摘はどれでしょう?

1. 集約内部のオブジェクトを直接更新すると、ルートが守るべき不変条件(合計一致など)を迂回してしまうため、Order経由で操作すべき
2. リポジトリはいくつ作ってもよいので、便利なら賛成する
3. OrderLineにもIDがあるなら独立したリポジトリを作って問題ない
4. DBトランザクションで囲めば直接更新しても安全なので問題ない

<details><summary>答えと解説</summary>

正解: **1**

リポジトリは集約ルート単位に作るのが原則です。内部オブジェクトを直接更新できる経路を作ると、ルートのメソッドに書いた検証がすべて素通りされます。IDの有無は関係ありません(内部エンティティもIDを持ちます)。DBトランザクションが守るのは原子性であって、「合計が一致する」といったビジネスルールは守ってくれません。

</details>

**問4.** 不変条件 (invariant) の説明として最も適切なのはどれでしょう?

1. システム起動中に変化しない設定値のこと
2. イミュータブルな値オブジェクトの別名
3. 集約が変更の前後で常に満たしていなければならないビジネスルール
4. DBのNOT NULL制約の別名

<details><summary>答えと解説</summary>

正解: **3**

不変条件は「明細は10行まで」「残高はマイナス不可」のような、どの変更の後でも必ず成立しているべきビジネスルールです。設定値(定数)や値オブジェクトの不変性(immutability)と字面が似ているのがひっかけポイントですが、別の概念です。DB制約は不変条件を補強する手段にはなりますが、同義ではありません。

</details>

**問5.** 会員(Customer)は住所変更が頻繁にあり、注文(Order)は明細の追加が頻繁にあります。両者の設計として最も適切なのはどれでしょう?

1. 会員と注文は業務上関連が深いので、1つの大きな集約にまとめる
2. 変更のタイミングも守る不変条件も別なので、CustomerとOrderは別集約にし、OrderはCustomerのIDを参照として持つ
3. 性能のため、すべての集約はエンティティ1個だけで構成する
4. 集約はDBのテーブルと必ず1対1に対応させる

<details><summary>答えと解説</summary>

正解: **2**

住所変更と明細追加は別々のルールを守る別々の変更です。一緒に変わらないものを同じ集約に入れると、巨大化してロック競合や読み込みコストの問題を招きます(次チャプターで詳述)。他の集約はオブジェクトそのものではなくIDで参照するのが定石です。「集約=1エンティティ」「集約=テーブル」という機械的な対応づけは、不変条件という本来の判断基準を無視しています。

</details>

**問6.** 注文 o-001 は明細が2行(小計 2,400円 と 1,200円)、合計金額 3,600円 です。外部のコードが2行目の明細を直接取得し、小計を 3,000円 に書き換えました。注文の合計金額は 3,600円 のままです。このとき起きていることとして最も適切なものはどれでしょう？

1. 集約ルートを迂回したため、「明細の小計の合計 = 注文の合計金額」という不変条件が破れている
2. 注文の合計金額はあとで計算し直せばよいので、問題は起きていない
3. 明細もエンティティなので、直接書き換えるのが正しい手順である
4. 値オブジェクトの不変性が破れているだけで、集約とは関係がない

<details><summary>答えと解説</summary>

正解: **1**

明細の小計の合計は 2,400 + 3,000 = 5,400円 になったのに、注文の合計金額は 3,600円 のままなので、「常に一致する」という不変条件が破れています。原因は、集約ルート (Order) のメソッドを通さず内部の明細を直接書き換えたことです。ルート経由なら Order が合計金額も一緒に直します。「あとで直せばよい」は、その間に矛盾したデータが読まれてしまうので不変条件の考え方に反します。明細が ID を持つエンティティでも、集約の内部にある以上、外から直接触らずルート経由で操作します。

</details>

## 2. トランザクション境界としての集約

### 基礎の基礎: DB のトランザクション

**トランザクション**は、データベース(DB)に対する複数の書き込みを「全部成功」か「全部なかったことにする」かのどちらかにまとめる仕組みです。

| 手順 | 銀行の振込を1つのトランザクションで行う例 |
|---|---|
| 1 | A さんの口座から 1,000円 減らす |
| 2 | B さんの口座に 1,000円 増やす |
| 成功したら | **コミット**(確定)。2つの書き込みが同時に反映される |
| 途中で失敗したら | **ロールバック**(取り消し)。1 も取り消され、A さんのお金だけが消えることはない |

トランザクションの実行中、DB は書き換え中の行に**ロック**(他の処理がその行を同時に書き換えないよう待たせる仕組み)をかけます。ロックがかかっている間、同じ行を書き換えたい別の処理は待たされるか、エラー(同時更新エラー)になります。

### 鉄則: 1トランザクションで変更する集約は1つまで

集約には「不変条件を守る単位」(ch01)のほかにもう1つの顔があります。**トランザクションの境界 (transactional boundary)** です。

> **1つのトランザクションでは、1つの集約だけを変更する** — これがDDDの鉄則です。

集約は「ここまでは即時に一貫していることを保証する」という**一貫性の境界 (consistency boundary)** であり、実装上は**ロックの単位**でもあります。

```go
// ❌ 2つの集約を同一トランザクションで更新
tx.Save(order)  // 注文集約
tx.Save(stock)  // 在庫集約 — 境界をまたいでいる

// ✅ 注文の確定だけをコミットし、在庫はイベントで結果整合
order.Confirm() // → OrderConfirmed イベント発行
repo.Save(order)
// 在庫サービスがイベントを受けて別トランザクションで引き当て
```

このコードは考え方を示す擬似コード(実際の部品を省いた、説明用のコード)で、このままでは動きません。

| 行 | 意味 |
|---|---|
| `tx.Save(order)` / `tx.Save(stock)` | tx は1つのトランザクション。その中で注文と在庫の2つの集約を保存している(❌) |
| `order.Confirm()` | 注文を「確定」にする。このとき「注文が確定した」という出来事の記録(OrderConfirmed イベント)を作る |
| `repo.Save(order)` | リポジトリ(集約を保存する部品。詳しくは L11)で、注文だけを保存する |
| 最後のコメント | 在庫を担当する処理がそのイベントを受け取り、**別の**トランザクションで在庫を減らす |

集約をまたぐ整合性は、**結果整合性 (eventual consistency)** — ドメインイベント(業務上の出来事の記録。詳しくは L10)などを使って「少し遅れて必ず整合する」形で守ります(結果整合性は L9 で詳しく扱います)。時間の流れで見ると次のようになります。

| 時刻 | 注文 o-001 | 在庫(マグカップ) | 説明 |
|---|---|---|---|
| 10:00:00.000 | 確定 | 5個 | 注文だけをコミット。在庫はまだ減っていない |
| 10:00:00.300 | 確定 | 3個 | 在庫の処理がイベントを受け取り、2個を引き当てた |

0.3 秒の間は「注文は確定したのに在庫は減っていない」状態ですが、最後には必ず整合します。

### どちらで守るかはビジネスが決める

| 質問 | 答えが「はい」なら |
|---|---|
| そのルールが一瞬でも破れると業務上の損害が出るか? | 同一集約に入れて**即時一貫**で守る |
| 数秒〜数分後に整合すれば業務が回るか? | 別集約にして**結果整合**で守る |

「在庫の引き当てが数秒遅れてもよいか」はエンジニアではなく**ドメインエキスパート**(L1 で見た、業務に詳しい人)に確認すべき問いです。技術的な好みで決めてはいけません。

### 境界を誤るとどうなるか

| 境界が大きすぎる | 境界が小さすぎる |
|---|---|
| 読み込み・ロックの単位が肥大化し、無関係な変更同士が競合する | 本来即時に守るべき不変条件が集約の外にはみ出し、守れなくなる |

大きすぎる例: 「会員と、その全注文履歴」を1つの集約にすると、会員の住所変更と、注文 A の明細追加という無関係な操作が、同じ集約のロックを取り合います。注文が 1,000 件ある会員なら、住所を1つ変えるだけで 1,000 件の注文もまとめて読み込むことになります。

💡 コツ: 「とりあえず関連を全部入れた巨大集約」は最頻出の失敗です。迷ったら小さく切り、即時一貫が必要だと**証明されたものだけ**を同じ集約に入れます。

### 確認問題

**問1.** 集約とトランザクションの関係について、DDDの原則として最も適切なのはどれでしょう?

1. 1つのトランザクションでできるだけ多くの集約を更新し、整合性を高める
2. トランザクションは使わず、すべての整合性を結果整合性で扱う
3. 1つのトランザクションで変更する集約は原則1つまでにする
4. 集約とトランザクションは無関係なので自由に設計してよい

<details><summary>答えと解説</summary>

正解: **3**

集約は一貫性の境界＝トランザクションの境界です。複数集約を同一トランザクションで更新すると、境界設計の意味が失われ、ロック範囲も広がります。「全部まとめて更新した方が安全」に見えるのがひっかけで、実際にはロック競合と結合度の増大を招きます。すべて結果整合にするのも誤りで、集約の内部は即時一貫で守ります。

</details>

**問2.** 注文確定時に在庫も減らす必要があります。注文(Order)と在庫(Stock)は別集約です。最も適切な設計はどれでしょう?

1. 注文確定時に「注文が確定した」ドメインイベントを発行し、在庫の引き当ては別トランザクションで結果整合的に行う
2. OrderとStockを同一トランザクションで同時に更新する
3. OrderとStockを1つの集約に統合する
4. 在庫は参照用のビューなので更新しない

<details><summary>答えと解説</summary>

正解: **1**

別集約をまたぐ更新はドメインイベント経由の結果整合が定石です(1トランザクション1集約の原則)。同一トランザクションでの同時更新は原則違反で、注文処理と在庫処理の結合を強めます。集約の統合は「注文の確定」と「在庫の増減」という変更理由の違うものを1つにし、巨大集約化を招きます。在庫を更新しないのは業務要件を満たしません。

</details>

**問3.** 顧客とその全注文履歴を1つの集約にしたところ、注文が増えるにつれ更新が遅くなり、同時更新エラーも頻発するようになりました。原因として最も適切なのはどれでしょう?

1. DBのインデックスが不足している
2. Goのガベージコレクションが遅い
3. リポジトリの実装にバグがある
4. 集約が大きすぎて読み込み・ロックの単位が肥大化し、無関係な変更同士が競合している

<details><summary>答えと解説</summary>

正解: **4**

集約はまるごと読み込み、まるごと一貫性を守る単位なので、大きすぎると「顧客の住所変更」と「注文Aの明細追加」のような無関係な操作まで同じロックを奪い合います。これは境界設計の問題であり、インデックス(DB の検索を速くする索引)やGC(ガベージコレクション: 使わなくなったメモリを自動で片付ける仕組み)、リポジトリ実装をいくら改善しても根本は直りません。「技術で解決する前に境界(モデル)を疑う」のがDDD的な姿勢です。

</details>

**問4.** 「口座残高は一瞬たりともマイナスになってはならない」という銀行口座のルールは、どう守るのが最も適切でしょう?

1. 夜間バッチで残高をチェックし、マイナスがあれば翌日補正する
2. 残高と出金処理を同一集約(口座)のメソッド内で検証し、即時一貫で守る
3. 結果整合性で守れば十分である
4. 画面側の入力チェックで守る

<details><summary>答えと解説</summary>

正解: **2**

「一瞬でも破れると損害が出る」ルールは不変条件として集約の内側に置き、即時一貫で守ります。出金メソッドの中で残高を検証すれば、迂回経路がありません。バッチや結果整合は「破れている時間」を許してしまい、このルールの性質に合いません。画面チェックは補助にはなりますが、API直叩きなどで簡単に迂回されるため防衛線にはなりません。

</details>

**問5.** ある整合性ルールを「即時一貫」で守るか「結果整合」でよいかを判断するとき、最初にすべきことはどれでしょう?

1. 使用中のDBがトランザクションをサポートしているか確認する
2. フレームワークの推奨設定に従う
3. そのルールが一瞬でも破れると業務上の損害が出るのか、少し遅れて整合すれば十分なのかをドメインエキスパートに確認する
4. 他社システムの事例を調べて同じ構成にする

<details><summary>答えと解説</summary>

正解: **3**

即時一貫か結果整合かは技術選定ではなく業務要件の問題なので、ビジネス側(ドメインエキスパート)への確認が先です。これはCISSP等でも共通する「技術の前に要件」という鉄則のDDD版です。DBの機能やフレームワーク設定、他社事例は実現手段の話であり、要件が決まる前に見ても判断を誤ります。

</details>

**問6.** DB のトランザクションの説明として正しいものはどれでしょう？

1. 書き込みを1件ずつ必ず別々に確定させる仕組み
2. 複数の書き込みを「全部成功(コミット)」か「全部取り消し(ロールバック)」のどちらかにまとめる仕組み
3. DB の検索を速くするための索引
4. 書き込みを数分遅らせて、あとでまとめて反映する仕組み

<details><summary>答えと解説</summary>

正解: **2**

トランザクションは、振込の「A から減らす」と「B に増やす」のような複数の書き込みを、全部成功させて確定(コミット)するか、途中で失敗したら全部なかったことにする(ロールバック)か、のどちらかにまとめる仕組みです。1件ずつ別々に確定させると、途中で失敗したときに片方だけ反映される矛盾が起きます。検索を速くする索引はインデックスの説明です。「遅れてあとで整合させる」のは、集約をまたぐときの結果整合性の考え方で、トランザクションそのものの説明ではありません。

</details>

## 3. Goでの集約実装

### 「ルート経由を強制する」実装の型

Goには公開/非公開の2段階しかありません。名前の先頭が**大文字なら公開**(パッケージの外からも使える)、**小文字なら非公開**(同じパッケージの中からしか使えない)です。パッケージは L3 で見た、コードを入れるフォルダ単位のまとまりです。

| 名前 | 公開/非公開 | パッケージ order の外から |
|---|---|---|
| `Order`, `AddItem`, `Items` | 公開 | 使える |
| `items`, `status`, `maxLines`, `newLine` | 非公開 | 使えない(コンパイルエラー) |

これで十分に**変更経路をルートのメソッドに限定**できます。

```go
package order

type Order struct {
    id     OrderID
    items  []OrderLine // 非公開: パッケージ外から直接触れない
    status Status
}

const maxLines = 10

// AddItem が不変条件の番人になる
func (o *Order) AddItem(p ProductID, qty int) error {
    if o.status != StatusDraft {
        return ErrNotEditable
    }
    if len(o.items) >= maxLines {
        return ErrTooManyLines // 「明細は10行まで」
    }
    o.items = append(o.items, newLine(p, qty))
    return nil
}

// 内部スライスは漏らさず、コピーを返す
func (o *Order) Items() []OrderLine {
    out := make([]OrderLine, len(o.items))
    copy(out, o.items)
    return out
}
```

| 部分 | 意味 |
|---|---|
| `package order` | このファイルは order パッケージに属する |
| `items []OrderLine` | 明細のスライス。小文字なので非公開 |
| `const maxLines = 10` | 明細の上限を表す定数(L2) |
| `if o.status != StatusDraft` | 状態が「下書き」でなければ(確定済みなら)変更不可のエラー |
| `if len(o.items) >= maxLines` | すでに10行あれば、11行目は追加させない |
| `o.items = append(o.items, newLine(p, qty))` | 新しい明細を末尾に足したスライスを、items に入れ直す(L1 で見た append) |
| `out := make([]OrderLine, len(o.items))` | `make` は、指定した長さの新しいスライスを作る関数。items と同じ長さの空の入れ物を用意する |
| `copy(out, o.items)` | items の中身を out に写す。out は items とは別の入れ物 |
| `return out` | コピーのほうを返す |

ポイントは3つです。

| 型 | 効果 |
|---|---|
| フィールドを非公開にする | 変更は必ずメソッド経由 → 検証を**コンパイルレベルで**強制 |
| ゲッターはコピーを返す | 返したスライス経由で内部状態を書き換えられるのを防ぐ |
| 生成関数を分ける | `NewOrder`(新規: 採番・初期検証) と `ReconstructOrder`(DBからの復元: 保存済み状態をそのまま戻す) は責務が別 |

なぜコピーが必要なのでしょうか。Go のスライスは、要素そのものではなく「要素が並んでいる置き場所」を指す情報を持った値です。そのため、スライスをそのまま返すと、受け取った側と集約の中が**同じ中身**を指します。受け取った側が要素を書き換えると、集約の中身まで変わってしまうのです。

### 動かして確かめる

上のコードを order パッケージとして置き、パッケージの外(main)から使ってみます。比べるために、わざと内部スライスをそのまま返す `ItemsLeaky` も足しています。フォルダ構成は次のとおりです。

```text
shop/
  go.mod            … モジュール名 shop(go mod init shop で作る)
  main.go           … パッケージの外から使う側
  order/
    order.go        … 集約 Order
    order_test.go   … テストコード
```

`order/order.go`:

```go
package order

import "errors"

type OrderID string
type CustomerID string
type ProductID string
type Status string

const (
    StatusDraft     Status = "下書き"
    StatusConfirmed Status = "確定"
)

var (
    ErrNotEditable  = errors.New("確定済みの注文は変更できません")
    ErrTooManyLines = errors.New("明細は10行までです")
)

type OrderLine struct {
    ProductID ProductID
    Qty       int
}

func newLine(p ProductID, qty int) OrderLine {
    return OrderLine{ProductID: p, Qty: qty}
}

type Order struct {
    id         OrderID
    customerID CustomerID
    items      []OrderLine
    status     Status
}

const maxLines = 10

func NewOrder(c CustomerID) *Order {
    return &Order{id: "o-001", customerID: c, status: StatusDraft}
}

func (o *Order) AddItem(p ProductID, qty int) error {
    if o.status != StatusDraft {
        return ErrNotEditable
    }
    if len(o.items) >= maxLines {
        return ErrTooManyLines
    }
    o.items = append(o.items, newLine(p, qty))
    return nil
}

func (o *Order) Confirm() { o.status = StatusConfirmed }

func (o *Order) Items() []OrderLine {
    out := make([]OrderLine, len(o.items))
    copy(out, o.items)
    return out
}

// ItemsLeaky はわざと悪い書き方: 内部のスライスをそのまま返す
func (o *Order) ItemsLeaky() []OrderLine {
    return o.items
}
```

`main.go`:

```go
package main

import (
    "fmt"
    "shop/order"
)

func main() {
    o := order.NewOrder("c-001")
    if err := o.AddItem("p-001", 2); err != nil {
        fmt.Println("エラー:", err)
        return
    }
    fmt.Println("明細:", o.Items())

    // コピーを書き換えても、注文の中身は変わらない
    copied := o.Items()
    copied[0].Qty = 999
    fmt.Println("コピーを書き換えた後:", o.Items())

    // 内部スライスをそのまま返すと、外から中身を書き換えられてしまう
    leaked := o.ItemsLeaky()
    leaked[0].Qty = 999
    fmt.Println("漏れたスライスを書き換えた後:", o.Items())

    // 確定後は追加できない
    o.Confirm()
    fmt.Println("確定後に追加:", o.AddItem("p-002", 1))

    // o.items = nil // ← パッケージの外からは非公開フィールドに触れない
}
```

`import "shop/order"` で order パッケージを読み込み、`order.NewOrder` のように「パッケージ名.名前」で公開された名前を使います。`copied[0].Qty = 999` は、スライスの0番目(先頭)の明細の数量を 999 に書き換える、という意味です。`shop` フォルダで `go run .` を実行した結果です。

```text
明細: [{p-001 2}]
コピーを書き換えた後: [{p-001 2}]
漏れたスライスを書き換えた後: [{p-001 999}]
確定後に追加: 確定済みの注文は変更できません
```

| 結果の行 | 分かること |
|---|---|
| `明細: [{p-001 2}]` | 商品 p-001 を2個の明細が1行。`{...}` は1つの OrderLine の表示 |
| `コピーを書き換えた後: ...2` | Items() はコピーを返すので、書き換えても集約の中は 2 のまま |
| `漏れたスライスを書き換えた後: ...999` | ItemsLeaky() は中身を共有しているので、AddItem の検証を通らずに数量が 999 に変わってしまった |
| `確定後に追加: ...` | 確定後は AddItem がエラーを返す |

最後のコメント行 `// o.items = nil` の `//` を外すと、コンパイルの段階で止まります。

```text
# shop
./main.go:30:7: o.items undefined (type *order.Order has no field or method items, but does have Items)
```

「`*order.Order` 型には items というフィールドもメソッドもない(Items ならある)」という意味です。パッケージの外からは、非公開の items が存在しないものとして扱われます。

### テストのしやすさは集約の副産物

**テストコード**は、作ったコードが期待どおりに動くかを自動で確かめるためのコードです。Go では `〜_test.go` という名前のファイルに `Test` で始まる関数を書き、`go test` で実行します。不変条件がすべて集約のメソッドに集まっているので、**DBなしの単体テスト**(部品1つだけを取り出して確かめるテスト)でビジネスルールを検証できます。

```go
func TestAddItem_RejectsOver10Lines(t *testing.T) {
    o := NewOrder(testCustomer)
    for i := 0; i < 10; i++ { _ = o.AddItem(p, 1) }
    if err := o.AddItem(p, 1); !errors.Is(err, ErrTooManyLines) {
        t.Fatal("11行目が追加できてしまった")
    }
}
```

| 部分 | 意味 |
|---|---|
| `func TestAddItem_RejectsOver10Lines(t *testing.T)` | テスト関数。`t` はテストの結果を報告するための道具(testing パッケージが渡してくれる) |
| `for i := 0; i < 10; i++ { ... }` | i を 0 から 9 まで1ずつ増やしながら10回繰り返す |
| `_ = o.AddItem(p, 1)` | 明細を1行足す。戻り値のエラーは使わないので `_` で捨てる |
| `errors.Is(err, ErrTooManyLines)` | err が ErrTooManyLines かどうかを調べる |
| `!errors.Is(...)` | ErrTooManyLines **ではない**なら(11行目が通ってしまったなら) |
| `t.Fatal("...")` | テストを失敗としてメッセージを出し、そこで止める |

`order/order_test.go` に、テスト用の値(`testCustomer` と `p`)を足して置きます。

```go
package order

import (
    "errors"
    "testing"
)

var testCustomer CustomerID = "c-001"
var p ProductID = "p-001"

func TestAddItem_RejectsOver10Lines(t *testing.T) {
    o := NewOrder(testCustomer)
    for i := 0; i < 10; i++ {
        _ = o.AddItem(p, 1)
    }
    if err := o.AddItem(p, 1); !errors.Is(err, ErrTooManyLines) {
        t.Fatal("11行目が追加できてしまった")
    }
}
```

`go test -v ./order` の結果です(`-v` は各テストの名前と結果を表示する指定)。

```text
=== RUN   TestAddItem_RejectsOver10Lines
--- PASS: TestAddItem_RejectsOver10Lines (0.00s)
PASS
ok  	shop/order	0.006s
```

PASS は合格です。試しに AddItem から `if len(o.items) >= maxLines { ... }` の3行を消して `go test ./order` を実行すると、次のように失敗します。

```text
--- FAIL: TestAddItem_RejectsOver10Lines (0.00s)
    order_test.go:17: 11行目が追加できてしまった
FAIL
FAIL	shop/order	0.002s
FAIL
```

DB もネットワークも使わず、集約を作ってメソッドを呼ぶだけで「明細は10行まで」というルールを確かめられました(最後の秒数は実行のたびに少し変わります)。

💡 コツ: 「このルールのテストにDBやモック(本物の DB などの代わりに置く、テスト用の偽物の部品)が要る」と感じたら、ルールがアプリケーション層(処理の流れを組み立てる層。L12)やリポジトリ(L11)に漏れているサインです。集約に寄せ直しましょう。

### 確認問題

**問1.** Goで集約のフィールド(itemsスライスなど)をパッケージ非公開にする最大の狙いはどれでしょう?

1. メモリ使用量を削減するため
2. 変更を必ずAddItemなどのメソッド経由にさせ、不変条件の検証をコンパイルレベルで強制するため
3. JSONシリアライズを高速化するため
4. ガベージコレクションを最適化するため

<details><summary>答えと解説</summary>

正解: **2**

非公開フィールドにはパッケージ外から触れないため、状態変更の経路が公開メソッドに限定され、そこに書いた検証が迂回できなくなります。これは規約ではなくコンパイラが守ってくれる防衛線です。メモリ・シリアライズ(データを JSON などの形に変換すること)・GC(使わなくなったメモリの自動片付け)は可視性(公開/非公開)と無関係で、もっともらしい技術用語を並べたひっかけです。

</details>

**問2.** Items() メソッドが内部スライスをコピーせずそのまま返すと、何が起きるでしょう?

1. Goのスライスは安全なので何も問題は起きない
2. コンパイルエラーになる
3. 呼び出し側が返されたスライスの要素を直接書き換えられ、集約の検証を通らずに内部状態が変わってしまう
4. 性能が向上するので推奨される

<details><summary>答えと解説</summary>

正解: **3**

スライスは内部配列への参照なので、そのまま返すと呼び出し側から要素を書き換えられます。フィールドを非公開にした意味が、戻り値経由で台無しになるわけです。コンパイルは普通に通るのがこわいところで、コピーを返す(または読み取り専用のビューを返す)のが定石です。わずかなコピーコストより不変条件の保護を優先します。

</details>

**問3.** 新規作成の NewOrder と、DBからの復元用 ReconstructOrder を分ける理由として最も適切なのはどれでしょう?

1. 新規作成は採番・初期状態の検証・イベント発行などを行い、復元は保存済みの正しい状態をそのまま戻すという具合に、責務が異なるため
2. 関数名が長い方が読みやすいため
3. Goにはオーバーロードがないので、やむを得ず別名にしているだけで設計上の意味はない
4. 復元時は検証を全部省略した方がバグが減るため

<details><summary>答えと解説</summary>

正解: **1**

「業務として新しく生まれる」と「永続化済みの状態を取り戻す」は別のユースケースです。新規作成時だけ行うこと(採番、作成イベントの発行、初期ルールの検証)があるため分けます。Goにオーバーロード(同じ名前で引数の違う関数を複数定義する仕組み)がないのは事実ですが、それは表面的な理由にすぎません。復元でも型の整合は守るので「検証ゼロにするため」でもありません。

</details>

**問4.** 「注文明細は10行まで」という不変条件のチェックを書く場所として最も適切なのはどれでしょう?

1. HTTPハンドラ(コントローラ)
2. リポジトリのSaveメソッドの直前
3. フロントエンドの入力チェック
4. 集約OrderのAddItemメソッドの中

<details><summary>答えと解説</summary>

正解: **4**

不変条件は集約自身が守るのが原則で、AddItemの中に書けばどこから呼ばれても必ず検証されます。ハンドラやフロントのチェックはUX向上の補助にはなりますが、別経路(バッチ、他のユースケース)から迂回されます。リポジトリでの検証は「保存の直前に初めて失敗がわかる」上に、永続化という責務にビジネスルールが混ざってしまいます。

</details>

**問5.** 不変条件を集約のメソッドに集約させた場合、テストはどう変わるでしょう?

1. 集約のテストにはDBが必須になる
2. DBもモックもなしで、集約のメソッドを呼ぶだけでビジネスルールを単体テストできる
3. モックが増えてテストはむしろ難しくなる
4. ビジネスルールのテスト自体が不要になる

<details><summary>答えと解説</summary>

正解: **2**

集約は純粋なオブジェクトなので、生成してメソッドを呼び、結果を検証するだけでルールをテストできます。これが「ドメイン層をインフラから独立させる」ことの実利です。DBやモックが必要に感じるなら、ルールがリポジトリやアプリケーション層に漏れているサインです。もちろんテストが不要になるわけではなく、書きやすくなるのです。

</details>

**問6.** 集約 Order の `Items()` が `make` と `copy` でコピーを作って返します。呼び出し側が `items := o.Items()` で受け取り、`items[0].Qty = 999` と書き換えました。そのあと `o.Items()` で見た1行目の数量はどうなっているでしょう？(元の数量は 2 とします)

1. 2 のまま変わっていない
2. 999 に変わっている
3. 0 にリセットされている
4. コンパイルエラーになり、書き換えられない

<details><summary>答えと解説</summary>

正解: **1**

Items() は make で新しいスライスを作り、copy で中身を写してから返すので、呼び出し側が受け取ったのは集約の中とは別の入れ物です。それを書き換えても集約の中の数量は 2 のままです。999 に変わるのは、内部のスライスをそのまま返した場合(ItemsLeaky のような書き方)です。返されたスライスの要素への代入自体は普通の操作なので、コンパイルエラーにはなりません。

</details>
