# 第6章 エンティティ — 同一性とライフサイクル

DDDの戦術的設計は「エンティティと値オブジェクトの使い分け」から始まります。この章では、同一性 (identity) という考え方を軸に、エンティティの見分け方・IDの設計・振る舞いの持たせ方を、Goのコード例とともに身につけます。

## 1. エンティティとは — 同一性が本質

### 属性が同じでも「別人」、属性が変わっても「同じ人」

**エンティティ (Entity)** とは、**同一性 (identity)** によって区別されるオブジェクトです。氏名・生年月日がまったく同じ2人のユーザーがいても、2人は別人です。逆に、ユーザーが改名したりメールアドレスを変えたりしても、同じユーザーであり続けます。つまりエンティティは「属性の中身」ではなく「どの個体か」で識別され、**属性が変化するライフサイクル**を持ちます。

```go
u1 := User{ID: "u-001", Name: "田中"}
u2 := User{ID: "u-002", Name: "田中"} // 属性は同じでも別人
u1.Rename("佐藤")                      // 名前が変わっても u-001 は同じ人
```

### 値オブジェクトとの対比

| 観点 | エンティティ | 値オブジェクト (Value Object) |
|---|---|---|
| 区別のしかた | 同一性 (ID) | 等価性 (属性がすべて同じなら同じ) |
| 可変性 | 可変 (mutable)・状態が変わる | 不変 (immutable)・変えるなら作り直す |
| ライフサイクル | ある (作成→変更→削除) | ない |
| 例 | ユーザー、注文、口座 | 金額、住所、期間 |

### 見分け方 — 「追跡する必要があるか」

判断基準はシンプルです。**その対象を個体として追跡し続ける必要があるか**。注文は「あの注文がキャンセルされた」と追跡するのでエンティティ。注文に書かれた配送先住所は、中身が同じなら区別する意味がないので値オブジェクトです。

💡 コツ: 同じ「住所」でも文脈で答えが変わります。ECサイトの注文では住所は値ですが、**配送業者のシステム**では「この建物への配達履歴」を追跡するため、住所がエンティティになり得ます。「エンティティか値か」は対象そのものではなく、**そのドメインで何を追跡したいか**で決まる — これがDDDらしい考え方です。

### 確認問題

**問1.** 銀行口座システムで「口座」をエンティティとして扱うべき最大の理由はどれでしょう？

1. 口座はデータベースのテーブルに保存されるから
2. 口座には口座番号という属性があるから
3. 入出金で残高が変わり続けても、同じ口座として追跡する必要があるから
4. 口座は複数の属性を持つ複雑なオブジェクトだから

<details><summary>答えと解説</summary>

正解: **3**

エンティティの本質は「属性が変化しても同一性を保って追跡される」ことです。残高という属性が変わり続けても「同じ口座」であり続ける — これがエンティティの特徴そのものです。「テーブルに保存される」は値オブジェクトでも起こるので根拠になりません。「属性がある」「複雑である」もエンティティかどうかとは無関係で、属性1つの単純なエンティティも、属性が多い値オブジェクトも存在します。ひっかけ: 「DBに保存するか」で判断するのは典型的な誤りです。

</details>

**問2.** エンティティと値オブジェクトの違いの説明として正しいものはどれでしょう？

1. エンティティは同一性 (ID) で比較され、値オブジェクトは属性の等価性で比較される
2. エンティティは不変で、値オブジェクトは可変である
3. エンティティはドメイン層に置き、値オブジェクトはアプリケーション層に置く
4. エンティティは必ず複数の属性を持ち、値オブジェクトは属性を1つしか持てない

<details><summary>答えと解説</summary>

正解: **1**

比較のしかたが両者の決定的な違いです。エンティティはIDが同じなら同じ個体、値オブジェクトは属性がすべて等しければ同じ値とみなします。可変・不変の関係は逆で、エンティティが可変・値オブジェクトが不変です(「エンティティは不変」という記述は逆転のひっかけ)。両者ともドメイン層の構成要素なので層で分かれるという説明も誤り。属性の数にも制約はありません(住所は郵便番号・都道府県など複数属性の値オブジェクトの典型です)。

</details>

**問3.** ECサイトの注文機能を設計しています。注文に記録する「配送先住所」は、一度確定したら書き換えず、同じ内容なら区別する必要もありません。どう扱うのが適切でしょう？

1. 住所テーブルを作り、住所IDで管理するエンティティにする
2. 注文エンティティの文字列フィールドとして持つ
3. ユーザーエンティティの一部として持つ
4. 不変の値オブジェクト Address として注文に持たせる

<details><summary>答えと解説</summary>

正解: **4**

「追跡しない・同じ内容なら同じ」ものは値オブジェクトが適切です。不変なので「注文時点の住所」が後から書き換わる事故も防げます。住所IDで管理するのは、追跡の必要がないのに同一性を導入する過剰設計で、「中身が同じ住所が2レコードある」といった無意味な状態を生みます。単なる文字列では郵便番号の形式検証などのルールを置く場所がなくなります(プリミティブ強迫)。ユーザーの一部にすると、ユーザーが引っ越したら過去の注文の配送先まで変わってしまうバグの温床になります。

</details>

**問4.** ID が異なり、それ以外の属性（氏名・メールアドレスなど）がすべて同じ2つの User オブジェクトがあります。DDDではこの2つをどう扱いますか？

1. 属性がすべて同じなので、同一のエンティティとして扱う
2. ID が異なるので、別々のエンティティとして扱う
3. 等価性の比較を実装してから決める
4. どちらか一方を重複データとして削除しなければならない

<details><summary>答えと解説</summary>

正解: **2**

エンティティの同一性はIDだけで決まります。属性が偶然すべて一致していても、IDが違えば別の個体です(同姓同名の別人)。「属性が同じなら同一」は値オブジェクトの考え方で、エンティティに適用するのは典型的な混同です。等価性の実装で決めるのも値オブジェクトの話です。重複データかどうかはビジネス上の判断(メールアドレスの一意制約など)であって、エンティティの同一性の定義とは別問題です。

</details>

**問5.** 配送業者の業務システムを設計しています。「建物の住所」ごとに配達履歴・不在時のメモ・配達ルートを管理したい場合、住所はどう扱うのが適切でしょう？

1. 住所は常に値オブジェクトと決まっているので、値オブジェクトにする
2. 文字列として配達記録に埋め込む
3. この文脈では追跡対象なので、IDを持つエンティティとして扱う
4. エンティティと値オブジェクトの両方で二重管理する

<details><summary>答えと解説</summary>

正解: **3**

「エンティティか値か」は対象そのものではなく、ドメインで追跡が必要かで決まります。配達履歴やメモを「この建物」に紐づけて蓄積するなら、住所は同一性を持つ追跡対象＝エンティティです。「住所は常に値」という思い込みがこの問題のひっかけで、ECサイトの注文では値でも、配送ドメインではエンティティになり得ます。文字列埋め込みでは履歴を紐づけられません。同じ概念の二重管理は整合性バグの温床になるため、コンテキストごとに1つのモデルを選びます。

</details>

## 2. IDの設計 — 自然キーの罠と型安全なID

### 自然キーの罠

エンティティの同一性を支えるのがID設計です。まず避けたいのが、メールアドレスや社員番号のような**自然キー (natural key)** をそのまま同一性に使うことです。メールアドレスは変更されますし、退会者のアドレスが別人に再利用されることもあります。「同一性が変わる・再利用される」キーは、エンティティの土台として危険です。

そこで実務では **代理キー (surrogate key)** — UUID/ULID や連番 — を使います。

| 方式 | 長所 | 短所 |
|---|---|---|
| DB連番 (auto increment) | 短い・ソート可能 | 保存するまでIDが無い・推測可能 |
| UUID (v4) | どこでも生成可・推測困難 | 長い・時系列ソート不可 |
| ULID | 生成可・時系列ソート可能 | 連番ほど短くはない |

💡 コツ: **IDは生成時に採番**(アプリ側でUUID/ULIDを振る)すると、エンティティが保存前から完全な状態になり、DBなしでテストできます。「保存して初めてIDが決まる」設計は、ドメイン層をDBに依存させる原因です。

### Goでの型安全なID

IDをただの `string` にすると、`UserID` と `OrderID` を取り違えてもコンパイルが通ってしまいます。**専用の型**を定義しましょう。

```go
type UserID string
type OrderID string

func FindOrder(id OrderID) (*Order, error) { ... }

var uid UserID = "u-001"
FindOrder(uid) // コンパイルエラー！ 取り違えを型が防ぐ
```

### 等価性はIDだけで比較

エンティティ同士の比較は、属性ではなくIDだけで行います。

```go
func (u *User) Equals(other *User) bool {
    return other != nil && u.id == other.id
}
```

### 確認問題

**問1.** ユーザーの同一性(主キー)をメールアドレスにする設計があります。DDDの観点で最大の問題はどれでしょう？

1. メールアドレスは文字列なので検索が遅い
2. メールアドレスは変更・再利用され得るため、エンティティの同一性が壊れる
3. メールアドレスには個人情報が含まれるため主キーにできない
4. メールアドレスは値オブジェクトにできないから

<details><summary>答えと解説</summary>

正解: **2**

同一性は「変わらないこと」が生命線です。メール変更のたびに主キーが変わると、注文履歴など全参照の付け替えが必要になり、退会者のアドレス再利用では別人が過去データを引き継ぐ事故も起き得ます。検索速度は実装上の話でありDDDの本質的問題ではありません。個人情報の扱いは重要な考慮点ですが「主キーにできない」理由ではなく、またメールアドレス自体は形式検証を持つ立派な値オブジェクトにできます(属性としては持ってよい。同一性に使うのが問題)。

</details>

**問2.** 「エンティティのIDはDBのauto incrementで採番し、INSERT後に取得する」設計に対して、DDDの観点から最も適切な改善はどれでしょう？

1. INSERTを高速化してIDの取得を早める
2. IDが採番されるまでエンティティの利用を禁止するフラグを持たせる
3. IDをやめて属性の組み合わせで同一性を表現する
4. 生成時にアプリケーション側でUUID/ULIDを採番し、保存前から完全なエンティティにする

<details><summary>答えと解説</summary>

正解: **4**

生成時採番にすると、エンティティは保存前からIDを持つ完全な状態になり、DBなしの単体テストやドメインイベントへのID添付が自然にできます。DB採番のままでは「保存するまで半人前のオブジェクト」が存在し、ドメイン層がDBに依存します。高速化やフラグは問題の先送りで、半人前状態そのものが解消されません。属性の組み合わせは自然キーの罠に戻るだけです。ひっかけ: auto increment が常に悪いわけではありませんが、「ドメイン層の独立」を優先するなら生成時採番が定石です。

</details>

**問3.** Goで `type UserID string` のように専用のID型を定義する最大の利点はどれでしょう？

1. UserID と OrderID の取り違えをコンパイル時に検出できる
2. string よりメモリ使用量が少なくなる
3. データベースへの保存が高速になる
4. IDの値をあとから自由に書き換えられるようになる

<details><summary>答えと解説</summary>

正解: **1**

defined type にすると `FindOrder(userID)` のような取り違えが型エラーになり、テストでは見つけにくい「IDの混線」バグをコンパイラが防いでくれます。これが型安全なIDの核心です。メモリ・速度は string と同じで変わりません(Goの defined type は実行時コストゼロ)。IDの書き換えやすさはむしろ逆で、IDは同一性の土台なので書き換えられない方が望ましい性質です。

</details>

**問4.** 外部に公開するURLに含まれるリソースIDとして、連番ではなくUUIDを選ぶ理由として最も適切なのはどれでしょう？

1. UUIDの方が短くて覚えやすいから
2. UUIDは時系列順に並べ替えられるから
3. 連番は次のIDが推測でき、他人のリソースを列挙される恐れがあるから
4. 連番はデータベースで主キーにできないから

<details><summary>答えと解説</summary>

正解: **3**

連番IDは /orders/1001 の次が 1002 だと推測できるため、認可の不備と組み合わさると他人のデータを列挙する攻撃(IDOR)につながります。UUIDは推測がほぼ不可能で、この露出を減らせます。UUIDは36文字で連番より長く「短くて覚えやすい」は逆です。時系列ソートができるのはULIDの特徴で、UUID(v4)はランダムなのでソートできません。連番は主キーとして最も一般的な方式であり、最後の選択肢は事実に反します。

</details>

**問5.** エンティティ User の Equals メソッドの実装として、DDDの考え方に沿うものはどれでしょう？

1. 氏名とメールアドレスがすべて一致したら true を返す
2. ID が一致したら true を返す
3. ポインタ(参照)が同じオブジェクトを指していたら true を返す
4. ID と全属性の両方が一致したら true を返す

<details><summary>答えと解説</summary>

正解: **2**

エンティティの同一性はIDだけで決まるため、Equals もIDのみで比較します。属性で比較すると「改名した瞬間に別人扱い」になり、エンティティの定義(属性が変わっても同じ個体)と矛盾します。ポインタ比較では、DBから別々に読み込んだ同じユーザー(ID同一)が「別人」と判定されてしまいます。ID と全属性の両方を見る実装は一見厳密ですが、属性変更中の同一エンティティを不一致にしてしまうため誤りです。

</details>

## 3. 振る舞いを持つエンティティ — 貧血モデルからの脱却

### getter/setter だらけの「貧血エンティティ」

フィールドと getter/setter しかないエンティティは、**貧血ドメインモデル (anemic domain model)** と呼ばれます。何が問題なのでしょうか。

```go
// 悪い例: ルールが呼び出し側に散らばる
if order.Status() != StatusShipped { // 呼び出し側がルールを知っている
    order.SetStatus(StatusCancelled)
}
```

キャンセル可否のルールが**呼び出し側に漏れて**います。キャンセルする画面・バッチ・APIが増えるたびに同じ if 文がコピーされ、1か所でも漏れれば「発送済みなのにキャンセルされた」という不整合が起きます。

### ビジネスルールはエンティティのメソッドへ

```go
// 良い例: ルールがエンティティの中にある
func (o *Order) Cancel() error {
    if o.status == StatusShipped {
        return ErrAlreadyShipped // 発送後はキャンセル不可
    }
    o.status = StatusCancelled
    return nil
}
```

呼び出し側は `order.Cancel()` と書くだけ。**「発送後はキャンセル不可」という不変条件 (invariant) を破る手段がそもそも存在しない**のがポイントです。フィールドは非公開にし、状態変更は意図を表すメソッド経由に限定します。

### 常に正しい状態しか存在させない

生成時も同じです。コンストラクタ(Goではファクトリ関数)で検証し、不正なインスタンスを作れなくします。

```go
func NewOrder(userID UserID, items []OrderItem) (*Order, error) {
    if len(items) == 0 {
        return nil, ErrEmptyOrder // 明細ゼロの注文は存在できない
    }
    return &Order{id: NewOrderID(), userID: userID, items: items, status: StatusPending}, nil
}
```

💡 コツ: エンティティが肥大化してきたら、関連する属性とロジックを**値オブジェクトやドメインサービスに抽出**します。「全部エンティティに置く」のではなく「不変条件を守る責務だけを置く」のがバランスです。

### 確認問題

**問1.** 注文のキャンセル処理を「呼び出し側が order.Status() をチェックしてから order.SetStatus(StatusCancelled) を呼ぶ」設計にしました。最大の問題はどれでしょう？

1. キャンセル可否のルールが呼び出し側に散らばり、重複とチェック漏れが起きる
2. Status() の呼び出しが増えて性能が劣化する
3. SetStatus という名前がGoの命名規約に違反している
4. 呼び出し側のコード量がわずかに増える

<details><summary>答えと解説</summary>

正解: **1**

ビジネスルール(発送後はキャンセル不可)がエンティティの外に漏れると、キャンセルを行うすべての箇所に同じ if 文が必要になり、1か所の漏れが「発送済み注文のキャンセル」という不整合を生みます。これが貧血ドメインモデルの本質的な害です。性能劣化やコード量は誤差であり本質ではありません。命名規約の問題でもありません(SetXxx自体はGoで許容される命名です。問題は setter で不変条件を素通りさせる設計の方です)。

</details>

**問2.** 「発送済みの注文はキャンセルできない」というルールは、どこに実装するのが最も適切でしょう？

1. キャンセルボタンを押せなくするフロントエンドのコード
2. 注文キャンセルAPIのハンドラ関数
3. Order エンティティの Cancel() メソッド
4. データベースのトリガー

<details><summary>答えと解説</summary>

正解: **3**

不変条件はエンティティ自身が守るのがDDDの基本です。Cancel() の中にルールを置けば、画面・バッチ・APIなどどこから呼ばれても必ず検証が通り、ルールを破る手段が存在しなくなります。フロントエンドの制御はUX向上には有効ですが、APIを直接叩かれれば素通りします。APIハンドラに置くと別のユースケース(管理画面・バッチ)で漏れます。DBトリガーは最後の防波堤にはなりますが、ビジネスルールがドメインモデルの外に出てしまい、テストも把握も難しくなります。

</details>

**問3.** ファクトリ関数 NewOrder で「明細ゼロの注文はエラーにする」検証を行う狙いとして最も適切なのはどれでしょう？

1. エラーメッセージを統一して国際化しやすくするため
2. 不正な状態の Order インスタンスをそもそも存在させないため
3. データベースの NOT NULL 制約を省略できるようにするため
4. 注文作成の処理速度を向上させるため

<details><summary>答えと解説</summary>

正解: **2**

生成時に検証すれば「Order 型の値が存在する＝正しい状態である」と常に信頼でき、以降のコードから防御的なチェックが消えます。これが「常に正しい状態しか存在させない (always-valid)」という設計方針です。エラーメッセージの統一は副次的な効果にすぎません。DB制約は別レイヤーの防波堤であり、省略してよい理由にはなりません(多層防御として残します)。速度とは無関係です。ひっかけ: 検証を「保存の直前」にまとめる設計は、検証前の不正なインスタンスがドメイン層を漂うことを許してしまいます。

</details>

**問4.** Order エンティティに金額計算ロジック(小計・税・割引の計算メソッドと関連フィールド)が増え続けて肥大化してきました。最も適切なリファクタリングはどれでしょう？

1. Order を継承した PricedOrder サブクラスを作って分割する
2. 計算ロジックをすべてアプリケーション層のサービスに移動する
3. 計算ロジックをユーティリティパッケージの静的関数群に移す
4. 金額まわりの属性とロジックを Money などの値オブジェクトに抽出する

<details><summary>答えと解説</summary>

正解: **4**

関連する属性とロジックのまとまりは値オブジェクトに抽出するのが定石です。Money が加算・税計算を自分で持てば、ロジックはドメイン内に残ったままエンティティが痩せ、Money 単体でテストもできます。アプリケーション層への移動はロジックがドメインの外に漏れて貧血モデル化する方向です。ユーティリティ関数群も同様にデータと振る舞いが分離してしまいます。継承による分割はGoではそもそも継承がなく、他言語でも「種類の違い」ではない肥大化対策としては不適切です。

</details>

**問5.** レビューで「User 構造体の全フィールドが公開(exported)で、呼び出し側が自由に書き換えている」コードを見つけました。DDDの観点で最も適切な指摘はどれでしょう？

1. フィールド名をすべて大文字に統一すべき
2. User を interface にして実装を複数用意すべき
3. フィールドを非公開にし、意図を表すメソッド(Rename 等)経由でのみ状態変更させるべき
4. 構造体をやめて map[string]any で柔軟に持つべき

<details><summary>答えと解説</summary>

正解: **3**

フィールドを非公開にして Rename(newName) のような意図のあるメソッドだけを公開すれば、検証ロジックを必ず通せて、変更の意図もコードに残ります(なぜ名前が変わるのか＝改名という業務イベント)。公開フィールドのままでは不変条件をどこからでも破れます。interface 化は多態が必要な場面の道具で、カプセル化の問題は解決しません。map での保持は型安全すら失う最悪の方向です。最初の選択肢はGoの公開ルール(大文字=公開)を踏まえると逆効果で、全フィールド公開を固定化してしまいます。

</details>
