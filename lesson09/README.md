# 第9章 集約② — 設計ルールと結果整合性

L8 の集約の「作り方」に続き、この章では「境界の引き方」を学びます。Vaughn Vernon(DDD の実践書の著者)の4原則を軸に、巨大集約の分割と、境界を跨ぐルールを結果整合性(一時的なズレを許し、少し後で必ずそろえる方式)で扱う実装パターン(イベント・補償・Saga)まで、実務で最も悩む判断を訓練します。

## 1. 集約設計の4原則 (Vernon)

### この章の前提(L8 の復習)

この章は L8 の集約の続きです。使う言葉を先に確認します。

| 用語 | 意味(L8 で見たもの) | 例 |
|---|---|---|
| **集約 (Aggregate)** | 必ず一緒に変更・保存するオブジェクトのまとまり。外からは代表(集約ルート)のメソッド経由でだけ変更する | 注文(ルート)+注文明細 |
| **不変条件 (invariant)** | 集約がいつも守っていなければならないルール | 「明細は10行まで」「明細の合計 = 注文の合計」 |
| **トランザクション** | DB への複数の変更を「全部成功か、全部取り消しか」にまとめる単位 | 注文と明細を一緒に保存する |

DDD では「**1つのトランザクションで変更するのは1つの集約だけ**」が基本です。この章では、その集約の「境界をどこに引くか」を学びます。

### 集約設計の4原則 (Vaughn Vernon)

『実践ドメイン駆動設計』(DDD の実践書として広く読まれている本)の著者 Vaughn Vernon が整理した、集約設計の実践指針が次の4原則です。

| # | 原則 | 違反したときの症状 |
|---|---|---|
| 1 | **真の不変条件 (true invariant) で境界を引く** | 画面都合・便利さで境界が膨らみ、神集約(何でも抱え込んだ巨大な集約)になる |
| 2 | **集約は小さく設計する** | ロード(DB から読み込んでオブジェクトにすること)が重い、同時更新の競合が頻発する |
| 3 | **他の集約は ID で参照する** | 芋づる式ロード(1つ読むと関係する物が次々に読まれる)、境界外オブジェクトの誤変更 |
| 4 | **境界の外は結果整合性 (eventual consistency) で更新する** | 1トランザクションが複数集約に跨り、ロック(更新中のデータを他の処理が触れないよう押さえること)が衝突する |

「同時更新の競合」は、2つの処理が同じデータをほぼ同時に変更しようとしてぶつかることです。仕組みは次のチャプター(ch02)で実際に動かして確かめます。

### 真の不変条件とは

「真の不変条件」とは、**その瞬間に必ず守られていないとビジネスが壊れるルール**のことです。

| ルール | 真の不変条件か | 理由 |
|---|---|---|
| 注文明細の合計 = 注文合計 | はい | 一瞬でもズレると、請求額が間違う |
| 明細は10行まで | はい | 注文を変更する瞬間に守らないと意味がない |
| 画面で注文と顧客情報を一緒に見たい | いいえ | 表示の都合。データを読むときに組み合わせればよい |
| 顧客の月間購入額は50万円まで | 業務に確認が必要 | 注文と顧客の2つの集約に跨る。数秒のズレが許されるなら、後から確かめる方法もとれる |

最後の行の「後から確かめる方法」とは、たとえば「注文はいったん受け付け、少し後で月間の合計を集計し、上限を超えていたら担当者に知らせる」のような事後チェックです。

### 結果整合性とは

**結果整合性 (eventual consistency)** は、「一時的にズレることを許すが、少し待てば必ず正しい状態にそろう」という整合のさせ方です。反対に、変更した瞬間にすべてがそろっている状態を**即時整合性**(強い整合性)と呼びます。

注文が確定したら在庫を減らす例で、時刻ごとの状態を見てみます。

| 時刻 | 注文 | 在庫(本) | 状態 |
|---|---|---|---|
| 10:00:00.000 | 未確定 | 3 | そろっている |
| 10:00:00.100 | 確定 | 3 | ズレている(注文は確定したのに、在庫はまだ減っていない) |
| 10:00:02.000 | 確定 | 1 | そろった(在庫側が後から2冊減らした) |

注文と在庫は別々のトランザクションで更新するので、途中に「ズレている」時間があります。このズレを業務として許せるかどうかを確かめたうえで、集約を分けます。実装の方法は ch03 で扱います。

### ID参照 vs オブジェクト参照

```go
// ❌ 他の集約をオブジェクトごと抱え込む
type Order struct {
    customer *Customer // 顧客集約を丸ごと参照
}

// ✅ 他の集約は ID で参照する
type Order struct {
    customerID CustomerID // 必要なら ID で取り直す
}
```

| 部分 | 意味 |
|---|---|
| `customer *Customer` | 顧客オブジェクトへのポインタ(L1 で見た `*`)。注文から顧客の中身もメソッドもすべて触れる |
| `customerID CustomerID` | 顧客の ID だけを持つ。`CustomerID` は L6 で見た独自型(中身は文字列) |
| 「必要なら ID で取り直す」 | 顧客の情報が要る場面では、ID を使って顧客集約を別に読み込む(読み込む係はリポジトリ。詳しくは L11) |

オブジェクト参照にすると、注文をロードするたびに顧客も芋づる式にロードされ、さらに `order.customer.AddPoints(...)` のように**注文のトランザクションで顧客集約まで変更できてしまいます**。

### 動かして確かめる

2つの書き方を1つのプログラムにして動かします。

```go
package main

import "fmt"

type CustomerID string

// 顧客集約
type Customer struct {
	id     CustomerID
	points int
}

func (c *Customer) AddPoints(p int) { c.points += p }

// ❌ オブジェクト参照: 注文が顧客そのもの(のポインタ)を持つ
type OrderWithObject struct {
	customer *Customer
	total    int
}

func (o *OrderWithObject) Confirm() {
	o.customer.AddPoints(o.total / 100) // 注文の処理の中で顧客まで書き換わる
}

// ✅ ID 参照: 注文は顧客の ID だけを持つ
type Order struct {
	customerID CustomerID
	total      int
}

func main() {
	tanaka := &Customer{id: "c-001", points: 0}

	o1 := &OrderWithObject{customer: tanaka, total: 5000}
	o1.Confirm()
	fmt.Println("オブジェクト参照: 顧客のポイント =", tanaka.points)

	o2 := Order{customerID: "c-001", total: 5000}
	fmt.Println("ID 参照: 注文が持っているのは", o2.customerID)
}
```

実行結果:

```text
オブジェクト参照: 顧客のポイント = 50
ID 参照: 注文が持っているのは c-001
```

| 行 | 何が起きたか |
|---|---|
| `tanaka := &Customer{...}` | ポイント0の顧客を作る |
| `o1.Confirm()` | 注文を確定しただけなのに、`o.customer.AddPoints(5000 / 100)` が走り、顧客のポイントが50になった(`/` は整数どうしの割り算なので 5000 / 100 = 50) |
| `o2 := Order{customerID: "c-001", ...}` | ID 参照の注文が持っているのは `c-001` という文字列だけ |

ID 参照の注文から顧客を変更しようとして `o2.customerID.AddPoints(50)` と書くと、プログラムを動かす前の段階でエラーになります。

```text
# ex
./main.go:12:16: o2.customerID.AddPoints undefined (type CustomerID has no field or method AddPoints)
```

1行目の `# ex` は検査したプログラム(モジュール)の名前、`./main.go:12:16` はエラーの場所(main.go の12行目16文字目)です。本文は「`CustomerID` 型には `AddPoints` というフィールドもメソッドもない」という意味です。Go はプログラムを動かす前にコンパイル(コードを実行できる形に変換し、型の誤りを検査する処理)を行います。ID 参照にすると、顧客を誤って変更するコードはこの段階で弾かれます。これが「ID 参照は誤変更を**コンパイルレベルで**防ぐ」の意味です。

### 表示のために集約をまとめる必要はない

「画面で注文と顧客を一緒に見たい」ときは、集約を通さずに、表示用の読み取りクエリ(DB からデータを読み出す問い合わせ)で複数のテーブルを結合 (JOIN: 2つ以上のテーブルを、ID が一致する行どうしで突き合わせて1つの表にすること) して読めば足ります。集約が守るのは「書き込むときのルール」で、読むだけの処理はそのルールに関わらないからです(読み取りと書き込みを分ける考え方は L14 の CQRS で詳しく扱います)。

💡 コツ: 集約設計で迷ったら「このルールが一瞬でも破れたら、ビジネス上の損害が出るか？」と自問しましょう。答えが No なら、それは境界を広げる理由ではありません。

### 確認問題

**問1.** ECサイトの注文集約の設計レビューで「画面で一緒に表示するから、顧客のポイント残高も注文集約に含めよう」という提案が出ました。4原則に照らして最も適切な判断はどれでしょう？

1. 表示要件も立派な理由なので、ポイント残高を注文集約の属性として持たせる
2. 将来ルールが増えるかもしれないので、顧客集約を丸ごと注文の内部に取り込む
3. ポイント残高は注文の不変条件に関わらないため別集約のままとし、IDで参照する。表示はクエリ側で結合する
4. ポイント残高のコピーを注文に持たせ、変更のたびに両方を同期更新する

<details><summary>答えと解説</summary>

正解: **3**

集約の境界は「真の不変条件」で引きます(原則1)。ポイント残高は注文確定の瞬間に守るべきルールに関与しないので、別集約+ID参照が正解です。画面表示の都合は読み取り用クエリで解決でき、集約をまとめる理由になりません。丸ごと取り込む案は巨大集約への道、コピーの同期更新は複数集約の同時更新(原則4違反)で競合と不整合の温床です。ひっかけ: 「画面で一緒に見たい」は集約設計で最も多い誘惑ですが、表示と一貫性の問題は別物です。

</details>

**問2.** 「他の集約はIDで参照する」(原則3)の最も重要な理由はどれでしょう？

1. 芋づる式のロードを防ぎ、他集約を自分のトランザクションで誤って変更することも防げるため
2. JSONへのシリアライズが簡単になるため
3. 外部キー制約をデータベースに張りやすくなるため
4. メモリ使用量が数バイト減るため

<details><summary>答えと解説</summary>

正解: **1**

ID参照の本質は境界の防衛です。オブジェクト参照だと注文のロードで顧客まで読み込まれ(性能劣化)、さらに order.customer.ChangeEmail() のように注文のトランザクション内で他集約を変更できてしまいます(原則4違反)。シリアライズや外部キーは副次的な話で、メモリ削減が目的ではありません。ひっかけ: 「性能のため」だけと覚えると、誤変更の防止という設計上の核心を見落とします。

</details>

**問3.** コードレビューで次の実装が見つかりました。

```go
func (o *Order) Confirm() {
    o.status = Confirmed
    o.customer.AddPoints(o.total / 100) // 顧客集約を直接更新
}
```

この設計の最大の問題はどれでしょう？

1. ポイント計算式がハードコードされていること
2. メソッド名が英語であること
3. AddPointsの戻り値を無視していること
4. 1つのトランザクションで注文と顧客の2つの集約を変更しており、ロック競合と不整合の温床になること

<details><summary>答えと解説</summary>

正解: **4**

注文確定と同時に顧客集約を直接変更するのは原則3・4の違反です。注文と顧客が同じトランザクションでロックされ、競合が増え、片方だけ成功する中途半端な状態も生まれやすくなります。正しくは OrderConfirmed イベントを発行し、ポイント付与は別トランザクションで結果整合的に行います。計算式のハードコードや戻り値の扱いは改善点ではありますが、設計の構造問題に比べれば軽微です。

</details>

**問4.** 「注文明細の合計金額は注文の合計金額と常に一致する」「顧客の月間購入額は上限50万円を超えない」という2つのルールがあります。集約設計として最も適切なのはどれでしょう？

1. どちらも重要なルールなので、注文と顧客を1つの集約にまとめて両方を即時に守る
2. 前者は注文集約内の真の不変条件として守り、後者は集約を跨ぐため結果整合性(イベント+事後チェック)などで扱えないかビジネスに確認する
3. どちらもアプリケーションサービスのif文でチェックすれば集約は不要
4. 後者を優先し、顧客集約の中に全注文を持たせる

<details><summary>答えと解説</summary>

正解: **2**

「明細合計=注文合計」は1つの注文の中で完結する真の不変条件なので、注文集約が守ります。「月間購入額上限」は複数の注文に跨るルールなので、注文集約の境界内では守れません。こうしたルールは「確定時にチェックして超えそうなら警告でよいか」「数秒の遅延は許せるか」をドメインエキスパートに確認し、結果整合性で扱うのが定石です。注文と顧客の統合は巨大集約(原則2違反)、if文だけの案はルールがコードに散在する貧血設計への後退です。

</details>

**問5.** 集約を「小さく設計する」(原則2)ことで得られる最大の利点はどれでしょう？

1. データベースのテーブル数が減る
2. クラス図が1枚に収まり資料が作りやすくなる
3. 同時更新の競合が減り、ロードも軽くなり、単体でのテストもしやすくなる
4. リポジトリの実装が不要になる

<details><summary>答えと解説</summary>

正解: **3**

集約はトランザクションとロックの単位です。小さければ同じ集約を同時に触る確率が下がり(競合減)、ロードするオブジェクトも少なく(性能)、不変条件のテストも集約単体で完結します(テスト容易性)。テーブル数や資料の話は無関係で、リポジトリは集約の大小に関わらず集約ルートごとに用意します。ひっかけ: 「小さく」はクラスを細かく刻むことではなく、不変条件を守るのに必要十分な範囲まで絞ることです。

</details>

**問6.** 結果整合性 (eventual consistency) の説明として正しいものはどれでしょう？

1. 変更した瞬間に、関係するすべての集約が必ず同じ状態になっていること
2. 関係する集約をすべて1つのトランザクションにまとめて更新すること
3. 一時的なズレは放置し、そろえる処理は特に用意しないこと
4. 一時的にズレることを許すが、少し後で必ず正しい状態にそろうように作ること

<details><summary>答えと解説</summary>

正解: **4**

結果整合性は「途中に短いズレの時間があるが、最終的には必ずそろう」整合のさせ方です。例: 注文確定の直後は在庫がまだ減っていないが、2秒後に在庫側が引き当てて正しい数になる。変更の瞬間にすべてそろっているのは即時整合性(強い整合性)の説明で、それを実現する手段が「1つのトランザクションにまとめる」ことです。ズレを放置するのは結果整合性ではなく、ただの不整合です。そろえる仕組み(イベントとリトライなど)を用意して初めて結果整合性になります。

</details>

## 2. 巨大集約の害とリファクタリング

### 巨大集約の症状

集約が肥大化すると、コードは動いていても運用に症状が出ます。

- **楽観ロックの競合エラーが頻発する** — 別々の目的の更新(住所変更とポイント付与)が同じ集約を取り合う
- **ロードが遅い** — 1件の更新のために数千の子オブジェクトを読み込む
- **テストが大がかりになる** — 1つのルールを検証するのに巨大なオブジェクトツリーの組み立てが必要

典型例が「顧客」集約の肥大化です。顧客が注文履歴・ポイント・住所録・問い合わせ履歴をすべて抱えると、ポイント付与と住所変更が同じ行のバージョン番号を取り合い、互いに失敗させ合います。「バージョン番号を取り合う」の意味を、次の楽観ロックで確かめます。

### 楽観ロック (optimistic locking)

**楽観ロック**は、同時更新の競合を見つける方式の1つです。集約の行にバージョン番号(更新のたびに1増える数字)を持たせ、更新時に「読んだときのバージョン」と一致するかを確認します。一致しなければ、自分が読んだ後に誰かが先に更新したということなので、その更新は失敗させます。

「ぶつかることはめったにない」と楽観的に考え、普段は何も押さえずに読み書きするので「楽観」と呼びます。反対に、更新する前に行を押さえて(ロックして)他の処理を待たせる方式を**悲観ロック**と呼びます。

```sql
UPDATE orders SET status = 'shipped', version = version + 1
 WHERE id = ? AND version = ?
-- 0行更新なら競合
```

| 部分 | 意味 |
|---|---|
| `UPDATE orders SET ...` | orders テーブルの行を書き換える SQL(DB に命令する言語) |
| `version = version + 1` | 書き換えと同時に、バージョン番号を1つ上げる |
| `WHERE id = ? AND version = ?` | 「この ID で、かつバージョンが読んだときの値のままの行」だけを対象にする。`?` には実行時に値が入る(1つ目に ID、2つ目に読んだときのバージョン) |
| 0行更新 | 条件に合う行がなかった = 誰かが先にバージョンを上げていた = 競合 |

### 動かして確かめる(Python + SQLite)

Python に標準で付いている SQLite(ファイルやメモリ上で動く小さな DB)で、ポイント付与(A)と住所変更(B)が同じ顧客の行を取り合う様子を再現します。

```python
import sqlite3

db = sqlite3.connect(":memory:")  # メモリ上に使い捨ての DB を作る
db.execute("CREATE TABLE customers (id TEXT, points INTEGER, address TEXT, version INTEGER)")
db.execute("INSERT INTO customers VALUES ('c-001', 100, '東京都', 1)")

# A(ポイント付与)と B(住所変更)が、ほぼ同時に同じ行を読んだ。どちらも version は 1
version_a = 1
version_b = 1

# A が先に更新する。version が 1 のときだけ更新し、version を 2 に上げる
cur = db.execute(
    "UPDATE customers SET points = points + 50, version = version + 1"
    " WHERE id = ? AND version = ?",
    ("c-001", version_a),
)
print("A の更新行数:", cur.rowcount)

# B も「version は 1 のはず」と思って更新する
cur = db.execute(
    "UPDATE customers SET address = '大阪府', version = version + 1"
    " WHERE id = ? AND version = ?",
    ("c-001", version_b),
)
print("B の更新行数:", cur.rowcount)

print(db.execute("SELECT * FROM customers").fetchone())
```

実行結果:

```text
A の更新行数: 1
B の更新行数: 0
('c-001', 150, '東京都', 2)
```

| 時点 | 行の中身 (points, address, version) | 出来事 |
|---|---|---|
| 最初 | 100, 東京都, 1 | A も B も version=1 を読む |
| A の UPDATE 後 | 150, 東京都, 2 | 条件 `version = 1` に合ったので1行更新。version が2に上がる |
| B の UPDATE | 変化なし | 条件 `version = 1` に合う行がもうないので0行。B は競合として失敗 |

`cur.rowcount` は「実際に更新された行数」です。B は失敗したので、行を読み直してやり直す(リトライ)か、利用者に「もう一度お試しください」と返すことになります。ポイント付与と住所変更は本来まったく関係のない変更なのに、同じ行(同じ集約)にいるせいで互いを失敗させています。

競合が頻発するなら、それは**無関係な更新が1つの集約に同居しているサイン**です。

### 分割の手順

1. **不変条件の棚卸し** — この集約が守っているルールをすべて書き出す
2. **即時一貫が本当に必要なペアだけ残す** — 「一瞬でも破れたら損害が出るか」をビジネスに確認
3. **残りは別集約に切り出し、ID で参照する** — 跨ぐルールは結果整合性(ch01)へ

| 元の「顧客」集約 | 分割後 |
|---|---|
| 基本情報・ログイン情報 | 顧客集約 |
| 注文履歴 | 注文集約(顧客IDで参照) |
| ポイント残高 | ポイント口座集約 |
| 住所録 | 住所録集約 |

分割後は、ポイント付与は「ポイント口座」の行、住所変更は「住所録」の行を更新します。別々の行なので、それぞれのバージョン番号も別々になり、上の実験のような取り合いは起きません。

### この章の問題に出てくる用語

| 用語 | 意味 |
|---|---|
| バッチ | 多くのデータをまとめて一括で処理するプログラム。例: 毎晩全会員にポイントを付与する |
| 正規化 | データの重複をなくすように、テーブルを分けて設計すること |
| マイクロサービス | システムを小さなサービスに分け、それぞれを別のプログラムとして動かす構成 |
| ビュー | SELECT 文(読み出しの SQL)に名前を付けて、テーブルのように読めるようにした DB の機能 |

💡 コツ: 「画面でまとめて表示したい」は分割をためらう理由になりません。表示は読み取り専用クエリで複数集約を自由に JOIN すればよく、書き込みの一貫性境界(集約)とは独立に設計できます。

### 確認問題

**問1.** 運用中のシステムで「ポイント付与のバッチと会員情報の変更が同時に走ると、楽観ロックの競合エラーが大量に出る」という障害報告が続いています。根本原因として最も疑うべきものはどれでしょう？

1. データベースのインデックス不足
2. バッチの実行時刻が深夜でないこと
3. ポイントと会員情報という無関係な関心事が1つの巨大集約に同居しており、同じバージョン番号を取り合っていること
4. 楽観ロックではなく悲観ロックを使っていないこと

<details><summary>答えと解説</summary>

正解: **3**

無関係な更新同士が競合するのは、集約境界が広すぎる典型症状です。ポイント残高を独立した集約に切り出せば、会員情報の変更とは別の行・別のバージョン番号になり、競合は構造的に消えます。悲観ロックへの変更は競合をエラーから待ち行列に変えるだけで、根本原因(境界の誤り)は残ります。インデックスや実行時刻は性能・運用の話であり、この競合の原因ではありません。

</details>

**問2.** 巨大集約を分割するとき、最初に行うべき作業はどれでしょう？

1. この集約が守っている不変条件をすべて棚卸しし、本当に即時一貫が必要なルールを特定する
2. テーブルを正規化してから集約をテーブルに合わせる
3. いちばん行数の多い子エンティティから機械的に切り出す
4. マイクロサービスに分割してネットワーク境界を作る

<details><summary>答えと解説</summary>

正解: **1**

集約の境界は不変条件で決まるので、分割もルールの棚卸しから始めます。「どのルールが一瞬でも破れてはいけないか」が分かれば、残すペアと切り出すものが自動的に決まります。テーブル構造やデータ量から機械的に切ると、守るべきルールが集約の外に出てしまう事故が起きます。マイクロサービス化は物理分割であり、論理境界が定まる前にやると境界の誤りをネットワーク越しに固定化してしまいます。

</details>

**問3.** 「注文詳細画面で配送状況と顧客のメモも一緒に表示したい」という要望に対し、DDD的に最も適切な対応はどれでしょう？

1. 表示に必要なので配送と顧客メモを注文集約に取り込む
2. 画面の要望は集約設計に影響させず、読み取り用のクエリ(またはビュー)で複数集約のデータを結合して返す
3. 注文・配送・顧客を1つのトランザクションで同時更新するAPIを作る
4. 画面側で3回APIを呼ぶことを禁止し、集約の統合を検討する

<details><summary>答えと解説</summary>

正解: **2**

集約は「書き込み時の一貫性境界」であり、表示要件は読み取りの問題です。読み取りは集約境界に縛られず、専用クエリで自由にJOINして構いません(CQRSの考え方の入口です)。表示のために集約を広げると、無関係な更新の競合という書き込み側の問題を新たに生みます。同時更新APIは原則4違反、API呼び出し回数は最適化の話であって集約統合の理由にはなりません。

</details>

**問4.** 楽観ロックの仕組みの説明として正しいものはどれでしょう？

1. 更新前に行ロックを取得し、他のトランザクションを待たせる
2. テーブル全体をロックして整合性を保証する
3. リトライを一切行わず、競合したら必ずユーザーにエラーを返す仕様のこと
4. 集約にバージョン番号を持たせ、更新時に読んだときのバージョンと一致する場合だけ更新を成功させる

<details><summary>答えと解説</summary>

正解: **4**

楽観ロックは「競合は稀」という前提で、読み込み時のバージョン番号を UPDATE の条件に含め、0行更新なら競合として検出する方式です。行ロックで待たせるのは悲観ロック、テーブルロックは論外に粒度が粗い方式です。競合検出後にリトライするかエラーを返すかはアプリケーションの設計判断であり、楽観ロック自体の定義には含まれません。集約1つ=バージョン1つが対応するため、競合の頻度は集約境界の妥当性を映す鏡になります。

</details>

**問5.** 「顧客」集約が基本情報・注文履歴・ポイント残高・住所録を抱えています。分割後の設計として最も適切なのはどれでしょう？

1. 顧客・注文・ポイント口座・住所録をそれぞれ独立した集約にし、互いに顧客IDなどのIDで参照する
2. 顧客と注文だけ分け、ポイントと住所録は顧客に残す(変更頻度が低いため)
3. すべてを値オブジェクトに変換して不変にする
4. 注文履歴だけ別DBに移し、残りは現状維持する

<details><summary>答えと解説</summary>

正解: **1**

注文・ポイント・住所録はそれぞれ独立したライフサイクルと更新頻度を持ち、顧客の基本情報との間に即時一貫が必要な不変条件はありません。したがって全部を独立集約+ID参照にするのが4原則に沿った設計です。「変更頻度が低いから残す」は一見合理的ですが、境界の根拠が不変条件でなく頻度になっており、ルールが増えた時に再び肥大化します。全部値オブジェクト化は同一性(ID)と履歴を失い、DB移設は物理配置の話で論理境界の問題を解決しません。

</details>

**問6.** 顧客の行 (version=1) を A と B が同時に読みました。A が `UPDATE ... SET version = version + 1 WHERE id = 'c-001' AND version = 1` で先に更新したあと、B が同じ条件 `AND version = 1` で UPDATE しました。B の更新行数と、その意味として正しいものはどれでしょう？

1. 1行。B の変更も問題なく反映される
2. 0行。A の更新で version が2になったため条件に合わず、B は競合として扱われる
3. 2行。A と B の変更が両方とも同じ行に書き込まれる
4. SQL の文法エラーになり、DB が停止する

<details><summary>答えと解説</summary>

正解: **2**

A の UPDATE で version は 1 から 2 に上がりました。B の WHERE 句は「version = 1 の行」を探すので、該当する行がなく更新行数は0になります。この0行こそが楽観ロックの「競合を見つけた」合図で、B は読み直してやり直すか、利用者にエラーを返します。B の変更がそのまま反映されると A の変更を上書きしてしまう恐れがあり、それを防ぐのが楽観ロックの目的です。SQL としては正しい文なので文法エラーにはなりません。

</details>

## 3. 結果整合性の実装 — イベント・補償・Saga

### 境界を跨ぐルールは結果整合性で

「注文が確定したら在庫を引き当てる(注文分の在庫を確保して減らす)」— 注文と在庫は別々の集約(しばしば別コンテキスト。境界づけられたコンテキストは L3 で見ました)なので、1つのトランザクションでは更新しません。**ドメインイベント (domain event)** を使った結果整合性 (eventual consistency、ch01) で連携します。

ドメインイベントは「ドメインで起きた出来事」を表すデータです。たとえば `OrderConfirmed` は「注文が確定した」という出来事を表します(詳しくは L10)。

```go
// 注文集約: 自分のことだけ行い、起きた事実を発行する
func (o *Order) Confirm() OrderConfirmed {
    o.status = Confirmed
    return OrderConfirmed{OrderID: o.id, Items: o.items.Snapshot()}
}
```

| 行 | 意味 |
|---|---|
| `func (o *Order) Confirm() OrderConfirmed` | 注文のメソッド。戻り値はエラーではなく `OrderConfirmed` イベント |
| `o.status = Confirmed` | 自分(注文)の状態だけを「確定」に変える。在庫には触らない |
| `return OrderConfirmed{OrderID: o.id, Items: ...}` | 「どの注文が・何を」確定したかを詰めたイベントを作って返す |
| `o.items.Snapshot()` | 明細のコピーを作る自作メソッド(この例では定義を省略)。イベントを受け取った側が注文の中身を書き換えられないよう、コピーを渡す |

```text
注文Tx: 注文を確定保存 + イベント保存(同一Tx)
  ↓ 非同期
在庫Tx: OrderConfirmed を購読 → 在庫を引き当て
```

Tx はトランザクションの略です。**非同期**は「相手の処理が終わるのを待たずに先へ進む」こと、**購読**は「このイベントが来たらこの処理を動かす」と登録しておくことです。注文側はイベントを保存したらすぐ処理を終え、在庫側は少し後でそのイベントを受け取って動きます。

### 動かして確かめる

本物の仕組みではイベントは DB やメッセージブローカ(L10 ch03)を通って届きますが、ここではスライス(L3 で見た `[]T`)を「待ち行列」に見立てて流れだけを再現します。在庫3冊の本に、2冊と5冊の注文が来た場合です。

```go
package main

import (
	"errors"
	"fmt"
)

type Line struct {
	ProductID string
	Qty       int
}

// ドメインイベント: 「注文が確定した」という事実
type OrderConfirmed struct {
	OrderID string
	Items   []Line
}

// 注文集約
type Order struct {
	id     string
	status string
	items  []Line
}

func (o *Order) Confirm() OrderConfirmed {
	o.status = "確定"
	snapshot := make([]Line, len(o.items)) // 明細のコピーを作る
	copy(snapshot, o.items)
	return OrderConfirmed{OrderID: o.id, Items: snapshot}
}

// 在庫集約(本来は別コンテキスト)
type Inventory struct {
	stock map[string]int
}

func (inv *Inventory) Reserve(e OrderConfirmed) error {
	for _, l := range e.Items {
		if inv.stock[l.ProductID] < l.Qty {
			return errors.New("在庫不足: " + l.ProductID)
		}
	}
	for _, l := range e.Items {
		inv.stock[l.ProductID] -= l.Qty
	}
	return nil
}

func main() {
	inv := &Inventory{stock: map[string]int{"book": 3}}
	var queue []OrderConfirmed // イベントの待ち行列

	// 注文Tx: 注文を確定し、イベントを待ち行列に入れるところまで
	o1 := &Order{id: "o-001", items: []Line{{"book", 2}}}
	queue = append(queue, o1.Confirm())
	o2 := &Order{id: "o-002", items: []Line{{"book", 5}}}
	queue = append(queue, o2.Confirm())
	fmt.Println("注文Tx 直後:", o1.id, o1.status, "/", o2.id, o2.status, "/ 在庫 book =", inv.stock["book"])

	// 在庫Tx: 少し後で、待ち行列のイベントを1件ずつ処理する
	orders := map[string]*Order{"o-001": o1, "o-002": o2}
	for _, e := range queue {
		if err := inv.Reserve(e); err != nil {
			fmt.Println(e.OrderID, "の引き当て失敗:", err)
			orders[e.OrderID].status = "在庫待ち" // 補償アクション
			continue
		}
		fmt.Println(e.OrderID, "の引き当て成功: 在庫 book =", inv.stock["book"])
	}
	fmt.Println("最終:", o1.id, o1.status, "/", o2.id, o2.status)
}
```

実行結果:

```text
注文Tx 直後: o-001 確定 / o-002 確定 / 在庫 book = 3
o-001 の引き当て成功: 在庫 book = 1
o-002 の引き当て失敗: 在庫不足: book
最終: o-001 確定 / o-002 在庫待ち
```

| 段階 | 出来事 |
|---|---|
| 注文Tx 直後 | 2件とも「確定」。在庫はまだ3冊のまま(結果整合性のズレの時間) |
| o-001 の処理 | 在庫3冊 ≥ 2冊なので成功。在庫は1冊に |
| o-002 の処理 | 在庫1冊 < 5冊なので失敗。注文を「在庫待ち」に変える(下の補償アクション) |

`for _, e := range queue` は「待ち行列のイベントを先頭から1つずつ `e` に入れて繰り返す」という意味です。`continue` は「この回の残りを飛ばして次の回へ進む」です。この例では簡単のため main の中で注文の状態を直接書き換えていますが、実際には在庫側が「在庫不足」イベントを発行し、注文側がそれを受けて自分のメソッドで状態を変えます。

### 失敗したらどうするか

非同期更新は失敗がつきものです。対応は2段構えです。

- **リトライ** — 一時的な失敗(DB瞬断など)は再試行で解決。イベント処理は冪等 (idempotent: 同じイベントを2回処理しても結果が変わらないこと。詳しくは L10 ch03) に作る
- **補償アクション (compensating action)** — 在庫不足など業務的な失敗は、打ち消す業務行為で対応(注文を「在庫待ち」に変更、顧客へ通知)

複数ステップの業務フロー(注文→在庫→決済→配送)全体の進行と失敗時の巻き戻しを調整する役が **Saga / プロセスマネージャ**です。各ステップは独立したトランザクションで、失敗時は補償アクションを逆順に実行します。

| ステップ | 正常時の処理 | 失敗時に実行する補償アクション |
|---|---|---|
| 1. 注文 | 注文を確定 | 注文をキャンセル |
| 2. 在庫 | 在庫を引き当て | 引き当てた在庫を戻す |
| 3. 決済 | 代金を請求 | (ここで失敗) |

たとえば 3 の決済が失敗したら、実行済みの 2 → 1 の順に補償アクションを実行します(在庫を戻し、それから注文をキャンセルする)。DB のトランザクションのように「まとめて無かったことにする」のではなく、「打ち消す業務処理をもう一度行う」点が違います。

### この章の問題に出てくる用語

| 用語 | 意味 |
|---|---|
| 分散トランザクション | 複数の DB をまたいで1つのトランザクションにする仕組み。遅く、障害に弱いため、DDD では避けることが多い |
| ロールバック | トランザクションの変更をすべて取り消すこと |
| ACID | DB のトランザクションが保証する4つの性質の頭文字。「全部成功か全部取り消し」などを保証する |
| メッセージブローカー | サービスの間でメッセージ(イベント)を預かって届ける中継ソフト(L10 ch03) |
| ペイロード | イベントやメッセージに載せるデータの本体 |

### 遅延をどこまで許すかはビジネス判断

「在庫引当は注文確定から何秒以内であるべきか」はエンジニアが決める問題ではありません。ドメインエキスパート(業務に詳しい人。L1)に「確定と引当の間に数秒ズレたら何が起きますか？」と聞くのが正しい進め方です。

💡 コツ: 検討の結果「どうしても即時一貫が必要」と分かったら、それは**2つの集約が本当は1つであるサイン**かもしれません。結果整合性の実装を複雑にする前に、集約境界そのものを見直しましょう。

### 確認問題

**問1.** 注文確定時に別コンテキストの在庫を引き当てる必要があります。DDDの原則に沿った実装はどれでしょう？

1. 注文サービスから在庫テーブルを直接UPDATEする
2. 注文と在庫を同一トランザクションで更新できるよう、2つのDBを分散トランザクションで括る
3. 在庫引当が終わるまで注文確定APIの応答を待たせ、どちらかが失敗したら両方ロールバックする実装を自前で作る
4. 注文確定時に OrderConfirmed イベントを発行し、在庫コンテキストがそれを購読して別トランザクションで引き当てる

<details><summary>答えと解説</summary>

正解: **4**

境界を跨ぐ更新はドメインイベント+結果整合性が定石です。注文は自分の確定だけを行い、起きた事実をイベントで知らせ、在庫側が自分のトランザクションで引き当てます。他コンテキストのテーブル直接UPDATEは境界の破壊(モデルも守れない)、分散トランザクションは可用性と性能を犠牲にし結合を強めます。自前の同期待ち+両方ロールバックは分散トランザクションの再発明で、さらに壊れやすい選択です。

</details>

**問2.** 「注文確定から在庫引当まで、どのくらいの遅延なら許容できるか」を決めるべきなのは誰でしょう？

1. インフラチーム(メッセージブローカーの性能で決まるため)
2. ドメインエキスパート(遅延が業務に与える影響を知っているのはビジネス側のため)
3. 開発チームのテックリード(実装難易度を知っているため)
4. DBA(トランザクション設計の専門家のため)

<details><summary>答えと解説</summary>

正解: **2**

結果整合性の許容幅は技術制約ではなくビジネス要件です。「数秒ズレたら二重販売が起きるのか、それとも謝罪メールで済むのか」を知っているのはドメインエキスパートだけです。エンジニアは選択肢とコストを提示する立場で、インフラ性能や実装難易度は「できるか」の話であり「許されるか」の答えにはなりません。ひっかけ: DDDでは技術的に聞こえる判断も、影響がビジネスに及ぶなら必ずビジネスに確認します。

</details>

**問3.** OrderConfirmed イベントを購読した在庫コンテキストで在庫が足りませんでした。最も適切な対応はどれでしょう？

1. 引当できるまで無限にリトライし続ける
2. 在庫テーブルの数量をマイナスにして引き当てたことにする
3. 補償アクションとして「在庫不足」イベントを発行し、注文を在庫待ちに変更する・顧客に通知するなどの業務的な打ち消しを行う
4. 例外を投げて在庫コンテキストのプロセスを停止する

<details><summary>答えと解説</summary>

正解: **3**

在庫不足は一時障害ではなく業務上の事実なので、リトライでは解決しません。結果整合性の世界では、起きてしまった事実を業務的に打ち消す補償アクション(注文の状態変更・入荷待ち登録・顧客通知)で対応します。マイナス在庫はデータで嘘をつく行為で不変条件の放棄、プロセス停止は他の正常な注文まで巻き込みます。ひっかけ: リトライは「DB瞬断」のような一時的失敗にだけ有効で、業務的失敗との区別が設計の分かれ目です。

</details>

**問4.** Saga(プロセスマネージャ)の役割の説明として最も適切なものはどれでしょう？

1. 複数の集約を1つの分散トランザクションに束ねてACIDを保証する
2. 注文→在庫→決済のような複数ステップの業務フローの進行を追跡し、途中で失敗したら実行済みステップの補償アクションを順に実行する
3. ドメインイベントを時系列に全件保存してリプレイ可能にする
4. 読み取り専用のクエリモデルを構築する

<details><summary>答えと解説</summary>

正解: **2**

Sagaは長い業務フローの調整役です。各ステップは独立したローカルトランザクションで実行し、途中失敗時は「決済を取り消す→引当を戻す」のように補償を逆順に走らせて業務的に巻き戻します。ACIDを分散で保証するものではなく(それは2相コミットの発想)、イベントの全件保存はイベントソーシング、クエリモデルはCQRSの説明です。紛らわしい用語が並ぶ領域なので、「Saga=補償つきの進行管理」と覚えましょう。

</details>

**問5.** 結果整合性の設計を検討した結果「注文と在庫は1秒たりともズレが許されない」という結論になりました。このとき最初に疑うべきことはどれでしょう？

1. メッセージブローカーをより高速な製品に替えるべきこと
2. リトライ間隔を短くすべきこと
3. イベントのペイロードが大きすぎること
4. 「即時一貫が必須」という要件が本物なら、2つの集約(境界)の分け方自体が誤っている可能性があること

<details><summary>答えと解説</summary>

正解: **4**

本当に即時一貫が必要なルールは、定義上1つの集約の中で守るべき真の不変条件です。つまり「結果整合性では絶対ダメ」という結論は、境界の引き直し(統合または再設計)を検討するサインです。ブローカーの高速化やリトライ間隔の短縮は遅延を縮めるだけでゼロにはできず、「1秒も許されない」要件には原理的に応えられません。なお、その要件が本物かどうかをドメインエキスパートに再確認するのも大切です(「ズレたら本当に何が起きるか」)。

</details>

**問6.** Saga で「1. 注文確定 → 2. 在庫引当 → 3. 決済」と進め、3 の決済が失敗しました。補償アクションの進め方として最も適切なものはどれでしょう？

1. 実行済みのステップを逆順に打ち消す: 引き当てた在庫を戻し、そのあと注文をキャンセルする
2. 3つのステップをまとめて DB のロールバックで取り消す
3. 決済が成功するまで、在庫と注文はそのままにして永遠にリトライする
4. 注文だけキャンセルし、引き当てた在庫はそのままにする

<details><summary>答えと解説</summary>

正解: **1**

Saga の各ステップは別々のトランザクションですでにコミット済みなので、DB のロールバックでまとめて取り消すことはできません。代わりに、実行済みのステップを打ち消す業務処理(補償アクション)を逆順(2 → 1)に実行します。在庫を戻さずに注文だけキャンセルすると、売れていない在庫が確保されたまま残ります。永遠のリトライは、カード残高不足のような業務的な失敗では解決しないので不適切です。

</details>
