# 第1章 DDDとは何か — なぜ設計は壊れるのか

DDD の個々のパターンに入る前に、「そもそもなぜ設計は壊れるのか」「DDD は何を解決する道具なのか」という土台を固める章です。ここで戦略的設計と戦術的設計の全体地図を頭に入れておくと、以降の章が「地図のどこを歩いているか」を意識しながら学べます。

## 1. ソフトウェアの複雑さと設計の崩壊

### まず言葉をそろえる: ドメインと DDD

**DDD** は **Domain-Driven Design(ドメイン駆動設計)** の略で、ソフトウェアの「設計」(コードをどう分け、何をどこに書くかの決めごと)の考え方の1つです。

**ドメイン (domain)** とは、そのソフトウェアが扱う**業務の領域**のことです。ECサイト(ネット通販)なら「商品を並べる・注文を受ける・在庫を減らす・配送する・送料を決める」といった仕事全体がドメインです。DDD は「この業務の知識を中心に据えてコードを組み立てよう」という考え方です。

| 用語 | 意味 | ECサイトでの例 |
|---|---|---|
| ドメイン | ソフトウェアが扱う業務の領域 | 注文・在庫・配送・会員 |
| ビジネスルール(業務ルール) | 業務上の決まりごと | 「5,000円以上は送料無料」 |
| ビジネスロジック | ビジネスルールを実行するコード | 送料を計算する関数 |

### 2種類の複雑さを区別する

ソフトウェアの複雑さには2種類あります。**本質的な複雑さ (essential complexity)** は、ドメイン(業務領域)そのものが持つ複雑さです。「法人顧客は与信枠(後払いで買える上限額)内なら後払いできるが、初回取引では前払いのみ」のようなビジネスルールは、どんな技術を使っても消えません。一方 **偶有的な複雑さ (accidental complexity)** は、フレームワーク(アプリの骨組みを提供する部品集)や DB(データベース。データを保存・検索する仕組み)、通信など技術側の都合で生まれる複雑さです。

| 種類 | 例 | 減らし方 |
|---|---|---|
| 本質的な複雑さ | 「ゴールド会員は送料無料。ただし離島は除く」 | 消せない。整理して表現する |
| 偶有的な複雑さ | 「この DB は日付を文字列でしか保存できない」 | 道具を替える・ライブラリに任せる |

DDD が立ち向かうのは前者、**本質的な複雑さ**です。偶有的な複雑さはライブラリ(よく使う処理をまとめた部品)やインフラ(サーバーやネットワークなど動かす土台)の進歩で減らせますが、ドメインの複雑さは「正しく整理して表現する」しかありません。

### 設計が壊れたコードの症状

| 症状 | 中身 |
|---|---|
| 変更の波及 | 「送料ルールを1つ足すだけ」で10ファイルに修正が広がる |
| if の増殖 | 同じ判定 `if order.Status == 3 && user.Type == 2` がコピペで散在 |
| DB 都合の侵食 | テーブル(DB の中の表)の構造の都合がビジネスロジックの形を決めてしまう |
| 暗黙知化 | 「ステータス3は出荷済みの意味」をコードが語らず、古参しか知らない |

**暗黙知**とは、文書やコードに書かれず人の頭の中にだけある知識のことです。`order.Status == 3` を見ても「3=出荷済み」とは読み取れないので、知っている人がいなくなると誰も分からなくなります。

### トランザクションスクリプトが破綻する瞬間

「リクエスト(画面やほかのシステムからの処理の依頼)を受けて、SQL(DB を操作する命令文)を並べて、保存する」という、上から順に手続きを書き下す書き方を**トランザクションスクリプト (Transaction Script)** と呼びます。「注文作成」「注文変更」のように、依頼の種類ごとに1本の手続き(関数)を書くスタイルです。名前に「トランザクション」と付きますが、DB のトランザクション機能(L8 で扱います)とは別物です。

処理が単純なうちは最速の書き方ですが、ルールが増えると**同じ業務ルールが複数の手続きに重複**しはじめます。次の Go のコードは、注文作成の API(外部から呼び出せる機能の窓口)と注文変更の API に、同じ検証がコピペされている様子です。

```go
// 注文作成APIにも、注文変更APIにも、同じ検証がコピペされる
if item.Stock < qty || (user.Grade != "gold" && qty > 10) {
    return errors.New("注文できません")
}
```

### Go コードの読み方(基礎)

この講座のコード例は Go 言語で書かれています。1行ずつ読みます。

| 部分 | 意味 |
|---|---|
| `//` | ここから行末まではコメント(人間向けのメモで、実行されない) |
| `if 条件 { ... }` | 条件が成り立つときだけ `{ }` の中を実行する。Python の `if 条件:` と同じ。Go は条件を `( )` で囲まない |
| `item.Stock < qty` | 商品の在庫数 `item.Stock` が注文数 `qty` より少ない。`.` は「〜の中の」(`item` の中の `Stock`) |
| `!=` | 「等しくない」。`user.Grade != "gold"` は「会員ランクがゴールドではない」 |
| `errors.New("注文できません")` | 「注文できません」というメッセージを持つ**エラー**の値を作る。`errors` は Go に最初から付いている部品(パッケージ) |
| `return ...` | 関数の実行をここで終え、値を呼び出し元に返す |

記号 `||` は「または」(Python の `or`)、`&&` は「かつ」(Python の `and`)です。`( )` で囲んだ部分は先にひとまとまりで判定されます。

つまりこの3行は「在庫が足りない、**または**(ゴールド会員ではない**かつ** 11個以上)なら、エラーを返して処理をやめる」という意味です。

Go には Python のような例外(`raise`)を投げる習慣がありません。代わりに、**失敗したらエラーの値を `return` で返し、成功したら `nil`(「何もない」を表す値。Python の `None` に当たる)を返す**のが基本の書き方です。

### 動かして確かめる

検証が2つの手続きにコピペされた状態を、動く形にしたものです。

```go
package main // 実行できるプログラムは package main から始める

import ( // 使う部品(パッケージ)を読み込む
	"errors" // エラーを作る部品
	"fmt"    // 画面に表示する部品
)

// 注文作成の手続き。引数3つを受け取り、error 型の値を返す
func CreateOrder(stock int, grade string, qty int) error {
	if stock < qty || (grade != "gold" && qty > 10) {
		return errors.New("注文できません")
	}
	return nil // 問題なし
}

// 注文変更の手続き(同じ検証のコピペ)
func ChangeOrder(stock int, grade string, qty int) error {
	if stock < qty || (grade != "gold" && qty > 10) {
		return errors.New("注文できません")
	}
	return nil
}

func main() { // プログラムはここから実行される
	fmt.Println(CreateOrder(100, "gold", 20))   // 在庫十分・ゴールド会員
	fmt.Println(CreateOrder(100, "normal", 20)) // 一般会員が11個以上
	fmt.Println(ChangeOrder(5, "gold", 8))      // 在庫が足りない
}
```

`func 名前(引数 型, ...) 戻り値の型 { }` が関数の定義です(Python の `def`)。Go は `stock int` のように「名前 型」の順で書きます。`int` は整数、`string` は文字列、`error` はエラーを表す型です。`fmt.Println` は値を1行に表示します(Python の `print`)。

```text
<nil>
注文できません
注文できません
```

1行目はエラーなし(`nil`)なので `<nil>` と表示され、2行目と3行目はエラーのメッセージが表示されました。

同じことを Python で書くと次のようになります(Python では例外を使うのが普通です)。

```python
def create_order(stock, grade, qty):
    if stock < qty or (grade != "gold" and qty > 10):
        raise ValueError("注文できません")

try:
    create_order(100, "normal", 20)
except ValueError as e:
    print(e)
```

```text
注文できません
```

### コピペの何がまずいのか

ここで「一般会員の上限を10個から5個に変える」という仕様変更が来たとします。`CreateOrder` だけ直して `ChangeOrder` を直し忘れると、「作成では6個を断るのに、変更なら6個に増やせる」という矛盾したシステムになります。手続きが2本ならまだ気づけますが、実際の業務システムでは数十本になります。

**設計の崩壊は、ドメイン知識がコードの構造として表現されず、手続きの中に散らばることから始まる**——これが DDD の出発点の問題意識です。

💡 コツ: 自分のプロジェクトで「この仕様、どこに書いてあるんだっけ?」と grep(ファイルの中から文字列を検索するコマンド)した経験を思い出してください。grep しないと見つからない知識は、すでに散らばりはじめています。

### 確認問題

**問1.** ECサイトで「ゴールド会員は送料無料、ただし沖縄・離島は除く」という仕様があります。この複雑さの性質として最も適切な説明はどれでしょう？

1. フレームワークを変えれば消える偶有的な複雑さである
2. キャッシュを導入すれば緩和できる技術的な複雑さである
3. ドメインが本来持つ本質的な複雑さであり、整理して表現するしかない
4. 複雑さではなく単なる実装バグの一種である

<details><summary>答えと解説</summary>

正解: **3**

送料ルールはビジネスそのものが持つ決まりごとなので、本質的な複雑さ (essential complexity) です。どんな技術スタックに乗せ換えても消えないため、「正しく整理してコードに表現する」ことでしか扱えません。フレームワーク変更やキャッシュで消えるのは技術都合の偶有的な複雑さ (accidental complexity) の方で、ビジネスルールはそれらと無関係に存在し続けます。DDD が主戦場とするのはこの本質的な複雑さです。

</details>

**問2.** 「配送先変更の仕様を1つ直したら、注文作成・注文変更・管理画面の3箇所を別々に修正する必要があった」— この症状の根本原因として最も適切なものはどれでしょう？

1. 同じドメイン知識(ルール)が複数の手続きに重複して散らばっている
2. プログラミング言語の表現力が不足している
3. テストコードが不足している
4. 開発者のタイピング速度が遅い

<details><summary>答えと解説</summary>

正解: **1**

1つのルール変更が複数箇所の修正を要求するのは、そのルールが1箇所にまとまって表現されず、各手続きにコピーされているからです。これがトランザクションスクリプトの典型的な破綻パターンです。テスト不足は「壊れたことに気づけない」問題であって、修正箇所が増える原因ではありません。言語の表現力やタイピング速度は無関係です。ひっかけ: テストを足しても重複は解消されない点に注意しましょう。

</details>

**問3.** トランザクションスクリプトの説明として正しいものはどれでしょう？

1. DBのトランザクション分離レベルを制御する設計パターン
2. どんな規模でも使ってはいけないアンチパターン
3. ドメインモデルを必ず必要とする設計手法
4. リクエストごとに手続きを並べて書くスタイルで、単純な処理では有効だがルールが増えると重複が生じやすい

<details><summary>答えと解説</summary>

正解: **4**

トランザクションスクリプト (Transaction Script) は「1リクエスト=1手続き」で処理を書き下すスタイルです。単純な CRUD では最も読みやすく速い、正当な選択肢である点が重要です(第16章で「使い分け」を扱います)。「絶対に使ってはいけない」は言い過ぎで、DDD 的な設計が常に正解ではありません。DB のトランザクション制御とは名前が似ているだけの別物、という点もひっかけどころです。

</details>

**問4.** 「ステータス3は出荷済みという意味」という知識が、コード上は `status == 3` という比較でしか表現されていません。この状態の問題点として最も適切なものはどれでしょう？

1. 整数比較は文字列比較より遅いため性能が劣化する
2. ドメイン知識が暗黙知になり、コードが業務の意味を語らないため、変更や新人の理解が困難になる
3. マジックナンバーはコンパイルエラーになる
4. DBに数値を保存すること自体が誤りである

<details><summary>答えと解説</summary>

正解: **2**

問題の核心は「コードが業務の意味を表現していない」ことです。`status == 3` を見ても出荷済みの判定だとは読み取れず、知識が人の頭の中(暗黙知)にしかない状態になります。DDD ではこうした知識を `Order.IsShipped()` のような名前のあるコードに昇格させます。性能差は実質なく、マジックナンバーはコンパイルエラーになりません。DB に数値で保存すること自体は問題ではなく、「コード側で意味が失われること」が問題です。

</details>

**問5.** DDDが主に解決しようとする問題として最も適切なものはどれでしょう？

1. サーバーの応答速度を改善すること
2. インフラコストを削減すること
3. 複雑なドメイン知識をコードの構造として表現し、変更に強いソフトウェアを作ること
4. 開発チームの人数を減らすこと

<details><summary>答えと解説</summary>

正解: **3**

DDD (Domain-Driven Design) は、ビジネスの複雑さ=本質的な複雑さを、モデルとしてコードに表現することで変更に強いソフトウェアを作る設計手法です。性能改善・コスト削減・省人化は結果として付いてくることはあっても、直接の目的ではありません。「DDDを入れたら速くなる」という期待は方向違いで、むしろ短期的には書くコード量は増えます。それでも複雑なドメインでは変更コストの低減で元が取れる、という投資判断の話として捉えるのが正確です。

</details>

**問6.** 次の Go の判定で、在庫 `stock` が 100、会員ランク `grade` が "normal"、注文数 `qty` が 20 のとき、どうなるでしょう？

```go
if stock < qty || (grade != "gold" && qty > 10) {
    return errors.New("注文できません")
}
return nil
```

1. 在庫が足りているので nil(エラーなし)を返す
2. ゴールド会員ではなく、かつ 11 個以上なので「注文できません」のエラーを返す
3. grade が "gold" ではないのでコンパイルエラーになる
4. || の左側が偽なので、右側は判定されずに nil を返す

<details><summary>答えと解説</summary>

正解: **2**

`stock < qty` は 100 < 20 で偽ですが、`||`(または)の右側 `(grade != "gold" && qty > 10)` が「normal はゴールドではない」かつ「20 は 10 より大きい」で真になるため、条件全体が真になりエラーを返します。`||` は左が偽なら右も確かめるので、右側が判定されないのは左が真のときだけです。文字列を `!=` で比べるのは正しい書き方で、コンパイルエラーにはなりません。

</details>

## 2. モデル駆動設計 — モデルとコードを一致させる

### ドメインモデルとは「現実の模写」ではない

**モデル**とは、目的に必要な部分だけを取り出して単純化した表現のことです。**ドメインモデル (domain model)** は、業務(ドメイン)の問題を解くために、現実を**選び取って抽象化したもの**(必要な特徴だけ残し、ほかを捨てたもの)です。

地図が良い例です。路線図は距離も地形も無視しますが、「乗り換え」という問題を解くには最適です。同様に、ECサイトの「顧客」モデルに血液型は要りませんが、与信枠は必要かもしれません。**何を捨てるかがモデリング**(モデルを作る作業)です。

| 現実の顧客が持つ情報 | ECサイトの顧客モデルに入れるか | 理由 |
|---|---|---|
| 氏名・配送先住所 | 入れる | 届けるのに必要 |
| 会員ランク(ゴールドなど) | 入れる | 送料ルールが変わる |
| 血液型・身長 | 入れない | 業務のどのルールにも使わない |

### オブジェクト・クラス・メソッド

モデルをコードにするときの部品を確認しておきます。Python でクラスを書いたことがあれば、同じものです。

| 用語 | 意味 | 例 |
|---|---|---|
| クラス | 「データ+そのデータを扱う処理」をひとまとめにした型(設計図) | `Order`(注文) |
| オブジェクト(インスタンス) | クラスから作った1つ1つの実物 | 「注文 No.1001」 |
| フィールド(属性) | オブジェクトが持つデータ | `confirmed`(確定済みか)、`lines`(明細) |
| メソッド | オブジェクトに属する関数。そのオブジェクトのデータを読み書きする | `AddLine`(明細を追加する) |

Go には `class` という言葉がありません。代わりに **struct(構造体。フィールドをまとめた型)** を定義し、そこに**メソッド**をくっつけます。意味は Python のクラスとほぼ同じです。

### モデル駆動設計

**モデル駆動設計 (Model-Driven Design)** は、「分析用のモデル」と「実装用の設計」を分けず、**モデルをそのままコードに表現する**姿勢です。たとえば業務のルール「注文は確定すると明細を変更できない」を、注文のメソッドの中にそのまま書きます。

```go
// モデル: 「注文は確定すると明細を変更できない」
func (o *Order) AddLine(l OrderLine) error {
    if o.confirmed {
        return ErrOrderAlreadyConfirmed // ルールがコードとして読める
    }
    o.lines = append(o.lines, l)
    return nil
}
```

| 部分 | 意味 |
|---|---|
| `func (o *Order) AddLine(...)` | `Order` 型に `AddLine` というメソッドを定義する。`(o *Order)` を**レシーバ**と呼び、メソッドの中では `o` が「この注文自身」を指す(Python の `self`) |
| `*Order` | `*` は**ポインタ**(値そのものではなく、値が置かれた場所を指すもの)。`*Order` で受け取ると、メソッドの中で `o` を書き換えたとき、呼び出し元の注文そのものが変わる |
| `l OrderLine` | 引数 `l` は `OrderLine`(注文明細)型 |
| `error` | 戻り値の型。失敗ならエラー、成功なら `nil` を返す(L1 ch01 で見た形) |
| `if o.confirmed { ... }` | この注文が確定済みなら |
| `return ErrOrderAlreadyConfirmed` | 「確定済み」というエラーを返して終わる。明細は追加しない |
| `o.lines = append(o.lines, l)` | `append` は**スライス**(Go の可変長の並び。Python のリストに近い。詳しくは L3)の末尾に要素を足した結果を返す。それを `o.lines` に入れ直す |
| `return nil` | 成功(エラーなし) |

`if` で条件を確かめ、満たさなければすぐ `return` で抜ける書き方を**ガード節 (guard clause)** と呼びます。「この条件のときは処理させない」という門番をメソッドの入口に置くので、ルールがひと目で読めます。

### 動かして確かめる

断片を動く形にしたものです。`ErrOrderAlreadyConfirmed` や `OrderLine` の定義も足しています。

```go
package main

import (
	"errors"
	"fmt"
)

// エラーの値を1つ作って名前を付けておく(var は変数の宣言)
var ErrOrderAlreadyConfirmed = errors.New("確定済みの注文には明細を追加できません")

// 注文明細: 商品名と数量
type OrderLine struct {
	Product string
	Qty     int
}

// 注文: 確定済みかどうかと、明細の並び
type Order struct {
	confirmed bool        // true / false の値(真偽値)
	lines     []OrderLine // OrderLine の並び(スライス)
}

// モデル: 「注文は確定すると明細を変更できない」
func (o *Order) AddLine(l OrderLine) error {
	if o.confirmed {
		return ErrOrderAlreadyConfirmed // ルールがコードとして読める
	}
	o.lines = append(o.lines, l)
	return nil
}

// 注文を確定する
func (o *Order) Confirm() {
	o.confirmed = true
}

func main() {
	o := &Order{} // 空の注文を作る

	// 確定前なので追加できる
	fmt.Println(o.AddLine(OrderLine{Product: "りんご", Qty: 2}))
	fmt.Println(len(o.lines)) // 明細の数

	o.Confirm() // 確定する

	// 確定後なので断られる
	fmt.Println(o.AddLine(OrderLine{Product: "みかん", Qty: 1}))
	fmt.Println(len(o.lines)) // 明細の数は増えていない
}
```

| 部分 | 意味 |
|---|---|
| `type Order struct { ... }` | `Order` という struct(フィールドの集まり)の型を定義する |
| `o := &Order{}` | `:=` は「新しい変数を作って値を入れる」。`Order{}` は全フィールドが初期値(`false` や空)の注文、`&` はその**場所(ポインタ)を取る**記号。`o` は `*Order` 型になる(`&Order{...}` の書き方は L6 でもう一度見ます) |
| `OrderLine{Product: "りんご", Qty: 2}` | フィールド名を指定して struct の値を作る |
| `o.AddLine(...)` | `o` の `AddLine` メソッドを呼ぶ |
| `len(o.lines)` | スライスの要素数 |

```text
<nil>
1
確定済みの注文には明細を追加できません
1
```

確定前の追加は成功(`<nil>`)し、確定後の追加はエラーになって明細は1件のままです。業務のルールが、メソッドの中のコードとしてそのまま読めます。

Python で同じモデルを書くと次のとおりです。`self` が Go のレシーバ `o` に当たります。

```python
class OrderAlreadyConfirmed(Exception):
    pass

class Order:
    def __init__(self):
        self.confirmed = False
        self.lines = []

    def add_line(self, line):
        if self.confirmed:
            raise OrderAlreadyConfirmed("確定済みの注文には明細を追加できません")
        self.lines.append(line)

    def confirm(self):
        self.confirmed = True

o = Order()
o.add_line(("りんご", 2))
print(len(o.lines))
o.confirm()
try:
    o.add_line(("みかん", 1))
except OrderAlreadyConfirmed as e:
    print(e)
print(len(o.lines))
```

```text
1
確定済みの注文には明細を追加できません
1
```

モデルとコードが一致していれば、仕様変更=モデルの変更=コードの変更が一直線につながります。逆に「設計書上のモデル」(たとえば**クラス図**: クラスとその関係を箱と線で描いた図)と「実際のコード」が乖離すると、どちらも信用できなくなります。

### 知識の噛み砕き (Knowledge Crunching)

良いモデルは、開発者が一人で机上でひねり出すものではなく、**ドメインエキスパート**(業務に詳しい人: 営業、経理、CS(カスタマーサポート) など)との対話を繰り返して「噛み砕いて」得るものです。会話の中で「実は『キャンセル』には返金ありと無しの2種類あるんですよ」といった**隠れた概念**が見つかり、モデルが深まります。

| 用語 | 意味 |
|---|---|
| ドメインエキスパート (domain expert) | 業務知識を持つ人。職種は問わない |
| 知識の噛み砕き (knowledge crunching) | 対話と試行でモデルを練り上げる活動 |
| 深いモデル (deep model) | 表面的な名詞の整理を超え、業務の核心を捉えたモデル |

たとえば上の「キャンセル」の発見をモデルに反映すると、`Cancel()` 1つだったメソッドが `CancelWithRefund()`(返金ありキャンセル)と `CancelWithoutRefund()`(返金なしキャンセル)に分かれ、それぞれに固有のルールを書けるようになります。

この考え方は Eric Evans が2003年の著書『ドメイン駆動設計』(通称**エヴァンス本**)で体系化しました。DDD は新しい流行ではなく、20年以上使われてきた設計の古典です。

💡 コツ: 「モデリング=クラス図を書くこと」ではありません。ドメインエキスパートへの質問を1つ思いつくことも立派なモデリングの一歩です。

### 確認問題

**問1.** ドメインモデルの説明として最も適切なものはどれでしょう？

1. 業務に登場するすべての情報を漏れなく含んだ、現実の完全なコピー
2. 問題解決に必要な側面だけを選び取った、現実の抽象化
3. データベースのテーブル定義と完全に1対1対応する構造
4. UIの画面項目を一覧化したもの

<details><summary>答えと解説</summary>

正解: **2**

モデルは「問題を解くために現実から何を選び、何を捨てるか」を決めた抽象です。路線図が距離を捨てて乗り換え情報を残すように、目的に合わせて取捨選択します。「すべてを含む完全なコピー」を目指すと複雑さをそのまま持ち込むだけでモデルの意味がありません。テーブル定義や画面項目は実装・表示の都合であり、モデルがそれらに従属すると DB 都合・UI 都合の設計侵食が起きます。

</details>

**問2.** ECサイトの開発中、営業担当との会話で「実はキャンセルには返金ありと返金なしの2種類がある」と判明しました。DDDの観点で、この発見を活かす最もよい対応はどれでしょう？

1. 仕様書の備考欄にメモを追加して、コードは cancel_type フラグ(0/1)で済ませる
2. 営業の業務知識なので開発には関係ないと判断する
3. キャンセルは1種類のままにして、返金処理は手動運用でカバーする
4. 「返金キャンセル」「無償キャンセル」という概念をモデルとコードに明示的に導入する

<details><summary>答えと解説</summary>

正解: **4**

これは知識の噛み砕き (knowledge crunching) で隠れた概念が見つかった典型例です。発見した概念はモデルに取り込み、コード上も名前を持った形(型やメソッド)で表現することで、モデルとコードの一致が保たれます。0/1 フラグ+備考メモでは知識が暗黙知に戻り、ch01 で見た「コードが意味を語らない」状態を再生産します。手動運用への逃がしは知識をコードの外に捨てる選択で、業務が増えるほど破綻します。

</details>

**問3.** 「分析チームが作ったクラス図と、実際のコードの構造が大きく乖離している」— モデル駆動設計の観点から、この状態の最大の問題はどれでしょう？

1. モデルもコードも互いを反映していないため、どちらも意思決定の根拠として信用できなくなる
2. クラス図の作画ツールのライセンス費用が無駄になる
3. コードの行数がクラス図の箱の数より多くなる
4. 分析チームの人事評価が下がる

<details><summary>答えと解説</summary>

正解: **1**

モデル駆動設計 (Model-Driven Design) の核心は「モデル=コード」の一致です。乖離すると、仕様を考えるときはモデルを見て、実装を変えるときはコードを見る、という分裂が起き、変更のたびにズレが拡大します。最終的に「ドキュメントは信用できないからコードを読むしかない、でもコードは意味を語らない」という最悪の状態になります。ツール費用や行数は本質ではありません。

</details>

**問4.** DDDにおける「ドメインエキスパート」の説明として正しいものはどれでしょう？

1. ドメイン層のコードを書くシニアエンジニアのこと
2. DDDの資格を持つコンサルタントのこと
3. 業務知識を深く持つ人のことで、営業・経理・CSなど職種は問わない
4. DNSのドメイン設定に詳しいインフラ担当者のこと

<details><summary>答えと解説</summary>

正解: **3**

ドメインエキスパート (domain expert) は「その業務に詳しい人」です。肩書きや部署は関係なく、長年 CS 対応をしてきた担当者が最高のエキスパートであることも珍しくありません。エンジニアやコンサルタントという職種を指す言葉ではない点がひっかけどころです。DNS のドメインとは完全に無関係です。モデルはこの人たちとの対話(知識の噛み砕き)を通じて練り上げます。

</details>

**問5.** 「注文は確定後に明細を変更できない」というルールを Order 型の AddLine メソッド内のガード節として実装しました。このアプローチの利点として最も適切なものはどれでしょう？

1. ガード節はコンパイラの最適化が効きやすく実行速度が上がる
2. ビジネスルールがモデルの振る舞いとしてコードに表現され、仕様変更時にモデルとコードを一直線に変更できる
3. DBの制約を一切書かなくてよくなる
4. UIのバリデーションが不要になる

<details><summary>答えと解説</summary>

正解: **2**

ルールを「どこかの手続きの中の if」ではなく「Order 自身の振る舞い」として書くことで、モデル(注文は確定後変更不可)とコードが一致します。仕様が変われば AddLine を直す、と変更箇所も自明になります。性能向上は無関係です。DB 制約や UI バリデーションは多層防御として依然有用で、「モデルに書いたから他を省略してよい」とはならない点に注意してください(UI の検証はユーザー体験のため、DB 制約は最終防衛線のためにそれぞれ意味があります)。

</details>

**問6.** Go のメソッド定義 `func (o *Order) AddLine(l OrderLine) error` の説明として正しいものはどれでしょう？

1. `o` は引数の1つ目で、呼び出すときに `AddLine(order, line)` と2つ渡す
2. `*Order` は掛け算の記号で、注文の数を掛ける意味である
3. `error` はこのメソッドが必ずエラーを起こすことを表す
4. `Order` 型のメソッドで、`o` はその注文自身を指す。`*` によりメソッド内の変更が呼び出し元の注文そのものに反映される

<details><summary>答えと解説</summary>

正解: **4**

`(o *Order)` はレシーバと呼ばれ、メソッドの中で「この注文自身」を指します(Python の `self`)。`*Order` は Order のポインタ(値の置き場所)で、メソッド内で `o.lines` を書き換えると呼び出し元の注文が変わります。呼び出しは `order.AddLine(line)` の形で、レシーバを引数として渡すわけではありません。戻り値の型 `error` は「失敗したらエラー、成功なら nil を返しうる」という意味で、必ず失敗するわけではありません。

</details>

**問7.** 本文の Order(確定すると明細を追加できない)で、空の注文 `o` に対して「明細を1つ追加 → Confirm() → 明細をもう1つ追加」と呼んだあと、`len(o.lines)` は何になるでしょう？

1. 1
2. 2
3. 0
4. 実行時にプログラムが停止する

<details><summary>答えと解説</summary>

正解: **1**

1回目の追加は確定前なので成功し、明細は1件になります。Confirm() で confirmed が true になったあとの2回目は、ガード節 `if o.confirmed` に引っかかってエラーを返し、`append` まで到達しません。そのため明細は1件のままです。Go はエラーを値として返すだけなので、プログラムは停止せず次の行へ進みます。

</details>

## 3. DDDの全体地図 — 戦略と戦術

### DDDは2階建て

DDD のパターン(よくある問題への、名前の付いた定番の解き方)は大きく2つに分かれます。

| 階層 | 問い | 主なパターン |
|---|---|---|
| **戦略的設計 (Strategic Design)** | システムを**どこで区切り**、どこに投資するか | ユビキタス言語、境界づけられたコンテキスト、コンテキストマップ、サブドメイン |
| **戦術的設計 (Tactical Design)** | 区切った**境界の内側**をどう作るか | エンティティ、値オブジェクト、集約、ドメインサービス、リポジトリ、ファクトリ、ドメインイベント |

戦略が「システム全体をどの単位に分け、どこに力を入れるか」という大きな判断、戦術が「分けた1つの区画の中で、クラスやメソッドをどう作るか」という細かい判断です。本講座も第2〜5章で戦略、第6〜11章で戦術、第12章以降でアーキテクチャと実践、という順で進みます。

### 全体地図: 各パターンをひとことで

ここでは名前と雰囲気だけつかめば十分です。どれも後の章で、コードつきで1つずつ扱います。

**戦略的設計**(どこで区切るか)

| パターン | ひとことで | ECサイトでの小さな例 | 詳しく |
|---|---|---|---|
| ユビキタス言語 | チーム全員が会話でもコードでも使う共通の言葉 | 業務で「引当」と呼ぶなら、コードも `Allocate`(引当) にする | L2 |
| 境界づけられたコンテキスト | 言葉とモデルの意味が1つに決まる範囲 | 「商品」がカタログでは説明文と画像、配送では重さとサイズを指すので、別の区画に分ける | L3 |
| コンテキストマップ | 区画どうしのつながり方を描いた図 | 「注文」の区画が「会員」の区画の API に頼っている、と線で描く | L4 |
| サブドメイン | 業務を分けたときの1つ1つの領域と、その重要度 | 独自の送料・ポイント計算は差別化の源、ログイン機能は既製品で十分 | L5 |

**戦術的設計**(区画の中をどう作るか)

| パターン | ひとことで | ECサイトでの小さな例 | 詳しく |
|---|---|---|---|
| エンティティ | ID で見分け、中身が変わっても同じものとして扱う | 会員 `u-001` は名前を変えても同じ会員 | L6 |
| 値オブジェクト | 中身の値で見分ける、変更しない小さな部品 | 「1,000円」と「1,000円」は同じもの。金額や住所 | L7 |
| 集約 | 一緒に整合性を守るオブジェクトのまとまり | 注文と注文明細はセットで「明細は10行まで」を守る | L8・L9 |
| ドメインサービス | どのオブジェクトにも置きにくい業務処理の置き場 | 2つの口座の間の振替 | L10 |
| ドメインイベント | 業務上の「〜した」という出来事の記録 | 「注文が確定した」→ 在庫を引き当てるきっかけになる | L10 |
| リポジトリ | 集約を保存したり取り出したりする窓口 | `orders.Save(order)`、`orders.FindByID(id)` | L11 |
| ファクトリ | 複雑なオブジェクトを正しく組み立てる係 | カートの中身から注文を作る | L11 |

### 「軽量DDD」の罠

戦術パターンだけを真似て、Repository や Entity という名前のクラスを形だけ導入することを**軽量DDD (DDD-Lite)** と呼びます。形は DDD でも、境界を引かずユビキタス言語もない状態では、**巨大な1つの泥団子の中にきれいなクラスが散らばるだけ**になりがちです。

**泥団子 (Big Ball of Mud)** とは、構造らしい構造がなく、どのコードもどのコードとでもつながってしまっている巨大なシステムを指す、設計の世界の通称です。

パターンの名前を使うことが目的ではなく、ドメインの複雑さを扱うことが目的である、と常に思い出してください。

### DDDが効く場面・効かない場面

- **効く**: ビジネスルールが複雑で、仕様変更が頻繁な中核業務(与信、料金計算、在庫引当(注文のために在庫を確保すること)、保険の査定(保険金や保険料を審査して決めること)など)
- **効きにくい**: 単純な CRUD(マスタ管理画面など)、使い捨てのツール、技術的複雑さが支配的な領域(動画エンコードなど)

用語を補足します。

| 用語 | 意味 |
|---|---|
| CRUD | Create(作成)・Read(読み取り)・Update(更新)・Delete(削除)の4操作の頭文字。データを登録・表示・修正・削除するだけの処理を指す |
| マスタ | 商品一覧や取引先一覧のように、ほかの処理から参照される基本データ。その登録画面が「マスタ管理画面」 |
| 動画エンコード | 動画ファイルを別の形式に変換する処理。難しいのは技術(圧縮の計算)で、業務ルールはほとんどない |

すべてをDDDで書く必要はありません。**どこに戦術的設計を適用するか自体が戦略的判断**です(第5章・第16章で詳述)。

💡 コツ: 以降の章で迷子になったら、この表に戻って「いま戦略の話か、戦術の話か」を確認してください。それだけで理解の解像度が上がります。

### 確認問題

**問1.** DDDの「戦略的設計」と「戦術的設計」の関係として最も適切な説明はどれでしょう？

1. 戦略的設計はシステムの区切り方と投資先を決め、戦術的設計は区切った境界の内側の実装パターンを扱う
2. 戦略的設計は経営層が、戦術的設計は開発者が行うもので、互いに独立している
3. 戦術的設計を先にすべて適用してから、最後に戦略的設計を行う
4. 両者は同じ内容の別名である

<details><summary>答えと解説</summary>

正解: **1**

戦略 (Strategic Design) =「どこで区切り、どこに投資するか」(境界づけられたコンテキスト、サブドメインなど)、戦術 (Tactical Design) =「境界の内側をどう作るか」(エンティティ、集約、リポジトリなど)という2階建てです。順序としては境界を考える戦略が先にあり、戦術はその内側で生きます。経営層/開発者という分担の話ではなく、どちらも開発チームが関わる設計活動です。

</details>

**問2.** あるチームが Repository・Entity・Service というクラスを導入しましたが、境界づけられたコンテキストの検討もユビキタス言語の整備もしていません。この状態を指す用語と、起こりがちな結果の組み合わせとして適切なものはどれでしょう？

1. モデル駆動設計 — モデルとコードが一致して保守性が上がる
2. イベントソーシング — すべての変更が記録され監査性が上がる
3. 軽量DDD (DDD-Lite) — 形だけのパターン導入で、泥団子の中にクラスが散らばるだけになりがち
4. 知識の噛み砕き — ドメイン理解が深まる

<details><summary>答えと解説</summary>

正解: **3**

戦術パターンの形だけを真似る状態を軽量DDD (DDD-Lite) と呼びます。境界と言語という戦略的な土台がないと、どの Repository がどのモデルに属すのかが曖昧なまま肥大化し、「DDD 風の名前がついた泥団子」になります。パターン名を使うこと自体に効果はなく、ドメインの複雑さを扱えて初めて意味があります。他の選択肢は別概念の用語で、状況の説明として不適切です。

</details>

**問3.** 次のうち、DDD(特に戦術的設計)の適用効果が最も高いと考えられる領域はどれでしょう？

1. 社内マスタの登録・参照しかしない管理画面
2. 一度だけ実行するデータ移行スクリプト
3. 動画ファイルのエンコード処理
4. 条件が頻繁に変わる保険料の査定・計算ロジック

<details><summary>答えと解説</summary>

正解: **4**

DDD が効くのは「ビジネスルールが複雑で、変更が頻繁な中核業務」です。保険料の査定はまさにその典型で、ルールをモデルとして表現する投資が変更コストの低減で回収できます。単純 CRUD や使い捨てスクリプトでは DDD のコード量増加がただのコストになり、トランザクションスクリプトの方が適切なことも多いです。動画エンコードは技術的(偶有的)複雑さが支配的な領域で、ドメインモデルの出番は小さめです。

</details>

**問4.** 次のパターンのうち、「戦略的設計」に分類されるものはどれでしょう？

1. 値オブジェクト
2. 境界づけられたコンテキスト
3. リポジトリ
4. ファクトリ

<details><summary>答えと解説</summary>

正解: **2**

境界づけられたコンテキスト (Bounded Context) は「モデルが通用する範囲をどこで区切るか」という戦略的設計の中心パターンです。値オブジェクト・リポジトリ・ファクトリはいずれも境界の内側の作り方、つまり戦術的設計のパターンです。試験的なひっかけとして「コンテキスト」と付くものは戦略、モノの作り方の名前は戦術、と整理すると判別しやすくなります。

</details>

**問5.** 「社内の全システムを今後すべてDDDの戦術パターンで書き直す」という方針が提案されました。本章の内容を踏まえた最も適切な評価はどれでしょう？

1. DDDは常に最良の設計手法なので、全面適用が正しい
2. DDDはレガシーシステムには適用できないので、新規開発のみに限定すべきである
3. 戦術パターンはコード量を減らすので、単純なCRUDほど効果が大きい
4. どこに戦術的設計を適用するか自体が戦略的判断であり、複雑な中核業務に絞って投資すべきである

<details><summary>答えと解説</summary>

正解: **4**

DDD の適用自体にコストがかかるため、「複雑さがコストを上回る領域」=コアとなる複雑な業務に絞るのが正しい投資判断です。これはサブドメインの蒸留(第5章)につながる考え方です。「常に全面適用」は軽量DDDの量産につながりがちで、単純 CRUD では戦術パターンはむしろコード量を増やします。レガシーに適用できないわけではなく、段階的導入の手法もあります(第16章)。

</details>

**問6.** ECサイトで「会員 u-001 が名前を山田から佐藤に変えても、同じ会員として扱い続ける」——この考え方に最も対応する戦術的設計のパターンはどれでしょう？

1. 値オブジェクト
2. コンテキストマップ
3. エンティティ
4. ユビキタス言語

<details><summary>答えと解説</summary>

正解: **3**

ID で見分け、中身(名前など)が変わっても同じものとして扱うのがエンティティです(L6 で詳しく扱います)。値オブジェクトは逆に、中身の値そのもので見分ける部品(金額など)です。コンテキストマップとユビキタス言語は戦略的設計のパターンで、クラスの作り方の話ではありません。

</details>
