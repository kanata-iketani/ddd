# 第4章 コンテキストマップと連携パターン（ACL・OHSほか）

この章では、コンテキスト同士の関係を1枚で可視化する「コンテキストマップ」と、連携の型(パートナーシップから別々の道まで)を学びます。設計の話に見えて、実はチーム間の力関係と交渉の話でもある——そこがDDD戦略的設計の核心です。

## 1. コンテキストマップと上流・下流

### コンテキストマップとは

境界づけられたコンテキスト (Bounded Context) を見つけたら、次は**コンテキスト同士の関係**を描きます。これが**コンテキストマップ (Context Map)** です。箱(コンテキスト)と線(連携)だけの素朴な図ですが、「どのチームがどのモデルを持ち、誰が誰に依存しているか」を1枚で共有できます。

### 上流と下流

連携には力の向きがあります。

| 用語 | 意味 |
|---|---|
| 上流 (upstream) | 相手に影響を**与える**側。API の提供者など |
| 下流 (downstream) | 影響を**受ける**側。上流の変更で壊れうる |

上流が API を変更すれば、下流は追従するしかありません。逆に下流がどれだけ困っても、上流が動いてくれるとは限りません。これは**技術の問題ではなく、チーム間の力関係・交渉関係の問題**です。

### コンウェイの法則

「システムの構造は、それを作る組織のコミュニケーション構造を写し取る」——これが**コンウェイの法則 (Conway's Law)** です。チームが分かれればモデルも分かれ、チーム間の会話が少なければ連携も壊れがちです。コンテキストマップは技術の地図であると同時に、**組織の地図**でもあります。

### 描くのは「現状」

💡 コツ: コンテキストマップは理想のアーキテクチャ図ではなく、**今の現実**を描きます。「本当は腐敗防止層が欲しいのに、今は上流に従うだけ」という不都合な真実こそ描く価値があります。現状を可視化して初めて「どの関係から改善するか」を議論できるからです。

### 確認問題

**問1.** コンテキストマップを作成する最大の目的として、最も適切なものはどれでしょう?

1. 将来あるべき理想のシステム構成を関係者に提示するため
2. マイクロサービスのデプロイ構成とインフラを管理するため
3. コンテキスト間の依存関係と力関係という「現状」を可視化し、改善を議論する土台にするため
4. データベースの ER 図を補完する詳細設計書とするため

<details><summary>答えと解説</summary>

正解: **3**

コンテキストマップは「現状」の地図です。どのコンテキストが上流でどれが下流か、どんな連携パターンで結ばれているかを可視化し、改善の議論を可能にすることが目的です。理想図を描くものではなく(将来構成の提示は別の図の役割)、デプロイ構成や ER 図のような実装詳細を管理するものでもありません。「理想ではなく現実を描く」はひっかけとして頻出の論点です。

</details>

**問2.** 会員コンテキストの API が変更されるたびに、注文コンテキスト側の改修が必要になっています。この関係の説明として正しいものはどれでしょう?

1. 会員コンテキストが上流 (upstream)、注文コンテキストが下流 (downstream) である
2. 注文コンテキストが上流 (upstream)、会員コンテキストが下流 (downstream) である
3. 両者はモデルを共同所有する共有カーネルの関係である
4. 両者は連携しない「別々の道」の関係である

<details><summary>答えと解説</summary>

正解: **1**

変更の影響を「与える」側が上流、「受ける」側が下流です。会員 API の変更が注文側を壊すので、会員が上流・注文が下流です。上下を逆にした選択肢は定番のひっかけで、「呼び出す側が上流」と誤解しがちですが、基準はあくまで影響の向きです。共有カーネルはコードやスキーマの共同所有、別々の道は連携しない選択なので、API 依存があるこの状況には当てはまりません。

</details>

**問3.** 「組織のチーム編成を変えたら、システムの分割構造も引きずられて変わってしまった」。この現象を説明する法則はどれでしょう?

1. パレートの法則
2. ブルックスの法則
3. デメテルの法則
4. コンウェイの法則

<details><summary>答えと解説</summary>

正解: **4**

コンウェイの法則 (Conway's Law) は「システムの構造は組織のコミュニケーション構造を写し取る」というもので、コンテキストの境界とチームの境界が連動する理由を説明します。パレートの法則は80:20の分布、ブルックスの法則は「遅れたプロジェクトへの人員追加はさらに遅らせる」、デメテルの法則はオブジェクトの結合を減らすコーディング原則で、いずれも組織とシステム構造の対応関係の話ではありません。

</details>

**問4.** コンテキストマップを初めて描くとき、最も適切 (BEST) な方針はどれでしょう?

1. 現状の問題は省き、目指すターゲットアーキテクチャだけを描く
2. 不都合な関係(交渉できない順応者関係など)も含め、現状をありのまま描く
3. 技術スタック(言語・フレームワーク)ごとに箱を分けて描く
4. モデルの詳細なクラス図をすべての箱の中に描き込む

<details><summary>答えと解説</summary>

正解: **2**

マップの価値は現状認識にあります。「上流に逆らえず順応者になっている」「腐敗防止層がなくレガシーの型が漏れている」といった不都合な真実を描くからこそ、改善の優先順位を議論できます。理想だけ描くと現状とのギャップが見えません。箱の単位は技術スタックではなくモデルの境界(境界づけられたコンテキスト)であり、クラス図レベルの詳細は持ち込まず関係の種類に集中するのがコツです。

</details>

**問5.** あなたは下流チームのリーダーです。上流チームの頻繁な破壊的変更に毎回振り回されています。最初に (FIRST) 取り組むべきことはどれでしょう?

1. すぐに腐敗防止層 (ACL) を実装して変換コードを書き始める
2. 上流チームの変更を凍結するよう経営層に直訴する
3. コンテキストマップで依存と影響範囲を可視化し、上流との関係を顧客/供給者型へ変える交渉材料にする
4. 上流のモデルに合わせて自分たちのドメインモデルを全面的に書き直す

<details><summary>答えと解説</summary>

正解: **3**

まず現状の関係を可視化し、交渉のテーブルに乗せるのが戦略的設計の定石です。関係が顧客/供給者 (Customer/Supplier) に変われば、下流の要望が上流の計画に乗り、根本原因が和らぎます。ACL は有効な防御ですが、モデルの汚染は防げても変更追従のコスト自体は残るため「まず」ではありません。変更凍結の直訴は関係を悪化させがちで、上流に合わせた全面書き直しは順応者化であり、コアドメインを歪めるリスクがあります。

</details>

## 2. 協力型の連携パターン

### 協力型の4パターン

上流・下流の間に信頼や交渉のチャンネルが**ある**場合の連携パターンです。

| パターン | 関係 | 特徴 |
|---|---|---|
| パートナーシップ (Partnership) | 対等・運命共同体 | 片方が失敗すると両方失敗する。計画とリリースを同期する |
| 共有カーネル (Shared Kernel) | 対等・一部共有 | モデルの一部(コードや DB スキーマ)を共同所有。変更は両チーム合意 |
| 顧客/供給者 (Customer/Supplier) | 上流⇔下流・交渉あり | 下流=顧客の要望が上流の計画(バックログ)に乗る |
| 順応者 (Conformist) | 上流⇔下流・交渉なし | 下流が上流のモデルをそのまま受け入れる |

### どの関係になるかは組織で決まる

- 同じ目標に向かって相互依存する2チーム → パートナーシップ
- 密接な2チームが同じコア概念を使う → 共有カーネル。ただし**共有部分は結合そのもの**なので最小限に
- 上流が社内チームで、下流の声を聞く建て付けがある → 顧客/供給者
- 上流が巨大ベンダーや他社で、交渉の余地がない → 順応者

### 順応者は「負け」ではない

順応者 (Conformist) は一見弱い立場ですが、**変換の手間を払わずに済む合理的な選択**でもあります。上流のモデルが十分よくできているなら、素直に従うほうが安上がりです。問題になるのは「上流モデルの歪みが自分のコアドメインまで侵食する」ときで、その場合は次チャプターの腐敗防止層 (ACL) を検討します。

💡 コツ: パターン名は「設計の選択肢」である前に「組織関係の診断名」です。まず現実の関係がどれに当たるかを診断し、まずければ関係自体を変える(交渉する)か、防御(ACL)を入れるかを選びます。

### 確認問題

**問1.** 在庫チームと物流チームが「商品」モデルの中核部分を共通コードとして共同所有し、変更には双方のレビューとテスト通過を必須にしています。この連携パターンはどれでしょう?

1. 顧客/供給者 (Customer/Supplier)
2. 共有カーネル (Shared Kernel)
3. 順応者 (Conformist)
4. 公開ホストサービス (Open Host Service)

<details><summary>答えと解説</summary>

正解: **2**

モデルの一部をコードレベルで共同所有し、変更に両チームの合意を要する関係は共有カーネルです。顧客/供給者は上流・下流の交渉関係であり共同所有はしません。順応者は一方的に従う関係、公開ホストサービスは上流が安定 API を公開する防御型のパターンです。共有カーネルは重複を減らせる一方で最も結合が強いパターンなので、「共同所有+合意必須」というキーワードから見分けます。

</details>

**問2.** 社内の会員基盤チーム(上流)が、注文チーム(下流)からの要望を定期的にヒアリングし、自分たちのロードマップに優先順位をつけて反映しています。この関係はどれでしょう?

1. パートナーシップ (Partnership)
2. 順応者 (Conformist)
3. 共有カーネル (Shared Kernel)
4. 顧客/供給者 (Customer/Supplier)

<details><summary>答えと解説</summary>

正解: **4**

下流が「顧客」として要望を出し、上流が「供給者」として計画に乗せる交渉チャンネルのある上下関係は顧客/供給者です。パートナーシップは上下ではなく対等な運命共同体で、計画を同期します。順応者は交渉チャンネルがなく一方的に従う場合です。共有カーネルはモデルの共同所有であり、この状況のような要望→反映の関係ではありません。「上下関係があるか」「交渉できるか」の2軸で診断するのがコツです。

</details>

**問3.** 大手決済ベンダーの API 仕様には交渉の余地がなく、支払いの社内モデルをベンダーの構造にそのまま合わせて実装しました。この選択はどのパターンでしょう?

1. 順応者 (Conformist)
2. パートナーシップ (Partnership)
3. 顧客/供給者 (Customer/Supplier)
4. 公表された言語 (Published Language)

<details><summary>答えと解説</summary>

正解: **1**

上流(ベンダー)のモデルをそのまま受け入れるのは順応者です。交渉の余地がない外部ベンダー相手では合理的な選択になりえます(変換層を書くコストを節約できる)。パートナーシップや顧客/供給者は交渉・協調チャンネルがある場合のパターンなので不適です。公表された言語は業界標準フォーマットで会話するパターンで、特定ベンダーの独自仕様に従うこととは異なります。順応者の弱点はベンダーモデルの歪みが自モデルへ侵食することで、それが痛み始めたら ACL を検討します。

</details>

**問4.** パートナーシップ (Partnership) が最も適する状況はどれでしょう?

1. 上流が外部ベンダーで、仕様変更の交渉が一切できない
2. 2つのサービスが完全に独立していて連携の必要がない
3. 2チームの機能が相互依存し、どちらかが失敗すればもう一方の目標も達成できない
4. 片方のチームがもう片方の公開 API を参照するだけの軽い依存がある

<details><summary>答えと解説</summary>

正解: **3**

パートナーシップは「運命共同体」の2チームが計画・リリースを同期して協調するパターンです。相互依存して一蓮托生という点が決め手です。交渉不能な外部ベンダー相手なら順応者か ACL、完全独立なら別々の道、公開 API を参照するだけなら公開ホストサービスの下流になるだけで、どれもパートナーシップの密な協調は不要です。密な同期はコストが高いため、本当に運命共同体の場合に限って選ぶのがポイントです。

</details>

**問5.** 共有カーネル (Shared Kernel) を運用するうえで、最も適切 (BEST) な方針はどれでしょう?

1. 重複を徹底排除するため、共有範囲をできるだけ広げる
2. 共有範囲は最小限に絞り、変更は両チームの合意と共通テストで守る
3. 開発速度を優先し、片方のチームが自由に共有部分を変更できるようにする
4. 共有するのはドキュメントだけにして、コードは各チームがコピーして持つ

<details><summary>答えと解説</summary>

正解: **2**

共有カーネルは共有した分だけ2チームが結合します。だから範囲は最小限(本当に共通の中核概念だけ)に絞り、変更は両チーム合意+共通テストで保護するのが定石です。共有範囲を広げるほど片方の変更がもう片方を壊しやすくなるので逆効果です。片方が自由に変更できる運用は共有カーネルの前提(合意)を壊します。コードをコピーして持つのは共有カーネルではなく重複を許す選択で、それ自体は「別々の道」に近い別のトレードオフです。

</details>

## 3. 防御型の連携パターンと選択基準

### 自分のモデルを守る防御型パターン

相手のモデルに影響されたくない、あるいは相手と調整できないときのパターンです。

### 腐敗防止層 (Anti-Corruption Layer, ACL)

外部のモデルを**自分のコンテキストの入口で自分のモデルへ変換する層**です。レガシーシステムや外部 SaaS との連携の定番で、相手の型・用語・構造がドメイン層へ漏れるのを防ぎます。

```go
// 外部決済SaaSのレスポンス(相手の都合のモデル)
type rawPayment struct {
    Stat int    `json:"stat"` // 0=OK, 9=NG という相手の符号
    Amt  string `json:"amt"`  // 文字列の金額
}

// ACL: 相手のモデル → 自分のドメインモデルへ変換
func toDomain(r rawPayment) (domain.Payment, error) {
    amount, err := domain.NewMoney(r.Amt) // 値オブジェクトで検証
    if err != nil {
        return domain.Payment{}, err
    }
    return domain.NewPayment(amount, r.Stat == 0), nil
}
```

変換はドメイン層の外側(インフラ層・連携アダプタ)に置き、ドメイン層は自分の言葉だけで書き続けます。

### 上流側の公開パターン

- **公開ホストサービス (Open Host Service, OHS)**: 上流が、特定の下流向けではない**安定した公開 API** を提供する
- **公表された言語 (Published Language, PL)**: 業界標準や公開仕様のフォーマット(例: iCalendar、全銀フォーマット)で会話する。OHS とセットで使われることが多い

### 別々の道 (Separate Ways)

連携のコストが利益を上回るなら、**つながない**のも立派な選択です。小さな重複(例: 2つのコンテキストがそれぞれ簡単な換算ロジックを持つ)は、密結合よりずっと安くつくことがあります。

### 選択基準

| 問い | Yes なら |
|---|---|
| 相手のモデルをそのまま使っても汚染されない? | 順応者 |
| 相手のモデルから自分のモデルを守りたい? | ACL |
| 自分が上流で、多数の下流に安定供給したい? | OHS (+PL) |
| そもそも連携の価値が小さい? | 別々の道 |

💡 コツ: 外部 SaaS・レガシー連携は「まず ACL」が定石です。相手は相手の都合で変わるので、変換層が緩衝材になります。

### 確認問題

**問1.** 20年運用されているレガシー基幹システムの「得意先マスタ」の構造を、新しく作る販売コンテキストのドメインモデルに持ち込みたくありません。最も適切 (BEST) な選択はどれでしょう?

1. 腐敗防止層 (ACL) を設け、境界でレガシーの構造を自分のモデルへ変換する
2. 順応者 (Conformist) としてレガシーの構造をそのまま採用する
3. レガシーと共有カーネルを組み、マスタ定義を共同所有する
4. 販売コンテキストの開発前に、レガシー基幹を全面リプレースする

<details><summary>答えと解説</summary>

正解: **1**

レガシーの型や符号をドメイン層に入れたくない、というのがまさに ACL の出番です。境界の変換層が緩衝材となり、新モデルをきれいに保てます。順応者はレガシーの歪みがコアドメインへ侵食することを受け入れる選択なので、この要件に反します。レガシーとの共有カーネルは古い構造との結合を強める最悪手です。全面リプレースは理想に見えますが、販売コンテキストの開発をブロックする巨大リスクで、「まず守って進める」ACL が現実解です。

</details>

**問2.** あなたのチームは社内10チームに商品カタログ情報を提供する上流です。下流ごとの個別 API 対応で疲弊しています。最も適切 (BEST) な打ち手はどれでしょう?

1. 主要な下流チームそれぞれと共有カーネルを組む
2. 10チームすべてとパートナーシップを結び計画を同期する
3. 公開ホストサービス (OHS) として安定した公開 API を整備し、公表された言語 (PL) で仕様を共有する
4. すべての連携をやめて別々の道 (Separate Ways) を選ぶ

<details><summary>答えと解説</summary>

正解: **3**

多数の下流を抱える上流の定石は OHS です。個別対応をやめ、誰に対しても同じ安定 API と文書化された共通フォーマット (PL) を提供することで、連携コストが「下流の数に比例」から「1本の API の維持」に変わります。10個の共有カーネルや10本のパートナーシップは結合と同期コストを爆発させる逆方向の打ち手です。別々の道はカタログ情報が実際に必要とされている以上、業務が成り立ちません。

</details>

**問3.** 腐敗防止層 (ACL) の実装方針として最も適切なものはどれでしょう?

1. ドメイン層のエンティティ内部に変換ロジックを書き、外部の型を直接受け取る
2. コンテキストの境界(インフラ層や連携アダプタ)に変換を置き、外部モデルを自分のドメインモデルへ変換してから内側に渡す
3. 変換は相手システム側に実装してもらい、自分は何も変換しない
4. 画面 (UI) 層で表示する直前に変換する

<details><summary>答えと解説</summary>

正解: **2**

ACL は「境界で変換し、内側(ドメイン層)には自分の言葉しか入れない」のが原則です。本文の Go 例のように、外部のレスポンス型をアダプタで受けて値オブジェクトやエンティティへ変換します。エンティティ内部に外部の型を持ち込むと、守りたかったドメイン層が汚染されて本末転倒です。相手側に変換を頼めるならそれは OHS/PL に近い話ですが、相手都合で変わるものに自分のモデルの防御を委ねるべきではありません。UI 層での変換ではドメイン層・アプリケーション層がすでに汚染されています。

</details>

**問4.** 2つのコンテキスト間で必要なデータ連携は年1回の簡単な一覧出力だけで、リアルタイム統合の構築には数か月かかると見積もられました。最も適切な選択はどれでしょう?

1. 公開ホストサービス (OHS) を構築する
2. 腐敗防止層 (ACL) つきの常時 API 連携を作る
3. 共有カーネルでモデルを統一する
4. 別々の道 (Separate Ways) を選び、統合せず小さな重複や手動連携を許容する

<details><summary>答えと解説</summary>

正解: **4**

連携の価値(年1回の一覧)に対して統合コスト(数か月)が明らかに過大なので、「つながない」別々の道が合理的です。小さな重複や手作業は密結合の維持費よりずっと安いことがよくあります。OHS や常時 API 連携+ACL は 技術的に正しくても投資対効果が合いません。共有カーネルは最も結合が強く、この状況では最も過剰な選択です。DDD の連携パターンには「統合しない」という選択肢が正式に含まれている、というのがこの問題の学びです。

</details>

**問5.** 順応者 (Conformist) と腐敗防止層 (ACL) の違いの説明として、最も適切なものはどれでしょう?

1. 両者は同じ概念の別名である
2. 順応者は外部 SaaS 専用、ACL はレガシーシステム専用のパターンである
3. 順応者は上流のモデルをそのまま受け入れ、ACL は変換層を設けて自分のモデルを守る
4. ACL は上流チームが下流のために実装するものである

<details><summary>答えと解説</summary>

正解: **3**

どちらも「交渉できない上流」への対応ですが、順応者は変換せずそのまま従う(安いが汚染リスク)、ACL は変換層を払ってでも自分のモデルを守る(高いが清潔)という正反対のトレードオフです。対象がSaaSかレガシーかで決まるものではなく、「上流モデルの歪みが自分のコアドメインに害を及ぼすか」で選びます。また ACL は守りたい側=下流が自分のコンテキスト内に実装するものです。上流が提供するのは OHS/PL であり、そこを混同させるのが典型的なひっかけです。

</details>
