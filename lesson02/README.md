# 第2章 ユビキタス言語 — モデルとコードを一致させる

DDDの土台は、チーム全員が同じ言葉で語ることです。この章では、ユビキタス言語 (Ubiquitous Language) がなぜ設計の質を決めるのか、そして言葉をコードにそのまま反映し、会話からモデルを掘り起こす方法を学びます。

## 1. ユビキタス言語とは

### 「同じ言葉」がチームを強くする

**ユビキタス言語 (Ubiquitous Language)** とは、開発者とドメインエキスパート(業務に詳しい人)がチーム全員で使う、共通の言葉のことです。「ユビキタス=遍在する」の名のとおり、**会話・ドキュメント・図・そしてコード**のすべての場所で同じ言葉を使います。

### 翻訳コストという見えない損失

よくある失敗は、エキスパートの言葉を開発者が「技術の言葉」に翻訳してしまうことです。

| エキスパートの言葉 | 開発者が付けた名前 | 何が失われたか |
|---|---|---|
| 在庫を**引当**する | `stock_update` | 「引当=注文のために在庫を確保する」という業務ルール |
| 契約を**解約**する | `delete_flag = 1` | 解約には違約金計算や通知が伴うという知識 |

翻訳が挟まると、仕様の会話のたびに「`stock_update` って引当のことでしたっけ?」という確認が発生し、やがて認識のズレがバグになります。逆に、コードがエキスパートの言葉そのままなら、**エキスパートとの会話がそのまま設計レビューになる**のです。

### 言語はコンテキストごとに1つ

ユビキタス言語は「全社共通の標準用語集」ではありません。同じ「商品」でも、販売の文脈では価格や在庫が重要で、配送の文脈では重量やサイズが重要です。言葉の意味は**境界づけられたコンテキスト(第3章)ごとに定義**します。無理に全社で1つの定義に統一しようとすると、誰の業務にも合わない曖昧な言葉ができあがります。

💡 コツ: 会議で「それって◯◯のことですか?」という言い換え確認が頻発したら、ユビキタス言語が育っていないサインです。その場で定義を合意し、用語集に残しましょう。

### 確認問題

**問1.** ドメインエキスパートが「在庫の引当」と呼ぶ処理を、開発者が stock_update という名前で実装しました。この命名の最大の問題はどれでしょう?

1. 英語の文法として誤っているため、海外メンバーに通じない
2. 「引当」という業務知識がコードから失われ、会話のたびに翻訳が必要になる
3. snake_case は Go の命名規約に反するため、lint エラーになる
4. update という動詞は SQL の UPDATE 文と紛らわしい

<details><summary>答えと解説</summary>

正解: **2**

stock_update は「在庫を何かしら更新する」としか語っておらず、「注文のために在庫を確保する」という引当の業務ルールがコードから読み取れなくなります。以後、エキスパートとの会話に毎回翻訳が挟まり、認識ズレがバグの温床になります。英語の文法や命名規約(選択肢の1・3番目)は表面的な問題にすぎず、SQL との紛らわしさも本質ではありません。DDDでは「名前の技術的な正しさ」より「ドメインの言葉との一致」を優先します。

</details>

**問2.** ユビキタス言語を使うべき場所として、DDDの考え方に最も合うものはどれでしょう?

1. ドメインエキスパートとの会議でのみ使い、コードは技術用語で書く
2. ドキュメントとコードで使い、口頭の会話はくだけた言い方でよい
3. 会話・ドキュメント・図・コードのすべてで一貫して使う
4. コードのコメントにだけ業務用語を併記する

<details><summary>答えと解説</summary>

正解: **3**

「ユビキタス(遍在する)」の名のとおり、会話からコードまですべての場所で同じ言葉を使うのが定義そのものです。「会議でのみ使う」「ドキュメントとコードだけで使う」のように場所によって言葉が変わると、その境目で毎回翻訳が発生し、知識が失われます。コメントに併記する案も、コード本体の名前が技術用語のままでは「実装を読む人」に翻訳を強いる点で不十分です。

</details>

**問3.** 営業チームは「出荷」を受注確定の意味で、物流チームは倉庫からの発送の意味で使っており、1つのシステムで混乱が起きています。DDD的に最も適切な対応はどれでしょう?

1. それぞれのコンテキストを分け、各コンテキスト内で「出荷」の意味を定義する
2. 全社会議を開き、「出荷」の意味を全社で1つに統一する
3. 混乱を避けるため「出荷」という言葉の使用を禁止し、英語の ship に統一する
4. システム側で出荷フラグを2つ持たせ、どちらの意味でも動くようにする

<details><summary>答えと解説</summary>

正解: **1**

ユビキタス言語は境界づけられたコンテキストごとに1つです。営業と物流では関心事が違うので、コンテキストを分けてそれぞれの中で「出荷」を明確に定義するのが正解です。全社で1つに統一する案は、どちらかの業務に合わない曖昧な定義を生みがちで、DDDが避ける道です。言葉の禁止や英語化は意味の衝突を解決せず、フラグを2つ持つ案はモデルの混乱をコードに持ち込むだけです。

</details>

**問4.** コードベースに「顧客」を表す名前として Customer・User・Member が混在しています。これを放置した場合に起きる可能性が最も高い問題はどれでしょう?

1. コンパイル時間が長くなり、ビルドが遅くなる
2. データベースの正規化が崩れ、性能が劣化する
3. クラス数が増えてメモリ使用量が増大する
4. 「会員だけに適用されるルール」を User に実装するなど、仕様の読み違いによるバグが生まれる

<details><summary>答えと解説</summary>

正解: **4**

名前のゆらぎは「この3つは同じものか、違うものか」という判断を読み手に毎回強います。実は「Member=ログインできる顧客」のような意味の違いが隠れていた場合、ルールを誤った型に実装する読み違いバグが起きます。コンパイル時間・DB性能・メモリ(他の3つの選択肢)は名前のゆらぎとは無関係です。ゆらぎを見つけたら、意味が同じなら1つにリネームし、違うなら違いを定義して用語集に残します。

</details>

**問5.** ユビキタス言語を作り育てる主体として、最も適切なのはどれでしょう?

1. 業務を正しく知っているドメインエキスパートが一方的に定める
2. 開発者とドメインエキスパートが対話しながら共同で育てる
3. 命名の一貫性に責任を持つテックリードが一括で決める
4. 外部の業務コンサルタントに用語集の作成を委託する

<details><summary>答えと解説</summary>

正解: **2**

ユビキタス言語は両者の対話の産物です。エキスパートの言葉には暗黙知が多く、開発者が「それはどういう意味ですか」と問い直すことで曖昧さが削られ、モデルとして使える言葉に磨かれていきます。エキスパートだけ(1番目)では実装に落ちない曖昧さが残り、テックリードだけ(3番目)では業務の実態からズレ、外部委託(4番目)では日々の会話の中で言葉を育てるというプロセス自体が成立しません。

</details>

## 2. 言葉をコードに反映する

### コードはドメインの言葉で書く

ユビキタス言語の真価は、**コードの名前がそのままドメインの言葉になっている**ときに発揮されます。悪い例と良い例を比べてみましょう。

```go
// ❌ 悪い例: 技術の言葉。何が起きるのか読み取れない
func (o *Order) SetStatus(s int) { o.status = s }
o.SetStatus(3) // 3って何?

// ✅ 良い例: ドメインの言葉。業務ルールの置き場所も明確
func (o *Order) Cancel(reason CancelReason) error {
    if o.isShipped {
        return ErrAlreadyShipped // 出荷済みはキャンセル不可という業務ルール
    }
    o.status = StatusCancelled
    return nil
}
order.Cancel(reason)
```

`SetStatus(3)` は「状態を3にする」としか語りませんが、`Cancel` は「キャンセルという業務行為」を表し、**「出荷済みならキャンセルできない」というルールの自然な置き場所**にもなります。名前を変えるだけで、設計が変わるのです。

### 動詞の選び分けがモデルを変える

「ユーザーを**登録する**」「保険に**申し込む**」「下書きを**作成する**」——どれも英語にすれば create かもしれませんが、業務上の意味は違います。申込には審査が続き、登録には重複チェックがあるかもしれません。何でも `CreateXxx` に寄せると、こうした違いがコードから消えます。**エキスパートが使い分けている動詞は、そのまま使い分けて実装**しましょう。

### 用語集とリネームの勇気

- 用語集 (glossary) はコンテキスト単位で作り、リポジトリに置いてコードレビューで参照する
- ドメインの言葉が変わったら、**コードもリネームする**。旧名のまま放置すると、その瞬間から翻訳コストが復活します

💡 コツ: IDE のリネーム機能があれば、名前の変更は安全で安い作業です。「動いているから触らない」より「言葉とズレたまま放置する」方が高くつきます。

### 確認問題

**問1.** 注文キャンセル機能の実装として、DDDの観点で最も望ましいものはどれでしょう?

1. order.SetStatus(3) のように状態コードを直接セットする
2. UpdateOrder(id, map[string]any{"status": 3}) のような汎用更新関数を使う
3. order.Cancel(reason) のようにドメインの行為を表すメソッドにする
4. db.Exec("UPDATE orders SET status=3") を呼び出し側に直接書く

<details><summary>答えと解説</summary>

正解: **3**

Cancel はエキスパートの言葉そのままであり、「出荷済みならキャンセル不可」のような業務ルールを中に閉じ込める自然な置き場所になります。SetStatus(3) や汎用更新関数は「何の業務行為なのか」を語らず、ルールの置き場所も失われるため、チェック漏れが呼び出し側に散らばります。SQL直書きはさらに進んで、モデルそのものを素通りしてしまう最悪の形です。

</details>

**問2.** ドメインエキスパートは一貫して「申込(もうしこみ)」と言うのに、コードでは Registration と命名されていました。最も適切な対応はどれでしょう?

1. Application(申込)へリネームし、用語集にも登録して言葉を一致させる
2. 動いているコードなので触らず、ドキュメントに対訳表を用意する
3. コメントで「// 申込のこと」と補足して名前はそのままにする
4. エキスパートに Registration という言葉に合わせてもらうよう依頼する

<details><summary>答えと解説</summary>

正解: **1**

コードを言葉に合わせてリネームするのが原則です。対訳表やコメント(2・3番目)は翻訳コストを固定化する対症療法で、会話とコードのズレは残り続けます。エキスパートに言葉を変えさせる案は本末転倒で、業務の言葉こそがモデルの源泉です。IDEのリネームは安全で安い作業なので、「動いているから触らない」より言葉との一致を優先しましょう。

</details>

**問3.** 「ユーザー登録」「保険の申込」「下書きの作成」をすべて CreateRecord(kind, data) という1つの汎用関数で実装する案の、最大の問題はどれでしょう?

1. 関数の引数が多くなり、呼び出し時にタイプ量が増える
2. 登録・申込・作成それぞれに固有の業務ルールの違いがコードから消える
3. kind の文字列比較が増えて実行速度が低下する
4. レコードという言葉が英語なので日本人チームに不向きである

<details><summary>答えと解説</summary>

正解: **2**

申込には審査、登録には重複チェックのように、動詞の違いの裏には業務ルールの違いがあります。汎用関数に寄せるとその違いがコードから消え、ルールは呼び出し側の if 文に散らばるか、実装漏れになります。タイプ量や文字列比較の速度(1・3番目)は本質ではなく、英語か日本語かも論点ではありません。エキスパートが言い分けているなら、コードも分けるのが原則です。

</details>

**問4.** 用語集 (glossary) の運用として最も効果的なのはどれでしょう?

1. プロジェクト開始時に全用語を確定し、以後は変更しない
2. 全社共通の1つの用語集を作り、全コンテキストで共用する
3. 個人のメモとして各自が好きな形式で管理する
4. コンテキスト単位でリポジトリに置き、会話で言葉が育つたびに更新する

<details><summary>答えと解説</summary>

正解: **4**

用語集は「言葉の現在地」を共有する生きたドキュメントなので、コードと同じリポジトリに置き、レビューで参照し、言葉の変化に合わせて更新し続けます。開始時に確定して凍結する案は、モデリングが継続的な活動であることと矛盾します。全社共通の1冊は「コンテキストごとに言語は1つ」の原則に反し、個人メモではチームの共通言語になりません。

</details>

**問5.** 業務の言葉が「仮予約」から「キープ」に変わりましたが、コードは ProvisionalReservation のままです。放置した場合に起きる本質的な問題はどれでしょう?

1. クラス名が長いままなので、コードの行幅が規約を超える
2. 新しい言葉を知らない新人が歴史的経緯を学べなくなる
3. 会話は「キープ」・コードは「仮予約」という翻訳が復活し、認識ズレが蓄積していく
4. Git の履歴とクラス名が一致しなくなり、blame が難しくなる

<details><summary>答えと解説</summary>

正解: **3**

ユビキタス言語の価値は「会話とコードの一致」なので、言葉が進化したのにコードが追従しないと、せっかく消した翻訳コストが復活します。新しいメンバーは「キープとProvisionalReservationは同じものか?」と毎回確認する羽目になり、ズレが積もればバグになります。行幅やGit履歴(1・4番目)は些末な話で、歴史的経緯は用語集やADRに残せば済みます。リネームの勇気が言語を生かし続けます。

</details>

## 3. 会話からモデルを発見する

### モデルは会話の中に埋まっている

ドメインモデルは、仕様書を読むだけでは手に入りません。ドメインエキスパートの頭の中にある**暗黙知 (tacit knowledge)** を、対話で掘り起こす必要があります。Evans はこの活動を**知識の噛み砕き (knowledge crunching)** と呼びました。

### 効果的な問いかけのパターン

| 問いかけ | 掘り起こせるもの |
|---|---|
| 「◯◯とは何ですか?」 | 用語の定義、概念の境界 |
| 「例外はありますか?」 | 隠れた業務ルール、エッジケース |
| 「それは誰が決めますか?」 | 責務の所在、権限のモデル |
| 「もし〜したらどうなりますか?」 | 状態遷移、イベントの連鎖 |

### 具体的なシナリオで検証する

抽象的な議論より、**実際の事例を一緒に追いかける**方が暗黙知は出てきます。「この注文をいまキャンセルしたら、引当済みの在庫はどうなりますか?」と聞けば、「あ、出荷準備に入っていたら倉庫に連絡が要りますね」のような、仕様書にない知識が現れます。

### 言葉の裏のルールを疑う

「キャンセルは3日以内です」と言われたら、そのまま `if days <= 3` と書く前に「なぜ3日なんですか?」と聞きましょう。「決済の確定が3営業日後だから」と分かれば、本当のルールは**「決済確定前ならキャンセル可能」**であり、モデルに置くべき概念は「3日」ではなく「決済確定」だと判明します。

💡 コツ: モデリングは設計フェーズで一度やって終わりではありません。実装中に「この言葉、曖昧だったな」と気づいたら、それが次の対話のチケットです。モデルは反復のたびに深くなります。

### 確認問題

**問1.** ドメインエキスパートが「在庫が足りないときは引当できません」と言いました。モデルを深めるために次に投げる質問として最も効果的なのはどれでしょう?

1. 「例外はありますか? 足りなくても引当する場合は?」と深掘りする
2. 「わかりました。在庫数チェックを実装します」と確認して終える
3. 「在庫テーブルにはどのカラムがありますか?」とDB構造を聞く
4. 「他社のシステムではどう実装されていますか?」と事例を聞く

<details><summary>答えと解説</summary>

正解: **1**

ルールを1つ聞いたら「例外はありますか?」と重ねるのが知識の噛み砕きの定石です。「予約商品は入荷予定を引当ててよい」のような隠れたルールが出てくれば、モデルは一段深くなります。すぐ実装に向かう(2番目)と暗黙知を取りこぼし、DB構造の質問(3番目)は実装の話で業務の理解を深めません。他社事例(4番目)は参考にはなっても、自分たちのドメインのルールは出てきません。

</details>

**問2.** ドメインエキスパートの暗黙知を引き出す方法として、最も効果が高いとされるのはどれでしょう?

1. 業務マニュアルを全ページ読み込んで仕様を抽出する
2. 「要件を漏れなく一覧にしてください」と依頼する
3. 具体的な事例を取り上げ、「この場合どうなりますか?」と一緒に追いかける
4. 既存システムのソースコードを解析して仕様を復元する

<details><summary>答えと解説</summary>

正解: **3**

暗黙知は「問われて初めて言葉になる」性質があるため、具体的なシナリオを一緒に歩くのが最も効果的です。「このケースなら倉庫に連絡が要る」のような、マニュアルにも要件一覧にも載らない知識が会話の中に現れます。マニュアルや既存コード(1・4番目)は過去のある時点の形式知でしかなく、「漏れなく一覧に」という依頼(2番目)はエキスパート自身が意識していない知識を外に出せません。

</details>

**問3.** 「キャンセルは3日以内」と言われたとき、そのまま if days <= 3 と実装する前に「なぜ3日なんですか?」と理由を確認する意義はどれでしょう?

1. ルールの根拠をドキュメントに残し、監査に備えるため
2. 「決済確定前なら可能」のような本当のルールを発見し、モデルに正しい概念を置くため
3. エキスパートの記憶違いを指摘し、仕様の誤りを正すため
4. 3日を設定ファイルに切り出すべきか判断するため

<details><summary>答えと解説</summary>

正解: **2**

「3日」は表面的な値で、裏には「決済が確定するまで」という本当のルールが隠れていることがあります。それが分かれば、モデルに置くべき概念は日数ではなく「決済確定」というイベントになり、決済仕様が変わっても壊れない設計になります。監査用の記録や設定値の切り出し(1・4番目)は副次的な効果にすぎず、記憶違いの指摘(3番目)は目的ではありません。問いの狙いはルールの構造の発見です。

</details>

**問4.** DDDにおけるモデリング活動の進め方として、正しい認識はどれでしょう?

1. 設計フェーズで完全なモデルを確定させ、実装フェーズでは変更しない
2. モデリングはアーキテクトの仕事であり、実装者は関与しない
3. まずコードを書き切り、リリース後にまとめてモデルを整理する
4. 実装中の気づきを対話に戻し、反復のたびにモデルを深めていく

<details><summary>答えと解説</summary>

正解: **4**

知識の噛み砕きは継続的な活動です。実装してみると「この言葉は曖昧だった」「この境界は違った」という発見が必ずあり、それを対話に戻してモデルを更新するループが DDD の核心です。前もって完全に確定する案(1番目)は暗黙知の性質に反し、アーキテクト専任(2番目)は会話とコードの距離を広げます。リリース後にまとめて整理(3番目)では、誤ったモデルの上に実装が積み上がってしまいます。

</details>

**問5.** 実装前に「この注文をいまキャンセルしたら在庫はどうなりますか?」のような具体シナリオでモデルを検証する最大の価値はどれでしょう?

1. テストコードのテストケースを事前に列挙できる
2. 画面デザインの要件を早期に固められる
3. モデルの欠落(考慮漏れの状態やルール)を実装前に発見できる
4. エキスパートとの打ち合わせ回数を減らせる

<details><summary>答えと解説</summary>

正解: **3**

シナリオを歩くと「出荷準備中のキャンセル」のような考慮漏れの状態が露呈し、モデルの穴を実装前の安い段階で塞げます。これが最大の価値です。テストケースの列挙(1番目)は嬉しい副産物ですが主目的ではなく、画面デザイン(2番目)は別の活動です。打ち合わせ回数はむしろ増えることもありますが、翻訳ミスややり直しが減るため総コストは下がります。

</details>
