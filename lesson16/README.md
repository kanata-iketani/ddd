# 第16章 アンチパターンと現実解 — DDDを使う判断・使わない判断

最終章は「DDDの使いどころ」を見極める章です。よくある失敗パターンを症状から見分ける目を養い、DDDを使わない勇気と、レガシーや組織へ段階的に導入する現実的な方法を身につけます。ここまでの15章の総仕上げとして、設計判断の「さじ加減」を問います。

## 1. アンチパターン集 — 形だけDDDの見分け方

### 貧血ドメインモデル (Anemic Domain Model)

最も多いアンチパターンが**貧血ドメインモデル**です。エンティティが getter/setter だけの「データの袋」になり、ビジネスルールが全部サービス層に流れ出した状態を指します。

```go
// 貧血: Order はデータを持つだけ、ルールは外側に散る
type Order struct { Status int }
func (o *Order) SetStatus(s int) { o.Status = s }

// サービス側にルールが漏れ出す
func (s *OrderService) Cancel(o *Order) error {
    if o.Status == 2 { return errors.New("出荷済みは取消不可") } // ← 本来 Order の責務
    o.SetStatus(3)
    return nil
}
```

「取消できる条件」は注文というドメインの知識なのに、外から `SetStatus` で好き放題書き換えられます。`order.Cancel()` のように**オブジェクト自身がルールを守る**形に戻すのが処方箋です。

### その他の典型パターン

| アンチパターン | 症状 | 処方箋 |
|---|---|---|
| スマートUI (Smart UI) | 画面のイベントハンドラにビジネスロジック直書き | ロジックをドメイン層へ抽出 |
| 神集約 (God Aggregate) | 1つの集約が何でも抱え、同時更新で競合多発 | 真の不変条件で境界を割り直す |
| リポジトリへのロジック漏れ | SQL の WHERE 句にビジネスルールが埋まる | ルールはドメイン、リポジトリは出し入れだけ |
| ユビキタス言語の形骸化 | 用語集は作ったが会話もコードも別言語 | 会話・コード・ドキュメントで同じ語を使う |
| DDDごっこ | `domain/` ディレクトリはあるが中身は貧血 | 命名ではなく「ルールがどこにあるか」で判断 |

💡 コツ: 「このルール、どのクラスが守っているの?」と聞いて即答できなければ、たいてい貧血化しています。ディレクトリ名が `domain/` でも、ルールがサービスに漏れていれば DDD ではありません。**構造ではなく、知識の置き場所で判定**しましょう。

### 確認問題

**問1.** あるコードベースで、全エンティティが getter/setter だけを持ち、「注文は出荷後はキャンセルできない」といった判定が全てサービス層の if 文に書かれています。この状態を表す最も適切な用語はどれでしょう？

1. 貧血ドメインモデル (Anemic Domain Model)
2. 境界づけられたコンテキスト (Bounded Context)
3. 腐敗防止層 (Anti-Corruption Layer)
4. 値オブジェクト (Value Object)

<details><summary>答えと解説</summary>

正解: **1**

エンティティがデータ保持だけを担い、ビジネスルールがサービス層に流出した状態は貧血ドメインモデル (Anemic Domain Model) です。処方箋は `order.Cancel()` のようにルールをオブジェクト自身へ戻すことです。境界づけられたコンテキストはモデルの適用範囲、腐敗防止層は外部モデルの変換層、値オブジェクトは不変の値を表す道具であり、いずれもこの症状の名前ではありません。

</details>

**問2.** プロジェクトに `domain/`, `usecase/`, `infrastructure/` というディレクトリがきれいに分かれています。しかし `domain/` の中のクラスは全て getter/setter だけで、判定ロジックは `usecase/` に集中していました。この状況の評価として最も適切なものはどれでしょう？

1. ディレクトリが分離されているので DDD が正しく実践できている
2. ディレクトリ構造は整っているが、知識がドメイン層に無いため実質は貧血モデルで、DDDごっこに陥っている
3. usecase にロジックが集まるのが DDD の理想形である
4. infrastructure 層が存在するので問題はない

<details><summary>答えと解説</summary>

正解: **2**

DDD は命名やディレクトリ構造ではなく「ドメイン知識がどこに表現されているか」で判定します。`domain/` があっても中身が貧血で、ルールが usecase に集まっているなら、形だけ真似た DDDごっこです。ディレクトリ分離やインフラ層の存在は必要条件ですらなく、ロジックが usecase に集中するのは理想ではなく貧血化の症状です。構造が整っていることと、モデルが知識を担っていることは別問題だと見抜く必要があります。

</details>

**問3.** リポジトリの実装で、`FindShippableOrders()` が SQL の中に「在庫がある AND 支払済み AND 配送先が国内」という条件を直接埋め込んでいます。この設計の問題点として最も適切なものはどれでしょう？

1. SQL は実行が速いので問題はまったくない
2. 「出荷可能」の判定というビジネスルールが SQL に漏れ、ドメイン層から知識が失われている
3. リポジトリは必ず全件取得してアプリ側で絞るべきである
4. リポジトリにメソッドを追加すること自体が誤りである

<details><summary>答えと解説</summary>

正解: **2**

「出荷可能とは何か」は重要なドメイン知識です。それが SQL の WHERE 句に埋まると、ルールを理解するのに DB クエリを読む必要が生じ、ドメイン層が業務を語らなくなります。リポジトリは集約の出し入れに徹し、判定ロジックはドメイン側に置くのが原則です。性能は別問題ですし、全件取得の強制やメソッド追加の禁止は過剰反応で、論点がずれています。

</details>

**問4.** 「ユビキタス言語の形骸化」というアンチパターンの説明として最も適切なものはどれでしょう？

1. 用語集を一度作ったが、日々の会話やコードでは別の言葉が使われ、言語が実態と乖離している
2. 専門用語が多すぎて新人が理解できない状態
3. 英語の原語を併記していない状態
4. ドメインエキスパートが複数いる状態

<details><summary>答えと解説</summary>

正解: **1**

ユビキタス言語は「会話・ドキュメント・コードすべてで同じ言葉を使い続ける」ことに価値があります。用語集を作っただけで会話やコードが別言語のままなら、言語は飾りになり形骸化します。用語が多い・原語併記がない・エキスパートが複数いる、といった状況はそれ自体が形骸化を意味するわけではありません。要は「決めた言葉が生きて使われ続けているか」が判断軸です。

</details>

**問5.** 貧血ドメインモデルを是正する方向として最も適切なものはどれでしょう？

1. エンティティに public フィールドを増やして自由に書き換えられるようにする
2. 全ての判定をサービス層にさらに集約する
3. ビジネスルールをエンティティや値オブジェクトのメソッドに戻し、オブジェクト自身が不変条件を守るようにする
4. エンティティを削除してマップ(辞書)でデータを持つ

<details><summary>答えと解説</summary>

正解: **3**

処方箋は、サービス層に漏れたルールをエンティティや値オブジェクトのメソッドへ戻し、オブジェクトが自分の不変条件を守る状態にすることです。public フィールドを増やすのは逆に外部からの不正な書き換えを許し、悪化させます。サービス層にさらに集約するのは貧血を進めるだけ、マップで持つのは型安全も振る舞いも失う最悪手です。「正しい状態しか作れない」オブジェクトに近づけるのが正解です。

</details>

## 2. DDDを使わない判断 — 複雑さに見合う道具を選ぶ

### DDD はタダではない

DDD はドメインエキスパートとの対話、モデリング、レイヤー分離など、**先行投資のコストが大きい**手法です。この投資は「ドメインが複雑で、長く変更され続ける」ときに回収できます。逆に言えば、複雑でもない・長生きしない領域に適用すると、ただコードが増えて遅くなるだけです。

### 使わなくてよい場面

| 状況 | 向いている書き方 |
|---|---|
| 単純な CRUD(マスタ管理画面など) | トランザクションスクリプト / 素直な CRUD |
| 一度きりの集計スクリプト・使い捨てツール | 手続き型でさっと書く |
| ビジネスルールがほぼ無い領域 | フレームワークの標準的な書き方 |
| ドメインエキスパートが不在・関われない | まず対話相手を確保する(DDD 以前の問題) |

**トランザクションスクリプトは正当な選択肢**です。ルールが少なければ、手続きが一直線に読める方がむしろ保守しやすいこともあります。

### 全か無かではない — 部分適用

DDD は「全部入れる」か「全部やめる」の二択ではありません。コンテキストごとに濃淡をつけられます。

- **値オブジェクトとユビキタス言語だけ**借りる → 低コストで効果大。`Money` や `EmailAddress` を導入するだけでバグが減る
- **戦略的設計だけ**借りる → 境界とコンテキストマップでシステム全体の見通しを良くし、中身は普通の CRUD
- **コアドメインだけ**フルセット → 差別化する部分に投資を集中し、汎用・支援は薄く作る

💡 コツ: 「この領域は3年後も活発に変更されているか?」「ルールをエキスパートに聞かないと書けないか?」の2つに Yes なら DDD の投資対象です。両方 No なら、素直な CRUD の方が正解です。流行で選ばず、**複雑さに道具を合わせる**のが本道です。

### 確認問題

**問1.** 社内の「お知らせマスタ」を管理する画面を作ります。項目はタイトル・本文・公開日だけで、ビジネスルールはほぼありません。この領域の設計方針として最も適切なものはどれでしょう？

1. 集約・リポジトリ・ドメインサービスをフルセットで導入する
2. ルールがほぼ無いので、素直な CRUD / トランザクションスクリプトで十分である
3. イベントソーシングで全変更履歴を保存する
4. 必ずヘキサゴナルアーキテクチャで5層に分ける

<details><summary>答えと解説</summary>

正解: **2**

ビジネスルールがほぼ無い単純 CRUD は、DDD の投資が回収できない典型です。素直な CRUD やトランザクションスクリプトで書く方が、短く・読みやすく・速く仕上がります。フルセットの集約やイベントソーシング、強制的な多層化は、複雑さに見合わないコストを払うだけで、保守性はむしろ下がります。道具は複雑さに合わせて選ぶのが原則です。

</details>

**問2.** 「DDD は全部入れるか、全部やめるかのどちらかだ」という考え方の評価として最も適切なものはどれでしょう？

1. 正しい。中途半端な適用は必ず失敗する
2. 正しい。DDD はすべてのパターンを同時に使って初めて機能する
3. 誤り。コンテキストごとに濃淡をつけられ、値オブジェクトやユビキタス言語だけの部分適用も有効である
4. 誤り。DDD は戦術的パターンのみを使うべきで戦略的設計は不要である

<details><summary>答えと解説</summary>

正解: **3**

DDD は全か無かではなく、コンテキストごとに適用の濃淡を選べます。値オブジェクトとユビキタス言語だけを借りるだけでも低コストで効果が大きく、コアドメインにフルセット・汎用は薄く、という配分が現実的です。「中途半端は必ず失敗」「全パターン同時でないと機能しない」は誤りで、むしろ一律適用こそ過剰設計を招きます。戦略的設計が不要というのも逆で、境界の設計はシステム全体の見通しに効きます。

</details>

**問3.** あるチームが「複雑な保険料計算ロジックを持つ基幹システム」を新規開発します。ルールは多く、10年は使われ、保険の専門家も協力できます。この領域への DDD 適用判断として最も適切なものはどれでしょう？

1. 使い捨てではないがルールが多いので DDD は避けるべきである
2. ドメインが複雑・長命・エキスパートが協力可能という条件が揃っており、DDD の投資が回収しやすい好適な対象である
3. 計算ロジックはスクリプトで書くべきで DDD は不向きである
4. エキスパートがいる場合はむしろ DDD を使うべきでない

<details><summary>答えと解説</summary>

正解: **2**

ドメインが複雑・長期間変更され続ける・エキスパートと対話できる、という3条件が揃う領域こそ DDD の先行投資が回収できる好適な対象です。ルールが多いことは避ける理由ではなく、むしろモデルで整理する価値がある証拠です。複雑な計算ロジックを素のスクリプトに押し込むと重複と暗黙知化を招きます。エキスパートがいることは障害ではなく、ユビキタス言語を育てる前提条件です。

</details>

**問4.** トランザクションスクリプトという書き方についての評価として最も適切なものはどれでしょう？

1. 常にアンチパターンであり、使ってはいけない
2. ルールが少ない領域では手続きが一直線に読めて保守しやすく、正当な選択肢になりうる
3. DDD を学んだ後は二度と使うべきでない
4. DB のトランザクション分離レベルを指す技術用語である

<details><summary>答えと解説</summary>

正解: **2**

トランザクションスクリプトは、ルールが少ない領域では処理が上から下へ一直線に読め、むしろ保守しやすい正当な選択肢です。「常にアンチパターン」「DDD 後は二度と使わない」は言い過ぎで、DDD はこれを置き換える万能薬ではありません。複雑さに応じて使い分けるものです。なお DB のトランザクション分離レベルとは名前が似ているだけの別概念で、混同はよくあるひっかけです。

</details>

**問5.** 新しい業務システムの開発にあたり、ドメインが複雑であるにもかかわらず、業務を説明できるドメインエキスパートが誰も関与できない状況です。まず取るべき行動として最も適切なものはどれでしょう？

1. エキスパート無しでも開発者だけでユビキタス言語を完成させる
2. DDD を諦めて全てを単純 CRUD で作る
3. 対話できるドメインエキスパート(または業務知識の源)を確保することを優先する。これは DDD 以前の前提条件である
4. とりあえず集約とリポジトリを先に実装する

<details><summary>答えと解説</summary>

正解: **3**

DDD はエキスパートとの対話から知識を引き出してモデルを育てる手法なので、知識の源が無ければ正しいモデルもユビキタス言語も作れません。まず業務を語れる人(または一次情報)を確保するのが前提条件で、これは DDD 以前の課題です。開発者だけで言語を「完成」させると想像で作った誤ったモデルになりがちです。複雑さが本物なら単純 CRUD への逃避も、知識不在のまま集約を先に作るのも、土台を欠いたまま進むことになります。

</details>

## 3. レガシーと組織への段階導入

### ビッグバン書き換えの罠

「レガシーが限界だから全部作り直す」——この**ビッグバン書き換え (big-bang rewrite)** は失敗の定番です。動いている仕様を完全には誰も把握しておらず、移行中は新旧2つを並行保守する地獄が待っています。

### ストラングラーフィグ・パターン

現実的なのは**ストラングラーフィグ・パターン (Strangler Fig)** です。絞め殺しの木が宿主を少しずつ覆っていくように、**新機能を新しいコンテキストで作り、腐敗防止層 (ACL) で旧システムと分離**しながら、機能を一つずつ移していきます。

```
[クライアント] → [ルーティング] ─→ 移行済み機能 → 新コンテキスト(DDD)
                             └→ 未移行機能   → レガシー(ACL経由で連携)
```

旧システムは生かしたまま、価値の高いところから徐々に置き換えるので、いつでも止められ・戻せます。

### 小さく始め、コアから攻める

- **一番複雑で価値のある業務を1つだけ**選んでコアドメインとして切り出す(全領域を一度に DDD 化しない)
- まず**用語の統一**から始める。ユビキタス言語は低コストで効果が出やすい入口
- 読書会・モブモデリング・イベントストーミングでチームの共通理解を作る
- 経営には「DDD は仕様変更に強くなるための投資」と、技術用語を避けて説明する

### モデルは育てるもの

最初から完璧なモデルは作れません。DDD は一度きりの設計ではなく、知識が増えるたびにリファクタリングして**モデルを育て続ける**営みです。

💡 コツ: この講座の次は、Eric Evans『ドメイン駆動設計』(概念の原典)と Vaughn Vernon『実践ドメイン駆動設計』(実装の手引き)を、実プロジェクトで手を動かしながら読むのがおすすめです。本を読むだけでなく、**自分のドメインで小さなコアを1つモデリングしてみる**のが一番の近道です。

### 確認問題

**問1.** 10年もののレガシー基幹システムを DDD で刷新したいチームがあります。最もリスクが低い進め方はどれでしょう？

1. 新機能や価値の高い部分を新コンテキストで作り、ACL で旧システムと分離しながら段階的に移すストラングラーフィグ・パターンを採る
2. 全機能を一度に新システムへ作り直すビッグバン書き換えを行う
3. レガシーには一切手を触れず放置する
4. まずデータベースのテーブルを全て再設計してから考える

<details><summary>答えと解説</summary>

正解: **1**

ストラングラーフィグ・パターンは、新機能を新コンテキストで作り腐敗防止層で旧システムと切り離しながら、価値の高い機能から一つずつ置き換える方法で、いつでも止められ戻せるのが強みです。ビッグバン書き換えは仕様の全把握が不可能で並行保守地獄に陥る定番の失敗です。放置は問題を先送りするだけ、DB 再設計から入るのはテーブル都合にモデルを縛られる悪手で、順序が逆です。

</details>

**問2.** レガシー刷新の第一歩として、チームへの負荷が小さく効果が出やすい取り組みはどれでしょう？

1. 全コンテキストに同時にヘキサゴナルアーキテクチャを導入する
2. まず用語の統一(ユビキタス言語)から始め、会話とコードで同じ言葉を使うようにする
3. イベントソーシングを全面採用する
4. 最初にマイクロサービスへ物理分割する

<details><summary>答えと解説</summary>

正解: **2**

ユビキタス言語の統一は、特別な基盤も大規模な改修も要らず、会話とコードの食い違いによるバグを減らせる低コスト・高効果の入口です。全面的なアーキテクチャ導入やイベントソーシングの全採用は初手としては重く、失敗時の損失も大きくなります。いきなりマイクロサービスへ物理分割するのは、論理境界が固まる前に分けてしまう典型的な早すぎる最適化です。小さく始めるのが鉄則です。

</details>

**問3.** DDD 導入を経営層に説明する際の伝え方として最も適切なものはどれでしょう？

1. 集約・値オブジェクト・ACL といったパターン名を詳細に説明する
2. DDD を入れればサーバー費用が下がると説明する
3. 「仕様変更に強くなり、長期の開発速度を保つための投資」とビジネス価値の言葉で説明する
4. DDD は技術的に高度なので経営には説明しないでおく

<details><summary>答えと解説</summary>

正解: **3**

経営層にはパターン名ではなく、「仕様変更に強くなる」「長期的に開発速度を維持できる」というビジネス価値=投資対効果の言葉で伝えるのが有効です。集約や ACL といった技術用語を並べても意思決定には繋がりません。DDD はインフラ費用の削減策ではないので誤った期待を持たせるべきではなく、説明せずに進めるのは必要な支援や時間を得られなくなるため最も危険です。

</details>

**問4.** DDD におけるドメインモデルの扱い方として最も適切なものはどれでしょう？

1. 最初の設計で完璧なモデルを完成させ、以後は変更しない
2. モデルはドキュメントであり、コードとは別に管理すべきである
3. 一度動いたら二度と触らないのが理想である
4. 知識が増えるたびにリファクタリングで育て続ける継続的な営みである

<details><summary>答えと解説</summary>

正解: **4**

ドメインモデルは、ドメイン知識が深まるたびにリファクタリングして育て続けるものです。最初から完璧なモデルは作れず、使いながら理解が進むからこそ継続的に磨きます。「完成させて以後不変」「一度動いたら触らない」は、知識の成長をコードに反映できず再び陳腐化を招きます。モデルをコードと切り離してドキュメントだけで管理するのも、モデルとコードの一致という DDD の核心に反します。

</details>

**問5.** レガシー刷新でコアドメインを切り出すとき、最初に選ぶ対象として最も適切なものはどれでしょう？

1. 一番複雑で、かつビジネス上の価値が高い中核業務を1つ選ぶ
2. 一番単純で誰でも作れる管理画面
3. 全領域を同時にコアとして切り出す
4. 外部ベンダーに任せている汎用機能(認証や決済など)

<details><summary>答えと解説</summary>

正解: **1**

段階導入では、一番複雑で価値の高い中核業務を1つだけ選び、そこに DDD の力を集中させるのが効果的です。単純な管理画面は DDD の投資が回収できず学びも少なく、全領域の同時着手はビッグバンと同じ失敗を招きます。認証や決済のような汎用サブドメインは買う・任せる対象であって、自前でモデリングに投資すべきコアではありません。差別化を生む中核に資源を集中するのが戦略的設計の考え方です。

</details>
