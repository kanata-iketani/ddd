# 第14章 CQRSとイベントソーシング入門

この章では、書き込みと読み取りを別々のモデルに分ける **CQRS** と、状態の代わりにイベント列を記録する **イベントソーシング (Event Sourcing)** を学びます。L8〜L9 の集約と結果整合性、L10 のドメインイベントが土台になります。どちらも強力ですが代償も大きい道具です。仕組みを理解したうえで、最後の章では「自分のドメインに本当に必要か」を判断する目を養います。

## 1. CQRS — コマンドとクエリの分離

### 基礎の基礎: コマンドとクエリ

システムへの操作は、大きく2種類に分けられます。

| 種類 | 意味 | ECサイトの例 |
|---|---|---|
| **コマンド (Command)** | 状態を変える指示 | 注文を確定する、注文をキャンセルする |
| **クエリ (Query)** | 状態を変えずにデータを返す問い合わせ | 注文一覧を見る、注文の合計を見る |

この章の CQRS は、この2つで使うモデルを分ける考え方です。

### 集約は一覧画面に向かない

ここまで学んだ集約 (Aggregate、L8) は「不変条件を守って安全に更新する」ために設計しました。ところが、この同じモデルで画面表示をまかなおうとすると、とたんに苦しくなります。

たとえば注文一覧画面で「注文番号・顧客名・商品名・合計金額・配送ステータス」を一覧したいとします。これらは注文・顧客・商品・配送という**複数の集約にまたがる**情報です。集約はIDでしか他集約を参照しないルールでした(L9)。素直に実装すると、次の2つのどちらかになります。

- **N+1問題**: 注文の一覧を1回のSQLで取り、そのあと注文1件ごとに顧客・商品・配送を取りにいく。注文が20件なら 1 + 20×3 = 61 回の SQL が走り、画面が遅くなる
- **巨大な JOIN**: JOIN(複数のテーブルを、共通の列で結びつけて1つの表にする SQL)をたくさん重ねた1本の SQL を書く。速度や読みやすさが落ちやすい

JOIN の小さな例です。DB の表が次のように分かれているとします。

| customers.id | customers.name |
|---|---|
| c-1 | 佐藤 |
| c-2 | 鈴木 |

| orders.id | orders.customer_id | orders.total |
|---|---|---|
| o-1 | c-1 | 3000 |
| o-2 | c-2 | 1200 |

| shipments.order_id | shipments.status |
|---|---|
| o-1 | 出荷済み |
| o-2 | 準備中 |

```sql
SELECT o.id, c.name, o.total, s.status
FROM orders o
JOIN customers c ON c.id = o.customer_id   -- 注文の customer_id と顧客の id が同じ行を結ぶ
JOIN shipments s ON s.order_id = o.id      -- 注文の id と配送の order_id が同じ行を結ぶ
ORDER BY o.id
```

実行結果(SQLite で実行):

| id | name | total | status |
|---|---|---|---|
| o-1 | 佐藤 | 3000 | 出荷済み |
| o-2 | 鈴木 | 1200 | 準備中 |

表示のたびに不変条件を守る重いドメインオブジェクトを組み立てるのも無駄です。

### 書き込みモデルと読み取りモデルを分ける

**CQRS (Command Query Responsibility Segregation、コマンドとクエリの責務の分離)** は、この苦しさを「モデルを2つに分ける」ことで解きます。

| | 書き込みモデル (Command) | 読み取りモデル (Query) |
|---|---|---|
| 目的 | 状態を正しく変更する | 画面に素早く表示する |
| 中身 | 集約・不変条件 | 画面に合わせたビュー |
| 正規化 | 正規化して整合性重視 | **非正規化**してよい |
| 例 | `Order.Cancel()` | `order_list_view` テーブル |

- **正規化**: 同じ情報を1か所にだけ持つようにテーブルを分けること。上の customers / orders / shipments のように、顧客名は customers にだけある
- **非正規化**: 読みやすさ・速さのために、あえて同じ情報を複数の場所にコピーして持つこと
- **ビュー**: 画面などで使う形にまとめた表。DB の機能としての VIEW(SELECT 文に名前を付けた仮想の表)を使うことも、普通のテーブルを用意することもある

`order_list_view` は、一覧画面の1行がそのまま1行になったテーブルです。

| order_id | customer_name | total | ship_status |
|---|---|---|---|
| o-1 | 佐藤 | 3000 | 出荷済み |
| o-2 | 鈴木 | 1200 | 準備中 |

一覧画面は `SELECT * FROM order_list_view` の1回で済みます。顧客名は customers にもあるので非正規化ですが、ここは読むだけなので問題になりません。

書き込み側は今まで通り集約で不変条件を守り、読み取り側は画面専用の「読むだけ」の構造(非正規化済みのビューや専用テーブル)を用意します。読み取りモデルにビジネスルールは要りません。表示に必要な形で持てばよいのです。

### 段階的に導入する

CQRSは「いきなりDBを2つ」ではありません。複雑さに応じて段階を選べます。

1. **同一DBで分離**: 書き込みは集約経由、読み取りは専用のクエリ(上のような JOIN の SQL やビュー)で直接取得する。最も軽量で、多くの場合これで十分です。
2. **読み取り専用レプリカ**: 書き込み用 DB の内容を自動でコピーし続ける読み取り専用の DB(リードレプリカ)を用意し、参照の負荷をそちらに逃がす。
3. **専用の読み取りストア**: 書き込みDBとは別に、検索に最適化したストア(非正規化テーブルや検索エンジン=全文検索などに特化したデータの置き場)へ、ドメインイベント(L10)を使って書き写す。この書き写しを**投影 (projection)** と呼びます。例: 「注文が確定した」イベントを受けて order_list_view に1行足す。

💡 コツ: 段階3では書き込みの結果が読み取りに反映されるまでに**遅延**が生じます(L9 で見た結果整合性)。「注文直後に一覧へ戻ると自分の注文がまだ出ない」といったUX(利用者の体験)の問題が起こり得るので、投稿直後だけ書き込みモデルから読む、楽観的にUIへ即時反映する(サーバーの反映を待たずに、画面に先に表示しておく)などの工夫で吸収します。この遅延を許せるかはドメイン次第です。

### 確認問題

**問1.** あるECの注文一覧画面が、注文・顧客・商品・配送の4集約にまたがる情報を表示するためにN+1問題で重くなっています。CQRSの考え方として最も適切な対応はどれでしょうか。

1. 注文集約の中に顧客・商品・配送の実体を全部保持させ、1回のロードで表示できるようにする
2. 表示専用に非正規化した読み取りモデル(ビューや専用テーブル)を用意し、一覧はそこから取得する
3. 注文集約の不変条件を一部ゆるめて、表示に必要なフィールドを自由に書き換えられるようにする
4. 一覧画面をやめて、1件ずつの詳細画面だけにする

<details><summary>答えと解説</summary>

正解: **2**

正解は、表示専用の非正規化した読み取りモデルを用意する案です。CQRSは書き込み(集約・不変条件)と読み取り(画面最適化のビュー)を分けることでN+1やJOIN地獄を解消します。他集約の実体を集約内に抱え込む案は、IDで参照する集約設計の原則を壊し、巨大集約・ロック競合を招きます。不変条件をゆるめる案は、表示の都合で書き込みモデルの安全性を犠牲にする本末転倒です。一覧をやめる案は、技術都合でビジネス要件を削っており不適切です。

</details>

**問2.** CQRSにおける「読み取りモデル」の性質として正しいものはどれでしょうか。

1. 読み取りモデルも必ず正規化し、書き込みモデルと同じ不変条件を持たせる
2. 読み取りモデルはビジネスルールの検証を担当し、コマンドの可否を判断する
3. 読み取りモデルは画面に合わせて非正規化してよく、ビジネスルールは持たない
4. 読み取りモデルは書き込みモデルより先に設計しなければならない

<details><summary>答えと解説</summary>

正解: **3**

正解は、画面に合わせて非正規化してよくビジネスルールを持たないという性質です。読み取りモデルは「表示を速くする」ことだけが目的で、重複を許し表示に最適な形で持ちます。正規化や不変条件を強いる案は、読み取りモデルを書き込みモデルと混同しており、CQRSで分けた意味が失われます。ビジネスルールの検証やコマンドの可否判断は書き込みモデル(集約)の仕事であり、読み取りモデルの責務ではありません。設計順序に決まりはなく、むしろ不変条件を守る書き込みモデルを軸に考えるのが基本です。

</details>

**問3.** 小規模な社内管理ツールで、参照も更新もさほど多くありません。開発者は2名です。「CQRSらしく最初から読み取り専用の別DBを立てて投影パイプラインを組もう」という提案への評価として最も適切なものはどれでしょうか。

1. CQRSはモデルを分ける考え方であり、まずは同一DBで読み取り専用クエリを分けるだけでも実践できる。別DBは複雑さに見合わないので段階を踏むべき
2. CQRSを名乗る以上、読み取り専用の別DBと投影パイプラインは必須なので提案通り進めるべき
3. 小規模ならCQRSの概念自体が一切使えないので、読み書きを完全に1つのモデルに混ぜるべき
4. 別DBを立てるなら、ついでにイベントソーシングも必ずセットで導入しなければ整合しない

<details><summary>答えと解説</summary>

正解: **1**

正解は、まず同一DBで読み取りクエリを分けるだけでよく別DBは段階を踏むべき、という評価です。CQRSは「モデルを分ける」考え方で、同一DB内で書き込みは集約経由・読み取りは専用クエリ、という軽量な形から始められます。小規模で負荷も低いのに最初から別DBと投影パイプラインを組むのは、運用と結果整合性のコストが複雑さに見合いません。別DBや投影が必須という理解は誤りで、段階1でも立派なCQRSです。概念が一切使えないというのも誤り。イベントソーシングは別の道具で、CQRSに必須ではありません。

</details>

**問4.** CQRSで専用の読み取りストアへ投影する構成にしたところ、「注文直後に一覧へ戻ると、自分の注文がまだ表示されない」という声が出ました。この遅延の性質と対応として最も適切なものはどれでしょうか。

1. 書き込みと読み取りが同一トランザクションでないのはバグなので、投影を同期化して常に即時反映にすべき
2. これは結果整合性による遅延であり、投稿直後だけ書き込みモデルから読む・UIに楽観的に即時反映するなどで吸収するのが現実的
3. 読み取りストアを使う以上この遅延は絶対に消せないので、一覧画面の提供自体を諦める
4. 遅延が出たら読み取りストアを捨て、すべて書き込みモデルから読むように戻すしかない

<details><summary>答えと解説</summary>

正解: **2**

正解は、結果整合性による遅延と理解し投稿直後だけ書き込みモデルから読む等で吸収する案です。専用の読み取りストアへの投影は非同期なので、わずかな反映遅れは仕様であってバグではありません。すべて同期化すると分離の利点(負荷分散・画面最適化)が失われます。遅延を理由に一覧を諦めるのは要件を捨てており不適切。常に書き込みモデルから読むよう全面的に戻すのは段階を1つ下げる判断で、ピンポイントの工夫で足りる場面では過剰です。許容できる遅延量はドメインに応じて判断します。

</details>

**問5.** CQRSを「コマンドとクエリの分離」と説明するとき、コマンド側とクエリ側の責務の分け方として正しいものはどれでしょうか。

1. コマンドもクエリも同じモデルで処理し、名前だけ分けて呼ぶのがCQRSである
2. コマンド側は状態を変更し不変条件を守る、クエリ側は状態を変えずに表示用データを返す
3. クエリ側が状態を変更し、コマンド側は読み取り専用で参照するのがCQRSである
4. コマンドは必ずイベントソーシングで、クエリは必ずSQLで実装しなければならない

<details><summary>答えと解説</summary>

正解: **2**

正解は、コマンド側が状態変更と不変条件、クエリ側が状態を変えない表示用データ、という分け方です。CQRSは「変更(Command)」と「参照(Query)」の責務を別モデルに分離する考え方です。同じモデルで名前だけ分けるのは分離になっておらず、CQRSの利点が得られません。クエリ側が状態を変更するのは責務が逆で、クエリは副作用を持たないのが原則です。実装手段(イベントソーシングやSQL)は自由であり、特定の技術を強制するものではありません。

</details>

**問6.** ECサイトの次の操作のうち、CQRS でいう「クエリ」に当たるものはどれでしょう?

1. 注文をキャンセルする
2. カートの商品を注文として確定する
3. 配送先住所を変更する
4. 購入履歴の一覧を表示する

<details><summary>答えと解説</summary>

正解: **4**

クエリは状態を変えずにデータを返す問い合わせなので、購入履歴の一覧表示が当たります。キャンセル・確定・住所変更はどれも注文や会員の状態を変えるので、コマンドです。CQRS では、コマンドは集約が不変条件を守りながら処理し、クエリは画面向けの読み取りモデルから返す、と分けます。

</details>

## 2. イベントソーシング — 状態ではなく履歴を保存する

### 現在の状態ではなく、起きたことを記録する

通常の**CRUD**(作成・読み取り・更新・削除をそのまま行う書き方)では、テーブルに**現在の状態**だけを保存します。銀行口座なら `balance = 5000` という1行です。入金や出金のたびにこの値を上書きするので、**どういう経緯で5000円になったのか**は残りません。

**イベントソーシング (Event Sourcing)** は発想を逆転させます。状態そのものではなく、**起きた出来事(L10 で見たドメインイベント)の列**を保存します。イベントを保存する場所を**イベントストア**と呼び、イベントは後ろに追記するだけで、上書きはしません。

```text
口座#42 のイベントストア
 1. 口座開設された        (2024-01-05)
 2. 入金された  +10000円  (2024-01-06)
 3. 出金された   -3000円  (2024-01-10)
 4. 出金された   -2000円  (2024-01-12)
```

同じ口座を2つの方式で保存したときの違いです。

| 方式 | 保存されているもの |
|---|---|
| 普通の CRUD | `balance = 5000` の1行だけ |
| イベントソーシング | 上の4件のイベント(残高そのものは保存しない) |

### 現在状態はリプレイで再構築する

「今の残高は?」と聞かれたら、イベントを最初から順に**再生 (replay)** して計算します。10000 − 3000 − 2000 = 5000円。現在状態はイベント列から**導出される結果**であって、保存された真実はイベントの方です。

イベントが増えると毎回全再生は重くなるので、途中結果を保存しておく **スナップショット (snapshot)** を併用します(例: 100件ごとに残高を記録し、以降だけ再生)。

### 動かして確かめる

再生とスナップショットを Go で書いた完全版です。

```go
package main

import "fmt"

// 起きた出来事(イベント)を1件ずつ表す
type Event struct {
	Type   string
	Amount int
}

// イベントを先頭から順に再生して残高を計算する
func Replay(start int, events []Event) int {
	balance := start
	for _, e := range events {
		switch e.Type {
		case "入金された":
			balance += e.Amount
		case "出金された":
			balance -= e.Amount
		}
	}
	return balance
}

func main() {
	events := []Event{
		{Type: "口座開設された"},
		{Type: "入金された", Amount: 10000},
		{Type: "出金された", Amount: 3000},
		{Type: "出金された", Amount: 2000},
	}
	fmt.Println("現在の残高:", Replay(0, events))
	fmt.Println("2件目までの残高:", Replay(0, events[:2]))

	snapshot := Replay(0, events[:3]) // 3件目までの結果を保存しておく
	fmt.Println("スナップショット(3件目まで):", snapshot)
	fmt.Println("スナップショット+残りだけ再生:", Replay(snapshot, events[3:]))
}
```

実行結果:

```text
現在の残高: 5000
2件目までの残高: 10000
スナップショット(3件目まで): 7000
スナップショット+残りだけ再生: 5000
```

| 部分 | 意味 |
|---|---|
| `type Event struct { Type string; Amount int }` | イベント1件。種類と金額を持つ |
| `func Replay(start int, events []Event) int` | 開始残高とイベントの列を受け取り、再生後の残高を返す |
| `for _, e := range events` | events を先頭から1件ずつ取り出して e に入れる。`_` は使わない番号を捨てる書き方(Python の `for e in events:` に当たる) |
| `switch e.Type { case ...: }` | e.Type の値によって処理を分ける。どの case にも当たらない「口座開設された」は何もしない |
| `balance += e.Amount` | `balance = balance + e.Amount` の短い書き方 |
| `events[:2]` | 先頭から2件(0番目と1番目)だけを取り出したスライス。Python のリストの `[:2]` と同じ |
| `events[3:]` | 3番目(4件目)から最後まで |
| `Replay(snapshot, events[3:])` | スナップショットの 7000 から始めて、4件目だけを再生する。全件再生と同じ 5000 になる |

`Replay(0, events[:2])` のように途中までで止めれば、**過去の任意の時点の状態**(ここでは 2024-01-06 時点の残高 10000)も再現できます。

### 利点と難点

| 利点 | 難点 |
|---|---|
| **監査ログが自然に手に入る**(履歴そのものが真実) | 「現在の状態」を得るのに再生が要る |
| **過去の任意時点**を再現できる | **イベントスキーマの進化**が難しい(古いイベントは消せない) |
| あとから新しい読み取りビューを作れる | 学習・運用・デバッグのコストが高い |

**監査ログ**は「誰が・いつ・何をしたか」を後から確かめるための記録です。

最大の難点は**スキーマの進化**です。スキーマはここでは「イベントが持つ項目の構成」です。いったん書いたイベントは歴史的事実なので、原則あとから変更・削除できません。項目を足す・意味が変わるといった変更には、バージョニングやアップキャスティング(古いイベントを新形式に変換して読む)といった工夫が要ります。

| | 「入金された」の項目 |
|---|---|
| 版1(昔のイベント) | 金額 |
| 版2(今のイベント) | 金額、通貨 |

版を記録しておき(バージョニング)、版1を読むときは「通貨は円」と補って版2の形にしてから使います(アップキャスティング)。保存済みの版1のイベント自体は書き換えません。

### CQRSとの関係

イベントソーシングで保存されるのはイベント列なので、そのままでは一覧画面に使えません。そこで**イベントを読み取りモデルへ投影 (projection)** します。これは ch01 で見たCQRSそのものです。たとえば「入金された」「出金された」が届くたびに、入出金一覧の表に1行ずつ足していきます。

💡 コツ: イベントソーシングは**ほぼ常にCQRSとセット**で使われます(書き込み=イベントストア、読み取り=投影されたビュー)。一方、CQRSはイベントソーシングなしでも成立します。「ES ⇒ CQRS」は成り立っても「CQRS ⇒ ES」ではない、という非対称を押さえておきましょう(ES はイベントソーシングの略、⇒ は「〜なら〜」)。

### 確認問題

**問1.** イベントソーシングが「状態ではなくイベント列を保存する」とはどういうことか、最も正確に説明しているものはどれでしょうか。

1. 起きた出来事を順に記録し、現在の状態はそのイベント列を再生して導出する
2. 現在の状態のみをテーブルに保存し、変更のたびに上書きする
3. イベントをログファイルに出力するが、真実は状態テーブルの方に持つ
4. 状態とイベントの両方を常に二重に保存し、どちらを正にするかは都度決める

<details><summary>答えと解説</summary>

正解: **1**

正解は、起きた出来事を順に記録し現在状態はイベント再生で導出する、という説明です。イベントソーシングではイベント列こそが保存された真実で、現在状態はそこから計算される結果です。現在状態を上書き保存するのは通常のCRUDであり、イベントソーシングではありません。イベントを単なるログとして出し真実は状態側に置く構成は、普通のCRUD+監査ログであってイベントソーシングとは呼びません。状態とイベントを常に二重保存してどちらが正か都度決めるのは整合性が崩れやすく、イベントソーシングの考え方とも異なります。

</details>

**問2.** イベントソーシングで現在状態を得るための再生(リプレイ)が、イベント件数の増加で重くなってきました。標準的な対処はどれでしょうか。

1. 古いイベントを削除して件数を減らす
2. 途中結果を保存するスナップショットを使い、そこから先だけ再生する
3. 現在状態を別テーブルに上書き保存し、イベントストアを捨てる
4. 再生が重いのは設計ミスなので、イベントソーシングをやめて必ずCRUDに戻す

<details><summary>答えと解説</summary>

正解: **2**

正解は、スナップショットを使いそこから先だけ再生する対処です。途中時点の状態を保存しておけば、全履歴を毎回再生せずに済みます。古いイベントの削除は、監査性と過去再現性というイベントソーシング最大の利点を壊すので不適切です。イベントストアを捨てて状態を上書きするのは、イベントソーシングをやめることと同義で、履歴という真実を失います。再生が重い=設計ミスと短絡してCRUDへ戻すのは、スナップショットという定石を知らない判断で、採用理由(監査・再現)が本当に必要なら性急です。

</details>

**問3.** イベントソーシングの難点として特に注意すべき「イベントスキーマの進化」とは、どのような問題でしょうか。

1. 読み取りモデルのテーブル定義を変更できないこと
2. イベントの命名を過去形にしなければならないという制約のこと
3. いったん保存したイベントは歴史的事実なので変更・削除しづらく、形式変更にバージョニングや変換が要ること
4. スナップショットを一度作ると二度と作り直せないこと

<details><summary>答えと解説</summary>

正解: **3**

正解は、保存済みイベントは事実なので変更・削除しづらく形式変更に工夫が要る、という問題です。古いイベントは消せない前提なので、項目追加や意味変更にはバージョニングやアップキャスティング(古い形式を新形式へ変換して読む)が必要になります。読み取りモデルのテーブルはむしろ作り直し可能で、問題の本質ではありません。過去形の命名は推奨ではありますが「進化が難しい」という難点とは別の話です。スナップショットは作り直せるので、二度と作れないという説明は誤りです。

</details>

**問4.** イベントソーシング(ES)とCQRSの関係について、正しい理解はどれでしょうか。

1. CQRSを使うなら必ずイベントソーシングも使わなければならない
2. イベントソーシングを使えば読み取りモデルは不要になり、一覧画面もイベントストアから直接引ける
3. イベントソーシングとCQRSは排他的で、同時には使えない
4. イベントソーシングは保存がイベント列なので、表示にはCQRSの読み取りモデルへの投影がほぼ必須になる

<details><summary>答えと解説</summary>

正解: **4**

正解は、イベントソーシングは表示のためにCQRSの読み取りモデルへの投影がほぼ必須、という理解です。イベント列はそのままでは一覧表示に向かないため、投影してビューを作ります。CQRSはイベントソーシングなしでも成立するので「CQRSなら必ずES」は誤りです(非対称な関係)。両者は排他どころか、むしろセットで使われる補完関係です。イベントストアから一覧を直接引くのは再生コストが高く非現実的で、読み取りモデルが不要になるという理解は誤りです。

</details>

**問5.** 次のうち、イベントソーシングの採用が最も噛み合いやすいドメインはどれでしょうか。

1. 入出金や残高のように、履歴そのものが業務価値を持ち監査も重視される会計・取引ドメイン
2. 設定値を保存するだけの、履歴に関心のない社内設定画面
3. 一度書いたら読むだけの、更新がほとんど発生しない静的なマスタ
4. 画面表示の高速化だけが唯一の関心事であるケース

<details><summary>答えと解説</summary>

正解: **1**

正解は、履歴そのものが価値を持ち監査も重視される会計・取引ドメインです。入出金の履歴が真実であり過去再現や監査が重要な領域は、イベントソーシングの利点がコストを上回りやすい典型です。履歴に関心のない設定画面や、更新がほぼない静的マスタは、イベント列を管理する複雑さに見合いません。表示高速化だけが関心ならCQRSの読み取りモデルで足り、イベントソーシングまでは不要です。採用は「履歴が業務価値を持つか」で判断します。

</details>

**問6.** ある口座のイベントストアに「口座開設された」「入金された +8000円」「出金された -1500円」「入金された +500円」の4件が順に入っています。開始残高 0 円から再生した現在の残高はいくらでしょう?

1. 8000円
2. 7000円
3. 10000円

<details><summary>答えと解説</summary>

正解: **2**

</details>

## 3. 採用判断 — 複雑さに見合うか

### まず「払うコスト」を直視する

CQRSやイベントソーシングは、記事やカンファレンスで華やかに語られます。しかし実務での導入可否は、**利点ではなくコスト**から考えるのが安全です。

- **学習コスト**: チーム全員が結果整合性(L9)・投影・リプレイ(ch01・ch02)を理解する必要がある
- **運用コスト**: 投影パイプライン(イベントを読み取りモデルへ書き写し続ける仕組み)、イベントストア、スナップショットが止まっていないかを見張る手間
- **デバッグの難しさ**: 「なぜこの画面がこの値なのか」が、投影の遅延やイベント順序に依存して追いにくい
- **UXへの影響**: 結果整合性による「書いた直後に読めない」をUIで吸収し続ける負担

### 採用すべきサイン / やめるべきサイン

| 採用を後押しするサイン | 見送りを示すサイン |
|---|---|
| 読み取りと書き込みで**負荷や形が大きく違う** | 単純なCRUDで足りる |
| **監査要件**が強い(誰がいつ何をしたかが業務価値) | 小規模チーム・短命なツール(すぐ使わなくなる道具) |
| ドメインが**本質的にイベント的**(会計・取引・在庫移動) | ドメインエキスパートが履歴に関心がない |
| 既に結果整合性を受け入れている | 即時一貫(書いた瞬間に、どこから読んでも最新が見える状態)が強く求められUXが厳しい |

「本質的にイベント的」とは、業務の人が普段から「入金があった」「出庫した」のように出来事の単位で話し、その記録自体を大事にしている、という意味です。

### 全部か無か、ではない

CQRS/ESは**部分適用**できます。システム全体ではなく、**1つの境界づけられたコンテキスト(L3)だけ**に導入するのが定石です。たとえばECで「会計・取引」コンテキストだけイベントソーシングにし、「商品カタログ」は普通のCRUDのまま、という使い分けができます。戦略的設計(L5 で見たコア/支援/汎用)の判断がここでも効きます。

### 「履歴テーブル+普通のCRUD」で足りないか

「過去を追いたい」だけが動機なら、多くの場合**履歴テーブル(監査ログ)を併設した普通のCRUD**で十分です。たとえば会員の住所変更なら、次の2つの表を持ちます。

members(現在の状態。これが正)

| id | address |
|---|---|
| m-1 | 大阪府 |

member_history(変更のたびに1行足す記録)

| member_id | changed_at | changed_by | before | after |
|---|---|---|---|---|
| m-1 | 2024-03-01 | 担当者A | 東京都 | 神奈川県 |
| m-1 | 2024-08-15 | 本人 | 神奈川県 | 大阪府 |

現在の住所は members を見ればすぐ分かり、履歴は「おまけの記録」として残ります。これはイベントソーシングよりずっと安く、スキーマ進化の苦しみもありません。イベントソーシングが本当に要るのは、履歴が「おまけの記録」ではなく「状態を導く唯一の真実」である場合に限られます。

💡 コツ: 流行や「モダンだから」で選ばないこと。DDDの本道は、**自分のドメインの複雑さに合う道具を選ぶ**ことです。CQRS/ESは強力な専用工具であって、すべての釘に使うハンマーではありません。

### 確認問題

**問1.** 新しいプロジェクトで「最近の事例でよく見るし、モダンだからイベントソーシングで作ろう」という提案が出ました。DDDの観点から最も適切な評価はどれでしょうか。

1. 採用はドメインの複雑さと要件(監査・負荷・イベント的な性質)で判断すべきで、流行を理由にするのは不適切
2. モダンな手法を使うこと自体が目的として正当なので、提案通り進めるべき
3. イベントソーシングは常に優れているので、どんなドメインでもデフォルトで選ぶべき
4. 新規なら必ずイベントソーシング、既存改修なら必ずCRUD、と一律に決めるべき

<details><summary>答えと解説</summary>

正解: **1**

正解は、ドメインの複雑さと要件で判断すべきで流行を理由にするのは不適切、という評価です。DDDの本道は自分のドメインに合う道具を選ぶことで、手法の目新しさは採用根拠になりません。モダンであること自体を目的化するのは手段と目的の取り違えです。どんなドメインでもデフォルトで選ぶべき、という主張はコスト(学習・運用・デバッグ)を無視しています。新規か改修かで一律に決めるのも、ドメインの性質を見ない機械的な判断で誤りです。

</details>

**問2.** ある業務で「過去にいつ誰がどう変更したかを追えるようにしたい」という要件があります。更新頻度は低く、現在状態の整合性はそれほど複雑ではありません。最も費用対効果の高い選択はどれでしょうか。

1. 全面的にイベントソーシングを導入し、状態をすべてイベントから再構築する
2. 普通のCRUDに履歴テーブル(監査ログ)を併設し、変更を記録する
3. CQRSで読み取り専用の別DBを立て、投影パイプラインを常時運用する
4. 要件を満たす手段がイベントソーシングしかないので、コストは無視して導入する

<details><summary>答えと解説</summary>

正解: **2**

正解は、普通のCRUDに履歴テーブルを併設する選択です。「過去を追いたい」だけが動機で状態も複雑でないなら、監査ログ付きCRUDが最も安く、スキーマ進化の苦しみもありません。全面イベントソーシングは、履歴が状態を導く唯一の真実でなければ過剰で、学習・運用コストが見合いません。読み取り専用の別DBと投影の常時運用も、この軽い要件には重すぎます。イベントソーシングしか手段がないというのは誤りで、履歴テーブルという安価な代替があります。

</details>

**問3.** 大規模ECで、会計・取引コンテキストは監査と履歴が重要な一方、商品カタログは単純な登録・編集が中心です。アーキテクチャ方針として最も適切なものはどれでしょうか。

1. システム全体で統一すべきなので、カタログも含め全コンテキストをイベントソーシングにする
2. 一貫性のため全コンテキストを単純CRUDに統一し、会計の監査要件は諦める
3. 会計・取引コンテキストにイベントソーシング/CQRSを部分適用し、カタログは普通のCRUDのままにする
4. コンテキストごとに手法を変えると混乱するので、迷ったら全体を一番複雑な手法に合わせる

<details><summary>答えと解説</summary>

正解: **3**

正解は、会計・取引にだけ部分適用しカタログはCRUDのままにする方針です。CQRS/ESは境界づけられたコンテキスト単位で部分適用でき、要件の重いところだけに導入するのが定石です。カタログまで巻き込む全体統一は、単純な領域に不要な複雑さを押し付けます。逆に全体をCRUDに統一して会計の監査要件を諦めるのは、本当に必要な要件を技術都合で捨てており不適切です。迷ったら全体を最も複雑な手法に合わせる、というのはコストを最大化する最悪の方針です。

</details>

**問4.** CQRS/イベントソーシングを導入した結果、チームで「この一覧画面の値がなぜこうなるのか追えない」という声が増えました。この現象が示すものとして最も適切なものはどれでしょうか。

1. この種の分かりにくさは発生し得ないので、報告は勘違いである
2. 単なる実装バグなので、CQRS/ESの構造自体には何のコストもない
3. 読み取りモデルを廃止して集約から直接読めば、あらゆる複雑さが消える
4. 投影の遅延やイベント順序に起因するデバッグの難しさという、CQRS/ESが本来払うコストが顕在化している

<details><summary>答えと解説</summary>

正解: **4**

正解は、投影の遅延やイベント順序に起因するデバッグの難しさというコストが顕在化している、という理解です。CQRS/ESは「なぜこの値か」が投影のタイミングやイベントの並びに依存し、追跡が難しくなる固有のコストを持ちます。これを単なるバグと片付けるのは、構造的コストの存在を見落としています。読み取りモデルを廃止して集約から直接読めばすべて解決する、というのは分離の利点を捨てる極論で、あらゆる複雑さが消えるわけでもありません。この分かりにくさは実在する現象であり、報告を勘違いとするのは誤りです。

</details>

**問5.** CQRSとイベントソーシングの採用判断について、総合的に正しい姿勢はどれでしょうか。

1. 強力だが代償も大きい専用の道具であり、ドメインの複雑さと要件に見合うコンテキストにだけ選択的に使う
2. 両者はセットで全システムに一律導入するのが最も安全である
3. 一度学んだら、以降のあらゆるプロジェクトのデフォルトにすべきである
4. CQRSとイベントソーシングは必ず同時に採用するか、同時に見送るかのどちらかしかない

<details><summary>答えと解説</summary>

正解: **1**

正解は、強力だが代償も大きい専用の道具でありドメインと要件に見合うコンテキストにだけ選択的に使う、という姿勢です。これはDDD全体を貫く「複雑さに見合う道具を選ぶ」考え方の一例です。全システムへの一律導入やデフォルト化は、単純な領域に不要なコストを課します。CQRSはイベントソーシングなしでも成立し、必ず同時採用・同時見送りというわけではありません(ESはCQRSを伴いやすいが逆は必須でない)。選択的・部分的に使うのが実務の定石です。

</details>
