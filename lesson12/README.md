# 第12章 アプリケーションサービスとレイヤー分離

ドメインモデルを作っても、それを呼び出す側が無秩序ではルールは守れません。この章では、ユースケースの進行役であるアプリケーションサービスと、4層の責務分担・依存の向き、そして境界でのデータ変換とバリデーションの置き場所を学びます。「この処理はどの層に置くべきか」を即答できるようになるのがゴールです。

## 1. アプリケーションサービス — ユースケースの進行役

### アプリケーションサービスとは

アプリケーションサービス (Application Service) は、**ユースケースの進行役**です。「注文する」「会員を退会させる」といったユースケース1つにつき1メソッドを持ち、処理の流れを取り仕切ります。典型的な流れは次の4ステップです。

1. リポジトリから集約を取得する
2. 集約(ドメインオブジェクト)のメソッドを呼ぶ — **ビジネスルールはここに任せる**
3. リポジトリで保存する
4. 必要ならドメインイベントを発行する

```go
type PlaceOrderUseCase struct {
    orders OrderRepository // インターフェース(ドメイン層で定義)
    events EventPublisher
}

func (u *PlaceOrderUseCase) Execute(ctx context.Context, cmd PlaceOrderCommand) error {
    order, err := u.orders.Find(ctx, cmd.OrderID)
    if err != nil {
        return err
    }
    if err := order.Place(cmd.PaymentMethod); err != nil { // ルールは集約が判断
        return err
    }
    if err := u.orders.Save(ctx, order); err != nil {
        return err
    }
    return u.events.Publish(ctx, order.PullEvents()...)
}
```

### 薄く保つ (keep it thin)

アプリケーションサービスに `if order.Total > 10000 { 割引... }` のような**ビジネスルールを書き始めたら、それはドメイン層へ移すサイン**です。ルールがユースケースごとに重複し、ドメインモデルが貧血化していきます。アプリケーションサービスは「進行表の読み上げ係」であって、判断はしません。

一方で**トランザクションの開始とコミットはアプリケーションサービスの仕事**です。「どこからどこまでを1つの作業とするか」はユースケースの関心事だからです。

### ドメインサービスとの違い

| | アプリケーションサービス | ドメインサービス |
|---|---|---|
| 関心 | 業務の進行(ユースケース) | ドメインの知識・計算 |
| 層 | アプリケーション層 | ドメイン層 |
| 例 | 注文確定の一連の流れ | 送料の算定ルール |

💡 コツ: アプリケーションサービスのメソッドを読んだとき、**業務マニュアルの目次のように読める**のが理想です。詳細が読めてしまったら書きすぎです。

### 確認問題

**問1.** アプリケーションサービス (Application Service) の役割として最も適切なものはどれでしょう？

1. ビジネスルールを一元的に実装し、エンティティからロジックを引き受ける
2. SQLを組み立てて集約をデータベースに保存する
3. リポジトリから集約を取得し、ドメインのメソッドに処理を委ね、結果を保存するユースケースの進行役を務める
4. HTTPリクエストのJSONを解析してバリデーションする

<details><summary>答えと解説</summary>

正解: **3**

アプリケーションサービスは「取得→ドメインに委譲→保存(→イベント発行)」という進行役に徹します。ビジネスルールを引き受けるのは逆で、ルールはエンティティや値オブジェクト、ドメインサービスに置きます(1つ目の選択肢はドメインモデル貧血症への道です)。SQLの組み立てはインフラストラクチャ層のリポジトリ実装、JSONの解析はプレゼンテーション層の仕事です。「進行はするが判断はしない」がアプリケーションサービスの合言葉です。

</details>

**問2.** ECサイトの注文確定ユースケースで、「合計金額が1万円以上なら送料無料にする」という判定を PlaceOrderUseCase のメソッド内に if 文で直接書きました。DDDの観点からの評価として最も適切なものはどれでしょう？

1. 送料無料はビジネスルールなので、ドメイン層(集約のメソッドやドメインサービス)に移すべきである
2. ユースケースの一部なのでアプリケーションサービスに書くのが正しい
3. 判定はデータベースのトリガーに移すべきである
4. プレゼンテーション層で判定して結果を渡すべきである

<details><summary>答えと解説</summary>

正解: **1**

「1万円以上なら送料無料」はドメインの知識(ビジネスルール)そのものです。アプリケーションサービスに書くと、別のユースケース(カート画面の送料表示、管理画面の再計算など)で同じ if 文が重複し、ルール変更時に修正漏れが起きます。DBトリガーはルールをコードから見えない場所に隠してしまい、プレゼンテーション層に置くと入口ごとにルールが散らばります。ひっかけ: 「ユースケースの中で使うルール」と「ユースケースの進行」は別物です。

</details>

**問3.** トランザクションの開始・コミットを置く場所として、DDDで最も一般的に推奨されるのはどこでしょう？

1. エンティティのメソッド内
2. リポジトリの各メソッド内
3. プレゼンテーション層のハンドラ内
4. アプリケーションサービスのユースケースメソッド内

<details><summary>答えと解説</summary>

正解: **4**

「どこからどこまでを1つの作業単位とするか」はユースケースの関心事なので、アプリケーションサービスがトランザクション境界を管理します。エンティティがトランザクションを知るとドメイン層がインフラに依存してしまいます。リポジトリの各メソッド内で完結させると、複数の操作を1トランザクションにまとめられません。プレゼンテーション層に置くと、同じユースケースを別の入口(バッチ、CLI)から呼んだときにトランザクション管理が重複・漏れします。

</details>

**問4.** アプリケーションサービスとドメインサービスの違いの説明として正しいものはどれでしょう？

1. アプリケーションサービスはユースケースの進行を担い、ドメインサービスはエンティティにも値オブジェクトにも置けないドメインの知識を担う
2. どちらもドメイン層に属し、粒度だけが違う
3. アプリケーションサービスはドメインの計算を行い、ドメインサービスはトランザクションを管理する
4. ドメインサービスはアプリケーションサービスの下請けとしてDBアクセスを行う

<details><summary>答えと解説</summary>

正解: **1**

アプリケーションサービスは「業務の進行(アプリケーション層)」、ドメインサービスは「ドメインの知識(ドメイン層)」と、属する層も関心も異なります。役割が逆になっている説明(アプリ側が計算・ドメイン側がトランザクション)はひっかけの定番です。DBアクセスの実装はインフラストラクチャ層のリポジトリの仕事であり、ドメインサービスが直接DBを触ることはありません。

</details>

**問5.** アプリケーションサービスのコードが100行を超えて膨らんできました。最初に疑うべきこととして最も適切なものはどれでしょう？

1. メソッドを private 関数に分割して行数を減らす
2. ビジネスルール(判断ロジック)が紛れ込んでいないかを確認し、あればドメイン層へ移す
3. 処理をすべてドメインサービスに移動する
4. ユースケースを統合して数を減らす

<details><summary>答えと解説</summary>

正解: **2**

アプリケーションサービスが太る最大の原因は、ドメインに置くべき判断ロジックの漏れ込みです。まず「これはルールか、進行か」を仕分けし、ルールを集約・値オブジェクト・ドメインサービスへ移します。private 関数への分割は見た目の整理にしかならず、責務の混在は解決しません。「すべてをドメインサービスへ」は、本来エンティティに置くべきロジックまで移してしまい貧血モデルを招きます。ユースケースの統合は逆に1メソッドをさらに太らせます。

</details>

## 2. レイヤードアーキテクチャ — 依存はドメインに向ける

### 4つの層と責務

DDDの文脈でよく使われるレイヤードアーキテクチャ (Layered Architecture) は、次の4層です。

| 層 | 責務 | 置くもの |
|---|---|---|
| プレゼンテーション | 入出力(HTTP/CLI/画面) | ハンドラ、DTO、形式チェック |
| アプリケーション | ユースケースの進行 | アプリケーションサービス、トランザクション |
| ドメイン | ビジネスルールとモデル | エンティティ、値オブジェクト、集約、**リポジトリのインターフェース** |
| インフラストラクチャ | 技術詳細 | リポジトリの実装、DB、外部API、メール送信 |

### 依存の方向 — ドメインを守る

鉄則は「**依存は内側(ドメイン)に向ける**」です。ドメイン層は他のどの層にも依存しません。フレームワークも、DBも、HTTPも知りません。だからこそビジネスルールを単体でテストでき、技術の変更(DB移行、フレームワーク更新)に巻き込まれません。

「ドメイン層がリポジトリを使うのに、実装はインフラ層にある」を成立させるのが**依存性逆転 (Dependency Inversion)** です。インターフェースをドメイン層に置き、実装をインフラ層に置きます。

```text
myapp/
├── domain/          # order.go, money.go, order_repository.go (interface)
├── application/     # place_order_usecase.go
├── infrastructure/  # order_repository_pg.go (PostgreSQL実装)
└── presentation/    # handler.go, dto.go
```

### 層をスキップする誘惑

「ハンドラから直接リポジトリを呼べば速いのでは」という誘惑は定番の落とし穴です。一見ムダに見える経由にも意味があります。

- ユースケースの進行(トランザクション、イベント発行)が入口ごとに重複する
- 集約のメソッドを通らない更新が生まれ、**不変条件が迂回される**
- テストで差し替える継ぎ目がなくなる

💡 コツ: 迷ったら「この import はドメインに向かっているか？」と自問してください。ドメイン層のファイルに `database/sql` や `net/http` の import が現れたら黄信号です。

### 確認問題

**問1.** レイヤードアーキテクチャにおいて、ドメイン層が依存してよいものはどれでしょう？

1. ORMライブラリ(データベースアクセスのため)
2. アプリケーション層(ユースケースを呼び出すため)
3. 原則として他のどの層にも依存しない(言語の標準機能程度にとどめる)
4. プレゼンテーション層のDTO(入力を受け取るため)

<details><summary>答えと解説</summary>

正解: **3**

ドメイン層は何にも依存しないのが原則です。だからこそDBなしでビジネスルールをテストでき、技術変更の影響を受けません。ORMへの依存はドメインモデルをDB都合で歪ませます。アプリケーション層への依存は方向が逆です(アプリケーション層がドメインを使う)。DTOへの依存もプレゼンテーションの都合をドメインに持ち込むことになります。「依存の矢印はすべてドメインに向かう」と覚えてください。

</details>

**問2.** HTTPハンドラからアプリケーションサービスを経由せず、直接リポジトリを呼んで注文ステータスを更新する実装にしました。最も深刻な問題はどれでしょう？

1. レスポンスがわずかに遅くなる
2. 集約のメソッドを通らない更新によって不変条件の検証が迂回され、不正な状態が保存されうる
3. ハンドラのコード行数が増える
4. リポジトリのメソッド名が長くなる

<details><summary>答えと解説</summary>

正解: **2**

最も深刻なのはルールの迂回です。集約は「キャンセル済みの注文は出荷できない」のような不変条件をメソッド内で守っていますが、ハンドラが直接リポジトリで状態を書き換えると、その検証をすり抜けて不正なデータが永続化されます。さらにトランザクション管理やイベント発行もハンドラごとに重複します。性能や行数は本質ではありません。ひっかけ: 層を飛ばすのは「速い」のではなく「ルールを踏み倒している」だけです。

</details>

**問3.** リポジトリの「インターフェース」と「実装」を置く場所の組み合わせとして、依存性逆転 (Dependency Inversion) にかなうものはどれでしょう？

1. インターフェース: インフラストラクチャ層 / 実装: ドメイン層
2. インターフェース: アプリケーション層 / 実装: プレゼンテーション層
3. 両方ともインフラストラクチャ層
4. インターフェース: ドメイン層 / 実装: インフラストラクチャ層

<details><summary>答えと解説</summary>

正解: **4**

インターフェースをドメイン層に置くことで「ドメインは抽象にだけ依存し、DB詳細(実装)はインフラ層が受け持つ」という逆転が成立します。両方をインフラ層に置くと、それを使うドメイン・アプリケーション層がインフラ層に依存してしまい、依存の向きが外側へ漏れます。実装をドメイン層に置く案は、SQLやドライバの import がドメインに入り込み、ドメインの純粋性が壊れます。

</details>

**問4.** コードレビューで、domain パッケージのファイルに `database/sql` の import を見つけました。最初に取るべき対応として最も適切なものはどれでしょう？

1. SQLの処理をリポジトリ実装(インフラストラクチャ層)へ移し、ドメインにはインターフェースだけを残す
2. import の並び順を整えて承認する
3. ドメイン層でもSQLは一般的なので問題ない
4. SQLをアプリケーションサービスに移す

<details><summary>答えと解説</summary>

正解: **1**

ドメイン層にDBの関心(database/sql)が漏れているので、永続化の詳細をインフラ層のリポジトリ実装に追い出し、ドメインにはリポジトリのインターフェースだけを残すのが正解です。これでドメインは再び単体テスト可能になります。アプリケーションサービスへ移すのも、場所が変わるだけでアプリケーション層が技術詳細に汚染される点で不十分です。「ドメインにインフラのimportが現れたら黄信号」はレビューの実用的なチェックポイントです。

</details>

**問5.** 4層の責務の対応として誤っているものはどれでしょう？

1. プレゼンテーション層 — HTTPリクエストの受付とレスポンスの整形
2. インフラストラクチャ層 — ビジネスルールの判定と不変条件の維持
3. アプリケーション層 — ユースケースの進行とトランザクション管理
4. ドメイン層 — エンティティ・値オブジェクト・集約によるモデルの表現

<details><summary>答えと解説</summary>

正解: **2**

ビジネスルールの判定と不変条件の維持はドメイン層の責務です。インフラストラクチャ層が受け持つのはDBアクセス・外部API・メール送信などの技術詳細であり、ルールを判断してはいけません。他の3つは正しい対応です。「誤っているものを選べ」形式では、責務の入れ替え(特にドメインとインフラの取り違え)が定番の作りなので、層の名前と責務をセットで即答できるようにしておきましょう。

</details>

## 3. 境界でのデータ変換とバリデーション

### DTOとドメインオブジェクトを分ける

APIのリクエスト/レスポンスの形(DTO: Data Transfer Object)と、ドメインオブジェクトは**別物として定義**します。ドメインの構造体に `json:"..."` タグを付けてそのまま返したくなりますが、こうするとAPIの表示都合(キー名、日付フォーマット)がドメインを汚し、逆にドメインの内部変更がそのままAPI互換性を壊します。

```go
// presentation/dto.go — 境界の形
type OrderResponse struct {
    ID    string `json:"id"`
    Total int64  `json:"total_yen"`
}

func toOrderResponse(o *domain.Order) OrderResponse {
    return OrderResponse{ID: o.ID().String(), Total: o.Total().Yen()}
}
```

FastAPI なら Pydantic モデルがこの DTO にあたります。変換関数は境界(プレゼンテーション層)に置きます。

### バリデーションの3段階

「どこで検証するか」は混乱しやすいので、3段階に整理します。

| 段階 | 例 | 置き場所 |
|---|---|---|
| 形式チェック | JSONとして妥当か、必須項目があるか、数値か | プレゼンテーション層(Pydantic / structタグ) |
| ドメインルール | 注文数は1〜100、メールアドレスの仕様 | ドメイン層(値オブジェクト・エンティティ) |
| ユースケース固有の前提 | 対象の会員が存在するか(他集約の照会が必要) | アプリケーション層 |

重要なのは、**ドメイン層が最終防衛線**だということです。「Pydanticでチェック済みだからドメインでは省略」は危険です。入口はHTTPだけとは限らず(バッチ、管理CLI、別API)、どの経路から来ても値オブジェクトの生成時検証がルールを守ります。

### エラーの変換

ドメイン層は `ErrAlreadyCancelled` のような**ドメインの言葉のエラー**を返します。それをHTTPステータス(409など)へ変換するのはプレゼンテーション層の仕事です。ドメインが `http.StatusConflict` を知っていたら依存の向きが壊れています。

💡 コツ: 「この検証は、入口が増えても必ず守られるべきか？」— Yes ならドメイン層に置く(または重ねて置く)のが安全です。

### 確認問題

**問1.** 「注文数は1以上100以下」というビジネスルールの最終的な守り手として最も適切な場所はどこでしょう？

1. フロントエンドの入力フォーム
2. プレゼンテーション層のstructタグ(またはPydantic)
3. ドメイン層の値オブジェクト(生成時に検証し、不正なら生成できない)
4. データベースのCHECK制約のみ

<details><summary>答えと解説</summary>

正解: **3**

ビジネスルールの最終防衛線はドメイン層です。値オブジェクト Quantity の生成時に検証すれば、HTTP・バッチ・CLIなどどの入口から来ても不正値は存在できません。フロントエンドやPydantic/structタグの検証はユーザー体験のための早期チェックとして有効ですが、別経路をすり抜けます。DB制約も保険にはなりますが、エラーがドメインの言葉にならず、ルールがコードから見えなくなるため「のみ」に頼るのは不適切です。

</details>

**問2.** ドメインの構造体に `json:"..."` タグを付けてAPIレスポンスとして直接返す設計の問題点として最も適切なものはどれでしょう？

1. JSONのエンコードが遅くなる
2. ドメインの内部変更がそのままAPI互換性を壊し、API都合の変更がドメインを歪める(双方向の結合)
3. structのフィールド数が増える
4. Goでは json タグが使えない

<details><summary>答えと解説</summary>

正解: **2**

ドメインオブジェクトとAPIの形を共有すると、ドメインのリファクタリング(フィールド名変更など)が外部契約の破壊になり、逆に「APIでこのキー名にしたい」という表示都合がドメインのモデリングを縛ります。DTOを分けて境界で変換すれば、両者は独立に進化できます。性能やフィールド数は本質ではなく、Goでjsonタグが使えないというのは事実に反します。

</details>

**問3.** FastAPIのPydanticモデルで形式チェックをしているのに、ドメイン層の値オブジェクトでも同じルールを検証する理由として最も適切なものはどれでしょう？

1. Pydanticのバリデーションは信頼性が低いから
2. 二重に検証するとパフォーマンスが向上するから
3. エラーメッセージを2回表示するため
4. 入口はWeb APIだけとは限らず(バッチ・CLI・別サービス)、どの経路でもドメインがルールを守る必要があるから

<details><summary>答えと解説</summary>

正解: **4**

ドメイン層の検証は「最終防衛線」です。システムが成長するとバッチ処理や管理ツールなどHTTP以外の入口が必ず増え、プレゼンテーション層のチェックはそれらを守れません。値オブジェクトの生成時検証なら全経路で必ず通ります。Pydanticの信頼性の問題ではなく責務の違いであり、二重検証は性能向上やメッセージ表示のためでもありません。💡「不正な状態を表現できないようにする」原則の実践です。

</details>

**問4.** 「この予約操作は、対象の会員がすでに退会していないことを確認してから実行する」— 会員集約への照会を伴うこの確認の置き場所として最も適切なのはどこでしょう？

1. アプリケーションサービス(リポジトリで会員を照会し、ユースケースの前提として確認する)
2. 予約エンティティのコンストラクタ
3. プレゼンテーション層のDTO変換時
4. データベースの外部キー制約に任せる

<details><summary>答えと解説</summary>

正解: **1**

他集約(会員)の存在・状態の照会が必要な前提確認は、リポジトリを使えるアプリケーションサービスが担うのが自然です。予約エンティティのコンストラクタに置くと、予約集約が会員リポジトリに依存してしまい集約の独立性が壊れます。DTO変換時はデータの形の変換が責務で、業務の前提確認の場所ではありません。外部キー制約は「存在」は守れても「退会済みか」という状態のルールは表現できません。

</details>

**問5.** ドメイン層が返した ErrAlreadyCancelled(キャンセル済みエラー)をHTTP 409 Conflict に変換する処理はどこに置くべきでしょう？

1. ドメイン層(エラー定義と一緒に置くのが自然だから)
2. リポジトリの実装内
3. プレゼンテーション層(ドメインのエラーをHTTPの言葉に翻訳する境界だから)
4. アプリケーションサービス(ユースケースの一部だから)

<details><summary>答えと解説</summary>

正解: **3**

HTTPステータスは「Webという入口」の言葉なので、翻訳はプレゼンテーション層の責務です。ドメイン層が409を知ると net/http への依存が生まれ、依存の向きが壊れます。アプリケーションサービスに置くと、同じユースケースをCLIから呼んだときにHTTPの概念が紛れ込みます。リポジトリはデータアクセスの実装であり、エラー翻訳の場所ではありません。「各層は自分の言葉でエラーを語り、境界で翻訳する」と覚えましょう。

</details>
