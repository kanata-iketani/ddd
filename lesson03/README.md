# 第3章 境界づけられたコンテキスト (Bounded Context)

DDDの戦略的設計の中核、境界づけられたコンテキスト (Bounded Context) を学びます。「1つの大きなモデルで全部を表す」のをやめ、言葉とモデルが一意に通じる範囲に境界を引くことで、複雑さを閉じ込める技術です。境界の必要性→見つけ方→物理構成との関係、の順に進みます。

## 1. なぜ境界が必要か — 統一モデルの失敗

### 「全社で1つの顧客クラス」の末路

システムが育つと、こんなクラスを見かけるようになります。

```go
type Customer struct {
    ID, Name, Email        string
    FavoriteCategories     []string // マーケ部の要望
    CreditLimit            int      // 経理部の要望
    SupportTickets         []Ticket // サポート部の要望
    DeliveryPreferences    []Pref   // 物流部の要望
    // ...以下、全部門の要望が積もり続ける
}
```

全部門の要求を1つのモデルで満たそうとすると、**誰の要求にも最適でない神クラス (god class)** が生まれます。どのフィールドがいつ使われるか誰も把握できず、ある部門の変更が別部門を壊す。これが「統一モデルの失敗」です。

### 同じ言葉でも、文脈で意味が違う

根本原因は、**同じ言葉が部門（文脈）によって違う概念を指す**ことです。たとえば EC サイトの「商品」:

| 文脈 | 「商品」が意味するもの | 関心事 |
|---|---|---|
| カタログ | 説明文・画像・価格表示 | 魅力的に見せる |
| 在庫 | SKU・数量・棚番号 | 数を正確に保つ |
| 配送 | 重量・サイズ・梱包区分 | 安全に運ぶ |

これらを1つの `Product` クラスに押し込むから壊れるのです。

### 境界づけられたコンテキスト (Bounded Context)

DDD の答えはシンプルで、**モデルの一貫性を保証できる範囲に境界を引く**ことです。境界づけられたコンテキストとは「**この境界の中では、言葉とモデルの意味が一意である**」という約束です。カタログコンテキストの `Product` と在庫コンテキストの `Product` は、同じ名前でも**別のモデル**として定義してかまいません。むしろ分けるのが正解です。

ユビキタス言語（第2章）は「コンテキストの中で」通用する言語です。境界がなければ言語は曖昧になり、境界があるから言語が厳密になれます。

💡 コツ: 「同じ名前のクラスを2つ作るのは重複では?」と感じたら、フィールドと振る舞いを見比べてください。重なりがほとんどないなら、それは重複ではなく**別概念が同名を名乗っていただけ**です。

### 確認問題

**問1.** ECサイトの `Product` クラスが、カタログ表示用の説明文・在庫数・配送用の重量データをすべて持ち、変更のたびに複数チームの調整が必要になっています。DDDの観点で最も適切な対処はどれでしょう？

1. フィールドをカテゴリ別にコメントで区分けし、変更時の影響範囲をドキュメント化する
2. カタログ・在庫・配送のコンテキストごとに別々の商品モデルを定義し、境界で分ける
3. Productクラスを抽象基底クラスにし、継承で各部門向けのサブクラスを作る
4. 全フィールドをgetterとsetterで包み、アクセス制御で安全にする

<details><summary>答えと解説</summary>

正解: **2**

同じ「商品」でも文脈ごとに関心事がまったく違うので、コンテキストごとに別モデルを定義するのが境界づけられたコンテキストの考え方です。コメントやドキュメント化は神クラスの構造自体を変えないので調整コストが残ります。継承は「共通の親がある」前提ですが、カタログの商品と配送の商品にはほとんど共通の振る舞いがなく、むしろ結合を増やします。getter/setterはカプセル化の見た目を与えるだけで、全部門が同じクラスに依存する問題を解決しません。ひっかけ: 「別モデルを2つ作る=重複」ではなく、別概念が同名だっただけです。

</details>

**問2.** 境界づけられたコンテキスト (Bounded Context) の定義として最も正確なものはどれでしょう？

1. その内側では用語とモデルの意味が一意に定まる、モデルの適用範囲の境界
2. マイクロサービス1つに相当する、デプロイ単位の境界
3. データベースのスキーマを分割する単位
4. チームのアクセス権限を分離するセキュリティ境界

<details><summary>答えと解説</summary>

正解: **1**

境界づけられたコンテキストは「この中では言葉とモデルが一意」という**モデルの適用範囲**を区切る論理的な境界です。マイクロサービスやDBスキーマは境界を物理的に表現する手段の1つにすぎず、1コンテキスト=1サービスとは限りません(モジュラモノリスでも境界は保てます)。セキュリティ境界は別の概念です。ひっかけ: 「境界」という言葉から物理的な分割を連想しがちですが、本質は意味論(言葉の一意性)の境界です。

</details>

1. どちらかの定義に全社で統一し、用語集で矯正すべきである
2. 「契約」クラスに status フィールドを持たせ、商談中と締結済みを状態で区別すべきである
3. 営業と契約管理は別のコンテキストであり、それぞれのモデルを別に定義してよいサイン
4. ドメインエキスパート同士の認識齟齬なので、モデリング以前にビジネス側で解決すべき問題

<details><summary>答えと解説</summary>

正解: **3**

同じ言葉が部門で違う意味を持つのは、そこに**コンテキストの境界がある**強いサインです。営業の「契約(商談)」と契約管理の「契約(証券)」は関心事もライフサイクルも違うので、別モデルにするのが自然です。全社で1つの定義に統一しようとするのが統一モデルの失敗パターンそのもの。statusフィールドでの区別は2つの概念を1クラスに同居させる神クラスへの第一歩です。認識齟齬ではなく、どちらの部門も自分の文脈では正しいので、ビジネス側で「解決」すべき問題でもありません。

</details>

**問4.** 「カタログコンテキストと在庫コンテキストの両方に Product 構造体を定義するのはDRY原則(重複排除)に反するのでは」というレビュー指摘への、DDD観点で最も適切な返答はどれでしょう？

1. 指摘どおり共通ライブラリに Product を1つ定義し、両コンテキストから参照するよう直す
2. 重複はやむを得ないコストとして受け入れ、2つのProductを手動で同期し続ける
3. フィールドと振る舞いがほぼ重ならないなら別概念であり、DRYが禁じる「知識の重複」には当たらない
4. GoのembeddingでProductBaseを共有し、差分だけ各コンテキストで足す

<details><summary>答えと解説</summary>

正解: **3**

DRYが禁じるのは「同一の知識・ルール」の重複です。カタログのProduct(説明・画像)と在庫のProduct(SKU・数量)は名前が同じだけで知識が異なるため、分けることはDRY違反ではありません。共通ライブラリ化やembeddingでの共有は、両コンテキストを1つのモデルに結合させ、片方の変更が他方を壊す統一モデルの失敗を再生産します。「やむを得ないコスト」という返答は、別概念であるという本質を説明できておらず、同期の必要もありません(それぞれ独立に進化してよい)。

</details>

**問5.** 統一モデル(全社共通の単一モデル)が大規模システムで失敗しやすい根本的な理由として最も適切なものはどれでしょう？

1. モデルが大きいとORMのパフォーマンスが劣化するから
2. 全部門の関心事を1つのモデルに背負わせると、どの部門にも最適でなく、変更の影響が全部門に波及するから
3. 開発者の人数が増えるとコンフリクトが頻発するから
4. 単一モデルではデータベースを分割できず、スケールしないから

<details><summary>答えと解説</summary>

正解: **2**

根本原因は意味論の問題です。文脈ごとに違う概念を1つのモデルに押し込むと、妥協だらけで誰の要求にも合わず、かつ全部門が同じモデルに依存するため変更が波及します。ORMの性能・コンフリクト・DB分割はいずれも二次的・技術的な症状であり、たとえそれらを技術で緩和しても「カタログの都合で在庫のモデルが変わる」という本質的な問題は残ります。ひっかけ: もっともらしい技術的理由が並びますが、DDDは技術ではなくモデルの意味の一貫性の話です。

</details>

## 2. 境界の見つけ方

### 境界は「言葉が変わる場所」にある

境界づけられたコンテキストは図面から発明するものではなく、**ドメインの会話の中から発見する**ものです。探すときの手がかりは次の4つです。

| 手がかり | 具体例 |
|---|---|
| 同じ言葉の意味が変わる | 「注文」が営業では見積もり、物流では出荷指示を指す |
| 業務プロセスの切れ目 | 「注文確定」を境に、販売の仕事から配送の仕事へ移る |
| ドメインエキスパートが交代する | 在庫の質問は在庫管理者に、価格の質問は営業企画に聞く |
| ルール(不変条件)の持ち主が変わる | 与信枠は経理が決め、配送制限は物流が決める |

💡 コツ: **データの形ではなく、振る舞いとルールで考える**こと。「どちらも name と id を持つから同じモデル」ではなく、「守るべきルールが違うなら別モデル」です。

### 1人の「顧客」が3つのモデルになる

ECサイトの「顧客」を追いかけると、コンテキストごとに姿が変わります。

- **カタログ文脈**: `Viewer` — 閲覧履歴とおすすめ対象。本名は不要
- **注文文脈**: `Buyer` — 支払い手段と請求先。与信ルールの対象
- **サポート文脈**: `Contact` — 問い合わせ履歴と対応状況

同一人物でも、各コンテキストが必要とする属性と振る舞いは別物です。無理に1つにせず、**共通するのは ID だけ**にします。

### 境界を跨ぐときは「IDで参照+変換」

コンテキストを跨いでオブジェクトをそのまま渡すと、相手のモデルが自分のコンテキストに漏れ込み、境界が溶けます。原則は次の2つです。

1. 他コンテキストのオブジェクトは **ID で参照**する(`buyerID` を持つ。`Buyer` 構造体は持たない)
2. 他コンテキストからデータを受け取るときは、境界で**自分のモデルに変換**する(変換の仕組みは第4章の腐敗防止層で詳しく扱います)

```go
// 注文コンテキスト: カタログのProductをそのまま持たない
type OrderLine struct {
    ProductID   string // IDで参照
    ProductName string // 注文時点の名前のコピー(スナップショット)
    UnitPrice   Money  // 注文時点の価格
}
```

注文明細が商品名や価格を**コピーして持つ**のは、注文確定後にカタログ側で値段が変わっても注文が変わらないため。これも境界の効用です。

### 確認問題

**問1.** 旅行予約システムのモデリング中、「予約」という言葉について、コールセンターでは「電話で受けた仮押さえ」、経理では「入金済みの確定取引」と説明されました。この観察から導ける最も適切な判断はどれでしょう？

1. 用語の揺れを正すため、社内標準の「予約」の定義を1つ決めて両部門に周知する
2. 言葉の意味が変わる場所なので、コンテキストの境界候補としてマークする
3. 仮押さえと確定は同じ予約の状態違いなので、1つの予約モデルにstatusを持たせる
4. 経理の定義の方が厳密なので、経理の定義をユビキタス言語として採用する

<details><summary>答えと解説</summary>

正解: **2**

同じ言葉の意味が部門で変わるのは境界発見の最重要シグナルです。コールセンターの「予約(仮押さえ)」と経理の「予約(確定取引)」は守るべきルールもライフサイクルも違うため、境界候補としてマークし、それぞれの文脈でモデルを検討します。標準定義の統一やどちらか一方の採用は、もう片方の文脈のモデルを歪めます。statusでの一本化は一見自然ですが、電話対応のルールと会計のルールが1つのクラスに同居し、神クラス化への道です。

</details>

1. 担当するドメインエキスパートが交代する場所
2. 業務プロセスの責任が別の部署へ移る場所

</details>

**問3.** 注文コンテキストが、カタログコンテキストの `Product` 構造体をimportしてそのまま注文明細に保持しています。この設計の最大の問題点はどれでしょう？

3. importの循環参照がコンパイルエラーを引き起こす
4. カタログチームのコードレビューを注文チームが受ける必要が生じる

</details>

**問4.** ECサイトで、同一人物の利用者がカタログ文脈では閲覧者(Viewer)、注文文脈では購入者(Buyer)、サポート文脈では問い合わせ者(Contact)として別々にモデリングされています。これらのモデル間で共有すべき情報として最も適切なものはどれでしょう？

## 3. コンテキストと物理構成 — サービス・パッケージ・チーム

### 1コンテキスト = 1マイクロサービス、とは限らない

よくある誤解が「境界づけられたコンテキストの数だけマイクロサービスを作る」です。コンテキストは**論理的な境界**(モデルと言葉の適用範囲)であり、マイクロサービスは**物理的な境界**(デプロイ単位)。対応関係は自由です。

| 構成 | 説明 | 向いている状況 |
|---|---|---|
| モジュラモノリス | 1プロセス内にコンテキストをモジュールとして分離 | チームが小さい・ドメイン理解がまだ浅い |
| 1コンテキスト=1サービス | 境界とデプロイ単位を一致させる | チーム・スケール要件が明確 |
| 複数コンテキスト=1サービス | 小さいコンテキストを同居させる | 運用コストを抑えたい |

順序が大事です: **論理境界(モデル)が先、物理分割(サービス)は後**。境界が曖昧なままサービスを切ると「分散した泥団子 (distributed big ball of mud)」になり、モノリスより悲惨です。

### コードで境界を表現する

モノリスでも、パッケージ/モジュールで境界は表現できます。

```
# Go: トップレベルのパッケージ = コンテキスト
/catalog   … カタログ文脈の Product
/ordering  … 注文文脈の Order, Buyer
/shipping  … 配送文脈の Shipment
```

```
# Python: パッケージで同じ構造
src/catalog/, src/ordering/, src/shipping/
```

ルールは「**コンテキストを跨ぐ import をしない**」(するなら ID と変換レイヤー経由)。Go なら `internal/` で強制でき、Python なら import-linter などで検査できます。

### 共有データベースの危険

物理分割していても、**複数コンテキストが同じテーブルを読み書き**していたら境界は実質ありません。スキーマ変更が全コンテキストを巻き込み、不変条件の持ち主も曖昧になります。コンテキストごとにスキーマ(最低でもテーブルの所有権)を分け、他コンテキストのデータは API やイベント経由で手に入れるのが原則です。

### チームとの関係

コンテキストは**チームの責任範囲**とも対応させるのが理想です(1コンテキスト=1チームの所有)。複数チームが1つのモデルを同時に触ると言葉の一意性が守れなくなるためで、組織構造がシステム構造に写るという**コンウェイの法則 (Conway's Law)** を逆手に取り、望むアーキテクチャに合わせてチームを切る(逆コンウェイ戦略)という考え方もあります。

💡 コツ: 迷ったら「モジュラモノリス+パッケージ境界」から始めるのが低リスクです。境界が正しければ、後からサービスに切り出すのは比較的簡単です。

### 確認問題

**問1.** 5人のチームが新規ECサイトを開発します。カタログ・注文・配送の3コンテキストを識別済みですが、ドメイン理解はまだ浅い段階です。初期アーキテクチャとして最も適切なものはどれでしょう？

1. コンテキストごとに3つのマイクロサービスを立て、最初から境界を物理的に強制する
2. 単一のコードベースにフラットに実装し、境界はコメントで示す
3. モジュラモノリスとし、コンテキストをパッケージで分離して跨ぎimportを禁止する
4. まず1つのコンテキストだけ実装し、他の2つは設計が固まるまで着手しない

<details><summary>答えと解説</summary>

正解: **3**

ドメイン理解が浅い段階では境界の引き直しが必ず起きます。モジュラモノリスなら境界(パッケージ)の変更はリファクタリングで済みますが、マイクロサービスに切ってしまうと境界変更=サービス再編成になり高コストです(分散した泥団子のリスク)。論理境界が先、物理分割は後が原則。コメントだけの境界は強制力がなく溶けていきます。1コンテキストずつの逐次開発は境界の妥当性を検証できず、ECサイトとして成立しません。

</details>

**問2.** 「境界づけられたコンテキスト」と「マイクロサービス」の関係について最も正確な説明はどれでしょう？

1. 両者は同じ概念をDDDとアーキテクチャの言葉で言い換えたものである
2. コンテキストは論理境界、サービスは物理境界であり、1対1に対応させる義務はない
3. マイクロサービスを採用する場合のみコンテキストの概念が意味を持つ
4. 1つのマイクロサービスは必ず複数のコンテキストを含むべきである

<details><summary>答えと解説</summary>

正解: **2**

コンテキストは「モデルと言葉が一意に通じる範囲」という論理的境界で、デプロイ単位(物理)とは独立した概念です。1対1にしてもよいし、モジュラモノリスで1プロセスに複数コンテキストを同居させてもよい。同一概念の言い換えではなく、マイクロサービスを使わなくても(モノリスでも)コンテキストは設計の中心概念として機能します。「1サービスに複数コンテキストを含むべき」という義務も逆の義務もありません。ひっかけ: 1サービス内に複数コンテキストは可ですが、1つのコンテキストを複数チームのサービスに泣き別れさせるのは境界崩壊のもとです。

</details>

**問3.** 注文サービスと配送サービスは別々にデプロイされていますが、どちらも同じ `orders` テーブルを直接読み書きしています。この構成の本質的な問題はどれでしょう？

1. 2サービスからの書き込みでデッドロックが頻発する
2. テーブルの所有権が曖昧になり、スキーマ変更と不変条件の管理が両コンテキストを巻き込む(境界が実質消滅)
3. DBが単一障害点になり可用性が下がる
4. ネットワーク越しのDB接続でレイテンシが増える

<details><summary>答えと解説</summary>

正解: **2**

物理的にサービスを分けても、共有テーブルを直接読み書きした時点でモデルの境界は実質消滅します。スキーマが共有された統一モデルそのものになり、変更は常に両チームの調整事項になり、「注文の不変条件を守るのは誰か」も曖昧になります。デッドロック・単一障害点・レイテンシは起こり得る技術症状ですが、たとえ技術で緩和できても境界の問題は残ります。対処はテーブル所有権をコンテキストごとに分け、他コンテキストはAPIやイベント経由でデータを得ることです。

</details>

**問4.** Goのモノリスでコンテキスト境界をコードとして強制したい場合、最も効果的な手段はどれでしょう？

1. 各コンテキストのパッケージ名にプレフィックス(ctx_)を付けて識別しやすくする
2. コーディング規約に「他コンテキストのimport禁止」と明記し、レビューで指摘する
3. コンテキストごとのパッケージ構成にし、internal/ ディレクトリで外部からの直接importをコンパイラレベルで防ぐ
4. 全コンテキストの共有型を types パッケージに集約し、各コンテキストはそこだけをimportする

<details><summary>答えと解説</summary>

正解: **3**

Goの internal/ はコンパイラが import 可能範囲を強制する仕組みで、境界違反をビルドエラーとして検出できます(人の注意力に頼らない)。命名規約や文書化された規約+レビューは強制力がなく、締切前に必ず破られます。共有typesパッケージへの集約は、全コンテキストが同じ型に依存する統一モデルの再発明であり、境界をむしろ破壊します。ひっかけ: 「共通化してきれいにする」方向の選択肢は、コンテキスト境界の文脈ではたいてい罠です。

</details>

**問5.** 2つの開発チームが1つの「注文コンテキスト」のモデルを同時に変更しており、用語の定義が揃わずコンフリクトが続いています。コンウェイの法則を踏まえた最も適切な対処はどれでしょう？

1. 週次の用語同期ミーティングを設け、モデル変更を相互承認制にする
2. コンテキストの所有チームを1つに定めるか、業務の切れ目があればコンテキスト自体を2つに分ける
3. モデル変更権限をアーキテクトに集約し、両チームは申請制にする
4. コードオーナー機能で変更可能ファイルをチームごとに割り当てる

<details><summary>答えと解説</summary>

正解: **2**

1コンテキスト=1チームの所有が原則です。組織構造はシステム構造に写る(コンウェイの法則)ので、2チームで1モデルを触り続ける限り、言葉の一意性は構造的に壊れ続けます。所有を1チームに寄せるか、会話の中に業務の切れ目(言葉やルールの違い)が見つかるならコンテキストを分割してチームに合わせるのが筋です。同期ミーティング・承認制・アーキテクト集約・ファイル分割はいずれも調整コストを恒久化するだけで、構造の不一致という根本原因に手を付けていません。

</details>
