# 第10章 ドメインサービスとドメインイベント

エンティティにも値オブジェクトにも置けない操作の受け皿「ドメインサービス」と、集約間を疎結合につなぐ「ドメインイベント」を学びます。この章を終えると「このロジックはどこに置くべきか」「集約をまたぐ連携をどう設計するか」に自分の言葉で答えられるようになります。

## 1. ドメインサービス — 置き場所に困る操作の受け皿

### 置き場所に困る操作

ドメインの操作の多くは、エンティティ(ID で見分けるオブジェクト。L6)か値オブジェクト(値で比べる不変のオブジェクト。L7)のメソッドとして置けます。しかし、どちらにも自然に置けない操作が残ります。

典型例が**口座間送金**です。「Aの口座から引き落とし、Bの口座に入金する」という操作は、2つの口座エンティティにまたがります。`a.TransferTo(b, amount)` とすると口座Aが口座Bの内部事情を知りすぎますし、逆向きにしても不自然さは消えません。また「ユーザー名の重複チェック」は全ユーザーを見渡す必要があり、1人のユーザーエンティティの中には置けません。

こうした操作の受け皿が**ドメインサービス (Domain Service)** です。「エンティティにも値オブジェクトにも属さない、ドメインの操作だけを持つオブジェクト」です。

```go
// 2つの口座にまたがる操作はドメインサービスに
type TransferService struct{}

func (s TransferService) Transfer(from, to *Account, amount Money) error {
    if err := from.Withdraw(amount); err != nil {
        return err
    }
    return to.Deposit(amount)
}
```

| 部分 | 意味 |
|---|---|
| `type TransferService struct{}` | フィールドが1つもない構造体。データを持たず、メソッドだけを持つ入れ物 |
| `func (s TransferService) Transfer(...)` | TransferService のメソッド。レシーバが `*` なしの値レシーバ(L7)なのは、変更する中身がないため |
| `from, to *Account` | `from` と `to` の2つの引数が、どちらも `*Account`(口座へのポインタ)型。同じ型が続くときはまとめて書ける |
| `if err := from.Withdraw(amount); err != nil {` | 「Withdraw を呼んで結果を err に入れ、err が nil でなければ」。`;` の前で変数を作り、後ろで判定する1行の書き方。この err は if の中だけで使える |
| `return err` | 引き落としに失敗したら、入金せずにそのエラーを返す |
| `return to.Deposit(amount)` | 入金し、Deposit が返したエラー(成功なら nil)をそのまま返す |

### 動かして確かめる

口座エンティティも含めた完全版です。A の残高 10000 円から 3000 円、続けて 20000 円を B に送ります。

```go
package main

import (
	"errors"
	"fmt"
)

type Money int64 // 簡単のため円の整数で表す

// 口座エンティティ
type Account struct {
	id      string
	balance Money
}

func (a *Account) Withdraw(m Money) error {
	if a.balance < m {
		return errors.New("残高不足")
	}
	a.balance -= m
	return nil
}

func (a *Account) Deposit(m Money) error {
	if m <= 0 {
		return errors.New("入金額は1円以上")
	}
	a.balance += m
	return nil
}

// 2つの口座にまたがる操作はドメインサービスに
type TransferService struct{}

func (s TransferService) Transfer(from, to *Account, amount Money) error {
	if err := from.Withdraw(amount); err != nil {
		return err
	}
	return to.Deposit(amount)
}

func main() {
	a := &Account{id: "A", balance: 10000}
	b := &Account{id: "B", balance: 0}
	svc := TransferService{}

	err := svc.Transfer(a, b, 3000)
	fmt.Println("1回目:", err, "/ A =", a.balance, "B =", b.balance)

	err = svc.Transfer(a, b, 20000)
	fmt.Println("2回目:", err, "/ A =", a.balance, "B =", b.balance)
}
```

実行結果:

```text
1回目: <nil> / A = 7000 B = 3000
2回目: 残高不足 / A = 7000 B = 3000
```

1回目は成功し(`<nil>` はエラーなし)、A が 7000 円、B が 3000 円になりました。2回目は A の残高 7000 円に対して 20000 円なので、Withdraw が「残高不足」を返し、Transfer は入金に進まずにそのエラーを返しています。残高の検査は口座エンティティ自身(`Withdraw`)が持ち、ドメインサービスは「引き落としてから入金する」という2つの口座にまたがる手順だけを持っている点が要所です。

### ドメインサービスの特徴

| 特徴 | 説明 |
|---|---|
| 状態を持たない (stateless) | 業務データをフィールドに持たず、引数で受け取って操作する。上の `TransferService{}` はどこで作っても同じ動きをする |
| ユビキタス言語の動詞 | 「送金する」「割り当てる」など、ドメインの操作そのものを名前にする(ユビキタス言語は L2) |
| ドメイン層に属する | DB や外部 API の都合は持ち込まない(それはインフラ層の仕事。層の分け方は L12) |

「ユーザー名の重複チェック」なら、ドメインサービスに `IsDuplicated(name)` のようなメソッドを置き、その中身では全ユーザーを検索する係(リポジトリ。L11)を使って同じ名前がいないかを調べます。DB のユニーク制約(同じ値の行を2つ入れられなくする DB の設定)を最後の安全網として併用するのはよいことですが、それだけだと「一意である」という業務ルールがコードのどこにも現れません。

### 💡 コツ: ドメインサービスは最後の手段

便利なので何でもドメインサービスに置きたくなりますが、やりすぎると**エンティティが貧血化**します(ルールが全部サービスに吸い出され、エンティティはただのデータの袋になる。この状態を「貧血ドメインモデル」と呼び、L16 で詳しく扱います)。そうなったエンティティは getter/setter(値を取り出すだけ・書き換えるだけのメソッド)しか持たなくなります。判断の順序を固定しましょう。

1. まず**エンティティのメソッド**に置けないか(そのオブジェクト自身の状態で決まるルールか?)
2. 次に**値オブジェクトの関数**に置けないか(値だけで完結する計算か?)
3. どちらも不自然なときだけ**ドメインサービス**へ

| 操作 | 置き場所 | 理由 |
|---|---|---|
| 注文は発送前ならキャンセルできる | 注文エンティティ | 注文自身の状態だけで決まる |
| 金額どうしの足し算 | Money 値オブジェクト | 値だけで計算が完結する |
| 口座Aから口座Bへ送金 | ドメインサービス | 2つのエンティティにまたがる |
| 過去の全注文を集計して送料無料か判定 | ドメインサービス | 多数の注文(集約)を見渡す必要がある |

この順で考えると、モデルの表現力を保ったまま、置き場所の迷いがなくなります。なお、ユースケースの進行役(トランザクション開始や DTO 変換。DTO は画面や API とやりとりするためのデータの形)は**アプリケーションサービス**の仕事で、ドメインサービスとは別物です。この区別は第12章で詳しく扱います。HTTP ハンドラ(コントローラ。Web からのリクエストを最初に受け取る関数)も、業務ルールの置き場所ではありません。

### 確認問題

**問1.** ECサイトで「顧客の過去の全注文を横断して集計し、配送料を無料にできるかを判定する」ロジックの置き場所として最も適切なのはどれでしょう?

1. 顧客エンティティのメソッドに置く
2. 配送料を表す値オブジェクトのメソッドに置く
3. ドメインサービスに置く
4. HTTPハンドラ(コントローラ)に置く

<details><summary>答えと解説</summary>

正解: **3**

全注文を横断する判定は、1つの顧客エンティティにも配送料の値にも閉じないため、ドメインサービスが適切です。顧客エンティティに置くと注文の集合を抱え込んで肥大化し、値オブジェクトは自分の値だけで完結する計算にしか向きません。コントローラに置くとドメイン知識がプレゼンテーション層に漏れ、別の入口(バッチやAPI)から呼べなくなります。「複数の集約を見渡す判定はドメインサービス」が目印です。

</details>

**問2.** 「注文は発送前であればキャンセルできる」というルールの置き場所として最も適切なのはどれでしょう?

1. 注文エンティティの Cancel メソッド
2. キャンセル専用のドメインサービス
3. アプリケーションサービス
4. リポジトリ

<details><summary>答えと解説</summary>

正解: **1**

このルールは注文自身の状態(発送済みかどうか)だけで判定できるので、注文エンティティのメソッドに置くのが最適です。わざわざドメインサービスに出すとエンティティが貧血化する第一歩になります。アプリケーションサービスは進行役であってルールの置き場所ではなく、リポジトリは永続化の抽象です。ひっかけ: 「サービス」という言葉の便利さに流されず、まず「エンティティ自身で決められるか」を考えるのがDDDの判断順序です。

</details>

**問3.** ドメインサービスの性質として最も適切なのはどれでしょう?

1. 業務データをフィールドに保持し、状態を管理する
2. DBアクセスを直接実装し、永続化も担当する
3. トランザクションの開始・コミットなどユースケースの進行を司る
4. 状態を持たず、引数で受け取ったドメインオブジェクトに対して操作を行う

<details><summary>答えと解説</summary>

正解: **4**

ドメインサービスは状態を持たない(stateless)のが原則で、操作対象は引数で受け取ります。業務データを抱えるならそれはエンティティであるべきです。DBアクセスの実装はインフラ層(リポジトリ実装)の仕事、トランザクション管理やユースケース進行はアプリケーションサービスの仕事です。「同じサービスという名前でも、ドメインサービスとアプリケーションサービスは役割が別」という区別は実務でも試験的な問いでも頻出です。

</details>

**問4.** 「ユーザー名はシステム全体で一意でなければならない」というルールの表現として最も適切なのはどれでしょう?

1. User エンティティのコンストラクタで全ユーザーを読み込んで重複を確認する
2. 一意性確認をドメインサービスとして表現し、実装ではリポジトリの検索を利用する
3. 画面側(フロントエンド)のバリデーションだけで保証する
4. DBのユニーク制約で守れるので、ドメイン層では何も表現しない

<details><summary>答えと解説</summary>

正解: **2**

全ユーザーを見渡す確認は1人のユーザーエンティティには置けないため、ドメインサービス(例: UserUniquenessChecker)として表現し、検索はリポジトリに任せるのが定石です。コンストラクタで全件読み込みは非現実的で、エンティティが集合全体の知識を抱えてしまいます。フロントのみの検証は API 直叩きで迂回されます。DBのユニーク制約は最後の砦として併用すべきですが、それ「だけ」にするとルールがモデルから消え、ユビキタス言語とコードの対応が失われます。

</details>

**問5.** あるチームが「ロジックはすべて〇〇Service クラスに置く」という方針を続けた結果、エンティティが getter/setter だけになりました。この状態の名前と問題点の組み合わせとして正しいのはどれでしょう?

1. ヘキサゴナルアーキテクチャ — 依存が整理された良い状態
2. 蒸留 — コアドメインが明確になった良い状態
3. 貧血ドメインモデル — ルールがサービスに散在し、重複や検証漏れが生じる
4. CQRS — 読み書きが分離された良い状態

<details><summary>答えと解説</summary>

正解: **3**

ルールがエンティティから吸い出されてデータの袋だけが残った状態を貧血ドメインモデル (Anemic Domain Model) と呼び、代表的なアンチパターンです。同じルールが複数のサービスに重複し、検証漏れの温床になります。ヘキサゴナルは依存方向の整理、蒸留はコアの分離、CQRSは読み書きモデルの分離であり、どれも「エンティティからルールを剥ぎ取ること」ではありません。ドメインサービスは便利ですが「最後の手段」という優先順位を忘れると、この状態に陥ります。

</details>

**問6.** 本文の TransferService で、残高 7000 円の口座 A から口座 B へ 20000 円を `Transfer(a, b, 20000)` しました。結果として正しいものはどれでしょう？

1. B に 20000 円が入金され、A の残高はマイナスになる
2. 「残高不足」のエラーが返り、Deposit は呼ばれないので A も B も残高は変わらない
3. A から 7000 円だけ引き落とされ、B に 7000 円が入金される
4. TransferService が残高を検査し、ドメインサービスの中で残高を直接書き換える

<details><summary>答えと解説</summary>

正解: **2**

Transfer はまず from.Withdraw を呼びます。Withdraw は口座エンティティ自身のルールとして「残高 < 引き落とし額」なら残高を変えずにエラーを返すので、Transfer は `if err != nil { return err }` で入金に進まず終わります。そのため A も B も変わりません。マイナス残高や一部だけの引き落としはこのコードには書かれていません。残高の検査はエンティティ(Withdraw)が持ち、ドメインサービスは2つの口座にまたがる手順だけを持つ、という分担がこの例の要点です。

</details>

## 2. ドメインイベント — 起きた事実をモデルにする

### ドメインイベントとは

**ドメインイベント (Domain Event)** は「ドメインで実際に起きた出来事」をオブジェクトにしたものです。名前は必ず**過去形**にします: `OrderPlaced`(注文が確定した)、`PaymentCompleted`(支払いが完了した)。ドメインエキスパートの「注文が確定**したら**、ポイントを付与する」という言葉の「〜したら」の部分がそのままイベントになります。つまりイベント名もユビキタス言語(L2)の一部です。

| 業務の言葉 | イベント名 | イベントを受けて動く側の例 |
|---|---|---|
| 注文が確定したら | `OrderPlaced` | ポイントを付与する・確認メールを送る |
| 支払いが完了したら | `PaymentCompleted` | 発送の準備を始める |
| 商品が発送されたら | `OrderShipped` | 配送状況のお知らせを送る |

```go
// 過去形で命名し、起きた事実を不変のデータとして持つ
type OrderPlaced struct {
    OrderID    OrderID
    CustomerID CustomerID
    Total      Money
    OccurredAt time.Time
}
```

| フィールド | 意味 |
|---|---|
| `OrderID` | どの注文で起きたか(集約の ID) |
| `CustomerID` | 誰の注文か |
| `Total` | 確定時点の合計金額(`Money` は L7 の値オブジェクト) |
| `OccurredAt time.Time` | いつ起きたか。`time.Time` は Go 標準の日時の型 |

「不変のデータとして持つ」とは、作った後に中身を書き換えないということです。起きた出来事は後から変わらないからです(不変については L7)。フィールド名が大文字で始まるのは、イベントを受け取る別パッケージからも読めるようにするためです(大文字・小文字による公開/非公開は L8)。

### イベントに含める情報

- 何が起きたか(イベント名)
- いつ起きたか(発生時刻)
- どの集約で起きたか(集約のID)
- 購読側の判断に必要な**最小限の事実**

### 集約が生成し、ディスパッチャが配る

イベントは**集約のメソッドの中で生成**します。「注文が確定した」という事実がいつ成立するかを知っているのは、確定のルールを持つ注文集約自身だからです。集約は発生したイベントをいったん内部に溜め、保存が成功した後にディスパッチャ(イベントを購読者へ配る係)が購読者(イベントを受け取って処理する側。subscriber)へ配ります。

```go
func (o *Order) Place() error {
    if len(o.items) == 0 {
        return errors.New("明細のない注文は確定できません")
    }
    o.status = StatusPlaced
    o.events = append(o.events, OrderPlaced{
        OrderID: o.id, CustomerID: o.customerID,
        Total: o.Total(), OccurredAt: time.Now(),
    })
    return nil
}
```

| 行 | 意味 |
|---|---|
| `if len(o.items) == 0 {` | 明細の数(`len` はスライスの長さ)が0なら |
| `return errors.New(...)` | 確定せずにエラーを返す(不変条件の検査) |
| `o.status = StatusPlaced` | 状態を「確定」にする |
| `o.events = append(o.events, OrderPlaced{...})` | 集約の中のイベント置き場 `events` に、新しいイベントを1つ追加する。`OrderPlaced{...}` は複数行にまたがって書いた構造体の値 |
| `Total: o.Total()` | 合計金額を計算するメソッドを呼び、その結果を入れる |
| `OccurredAt: time.Now()` | 今の日時を入れる |
| `return nil` | 成功(エラーなし) |

### 動かして確かめる

イベントを溜める `events` と、溜めたイベントを取り出す `PullEvents` を加えた完全版です(簡単のため、明細は金額の数字だけにしています)。

```go
package main

import (
	"errors"
	"fmt"
	"time"
)

// 過去形で命名し、起きた事実を持つ
type OrderPlaced struct {
	OrderID    string
	CustomerID string
	Total      int
	OccurredAt time.Time
}

type Order struct {
	id         string
	customerID string
	items      []int // 簡単のため明細は金額だけ
	status     string
	events     []OrderPlaced // 発生したイベントを溜めておく場所
}

func (o *Order) Total() int {
	sum := 0
	for _, price := range o.items {
		sum += price
	}
	return sum
}

func (o *Order) Place() error {
	if len(o.items) == 0 {
		return errors.New("明細のない注文は確定できません")
	}
	o.status = "確定"
	o.events = append(o.events, OrderPlaced{
		OrderID: o.id, CustomerID: o.customerID,
		Total: o.Total(), OccurredAt: time.Now(),
	})
	return nil
}

// 溜めたイベントを取り出し、集約の中は空にする
func (o *Order) PullEvents() []OrderPlaced {
	evs := o.events
	o.events = nil
	return evs
}

func main() {
	empty := &Order{id: "o-000", customerID: "c-001"}
	fmt.Println("明細なし:", empty.Place())

	o := &Order{id: "o-001", customerID: "c-001", items: []int{1200, 800}}
	fmt.Println("確定:", o.Place(), "/ 状態 =", o.status)

	// 保存が成功した後に、ディスパッチャがイベントを取り出して配る
	for _, e := range o.PullEvents() {
		fmt.Println("配る:", e.OrderID, e.CustomerID, e.Total)
	}
	fmt.Println("取り出した後に残っているイベント数:", len(o.events))
}
```

実行結果:

```text
明細なし: 明細のない注文は確定できません
確定: <nil> / 状態 = 確定
配る: o-001 c-001 2000
取り出した後に残っているイベント数: 0
```

| 出力 | 何が起きたか |
|---|---|
| 1行目 | 明細のない注文はルールに反するので、エラーが返り、イベントも作られない |
| 2行目 | 1200 + 800 円の注文は確定でき、状態が「確定」になった |
| 3行目 | 保存が成功した後(この例では省略)、`PullEvents` で取り出したイベントを配っている。合計 2000 円が入っている |
| 4行目 | 取り出した後は集約の中が空になる。同じイベントを2回配らないため |

`PullEvents` の `o.events = nil` は「イベント置き場を空にする」という意味です。イベントを配る処理そのもの(ディスパッチャ)は ch03 で扱います。

### 💡 コツ: 集約間の連携はイベントで疎結合に

「注文確定後にポイントを付与」を、注文集約がポイント集約を直接呼んで実現すると、注文がポイントの事情を知りすぎ、さらに1トランザクションで2つの集約を更新する原則違反(第9章)にもなります。`OrderPlaced` を発行してポイント側がそれを購読すれば、お互いの内部を知らずに連携でき、トランザクションも分離できます。このように、互いの中身を知らず、片方を変えてももう片方を直さずに済む関係を**疎結合**と呼びます(反対は**密結合**)。「直接呼ぶ代わりに、起きた事実を知らせる」—これがイベントの発想です。

なお、問題の選択肢に出てくる**ポーリング**は、相手のデータを定期的に見に行って変化を探す方式です。イベントのように「起きたら知らせてもらう」のではなく、自分から何度も確かめに行きます。

### 確認問題

## 3. イベント駆動の実装パターン

ドメインイベント (domain event) を「生成する」ところまでは前チャプターで学びました。ここでは、そのイベントを**どう配り、どう安全に処理するか**という実装の勘所を押さえます。

### 同一プロセス内 vs 非同期メッセージング

イベントの配送先には大きく2通りあります。プロセスは「動いているプログラム1つ分」のことです。

| 方式 | 配送 | 向いている場面 | 注意点 |
|---|---|---|---|
| 同一プロセス内ディスパッチ | メモリ上で即時に購読者を呼ぶ | 同じサービス内の軽い波及処理 | 購読者の失敗が発行側トランザクションを巻き込みやすい |
| 非同期メッセージング | メッセージブローカ (Kafka, SQS 等) 経由 | **境界づけられたコンテキスト (bounded context、L3) をまたぐ連携** | 配送保証・順序・重複を自分で設計する必要がある |

**メッセージブローカ**は、サービスの間でメッセージ(ここではイベント)を預かり、受け取る側へ届ける中継ソフトです。Kafka や Amazon SQS はその代表的な製品の名前です。発行側はブローカに預けた時点で処理を終えられ、受け取る側は自分の都合のよいときに取り出して処理します(これが非同期)。

別コンテキストや別サービスへ伝えるなら、疎結合を保てる非同期メッセージングが基本です。

### アウトボックスパターン (Outbox Pattern)

「DB を更新したのにイベント発行だけ失敗した(あるいはその逆)」という不整合は、2つの別々のシステム(DB とブローカ)を1つの操作で更新しようとすると必ず起きます。たとえば、注文を DB にコミット(変更を確定)した直後にプログラムが落ちると、ブローカへの送信は行われません。これを防ぐのが**アウトボックスパターン**です。

```go
// 集約の保存とイベント記録を「同じDBトランザクション」で行う
func (r *OrderRepo) Save(ctx context.Context, o *Order) error {
    return r.db.Tx(ctx, func(tx *sql.Tx) error {
        if err := saveOrder(tx, o); err != nil {
            return err
        }
        // イベントも同じトランザクションで outbox テーブルへ INSERT
        return insertOutbox(tx, o.PullEvents())
    })
}
```

| 部分 | 意味 |
|---|---|
| `func (r *OrderRepo) Save(...)` | 注文を保存する係(リポジトリ。L11)の Save メソッド |
| `ctx context.Context` | Go 標準の「処理の期限や中止の合図」を運ぶ引数。慣習として第1引数に置き、呼ばれた先へそのまま渡していく |
| `r.db.Tx(ctx, func(tx *sql.Tx) error { ... })` | この例で用意した補助メソッド(Go 標準のものではない)。渡された関数を1つのトランザクションの中で実行し、エラーがなければコミット、エラーならロールバック(全部取り消し)する |
| `func(tx *sql.Tx) error { ... }` | その場で書いた名前のない関数。`tx` は進行中のトランザクション(`*sql.Tx` は Go 標準 `database/sql` の型) |
| `saveOrder(tx, o)` | 注文を orders テーブルに書き込む補助関数(中身は省略) |
| `insertOutbox(tx, o.PullEvents())` | 集約に溜まったイベント(ch02)を取り出し、outbox テーブルに INSERT(行を追加する SQL)する補助関数 |

イベントは一旦 `outbox` テーブルに書き、別プロセス(リレー)が後からブローカへ送って `published` に印をつけます。業務データとイベントが**同じコミットで保存される**ため、「片方だけ成功」が起きません。

### 動かして確かめる(Python + SQLite)

同じ流れを Python の SQLite で再現します。`with db:` のブロックが、上の `r.db.Tx(...)` と同じく「中で例外が起きなければまとめてコミット、起きたらまとめて取り消し」の役をします。

```python
import sqlite3

db = sqlite3.connect(":memory:")
db.execute("CREATE TABLE orders (id TEXT, status TEXT)")
db.execute("CREATE TABLE outbox (event_id TEXT, name TEXT, order_id TEXT, published INTEGER)")

# 1) 注文の保存とイベントの記録を、同じトランザクションで行う
with db:  # with の中で例外がなければまとめてコミット、あればまとめて取り消し
    db.execute("INSERT INTO orders VALUES ('o-001', 'placed')")
    db.execute("INSERT INTO outbox VALUES ('ev-1', 'OrderPlaced', 'o-001', 0)")

# 2) 途中で失敗した場合: どちらも保存されない
try:
    with db:
        db.execute("INSERT INTO orders VALUES ('o-002', 'placed')")
        raise RuntimeError("保存の途中で障害")
except RuntimeError as e:
    print("失敗:", e)
print("orders:", db.execute("SELECT id FROM orders").fetchall())
print("outbox:", db.execute("SELECT event_id, published FROM outbox").fetchall())

# 3) リレー: 未送信のイベントを読み、ブローカへ送ったら印をつける
for event_id, name, order_id in db.execute(
        "SELECT event_id, name, order_id FROM outbox WHERE published = 0").fetchall():
    print("ブローカへ送信:", event_id, name, order_id)
    with db:
        db.execute("UPDATE outbox SET published = 1 WHERE event_id = ?", (event_id,))
print("outbox:", db.execute("SELECT event_id, published FROM outbox").fetchall())
```

実行結果:

```text
失敗: 保存の途中で障害
orders: [('o-001',)]
outbox: [('ev-1', 0)]
ブローカへ送信: ev-1 OrderPlaced o-001
outbox: [('ev-1', 1)]
```

| 段階 | 結果 |
|---|---|
| 1) 注文とイベントを同じトランザクションで保存 | orders に o-001、outbox に ev-1(未送信 = 0)が入った |
| 2) 途中で失敗 | o-002 の INSERT も取り消され、orders には o-001 しかない。「注文だけ保存されてイベントがない」状態にならない |
| 3) リレー | 未送信の ev-1 を送り、published を 1(送信済み)に変えた |

### at-least-once と冪等な購読者

アウトボックスのリレーは「送った直後にクラッシュ」すると同じイベントを再送します(上の 3 で、送信してから `published = 1` にする前に落ちた場合、次に起動したときに ev-1 をもう一度送ります)。つまり配送保証は **at-least-once(最低1回、ただし重複あり)** が現実解です。「ちょうど1回 (exactly-once)」を保証するのは非常に難しく、それに頼らない設計にします。

だから購読者 (subscriber) は**冪等 (idempotent)**、すなわち「同じイベントを2回受け取っても結果が変わらない」よう作る必要があります。

```python
points = {"c-001": 0}
processed = set()  # 処理済みのイベントIDを覚えておく場所

def on_order_placed_naive(event):
    points[event["customer_id"]] += 20

def on_order_placed_idempotent(event):
    if event["event_id"] in processed:  # 2回目以降は何もしない
        return
    points[event["customer_id"]] += 20
    processed.add(event["event_id"])

ev = {"event_id": "ev-1", "customer_id": "c-001"}

on_order_placed_naive(ev)
on_order_placed_naive(ev)  # 同じイベントが再送された
print("冪等でない購読者:", points["c-001"])

points["c-001"] = 0
on_order_placed_idempotent(ev)
on_order_placed_idempotent(ev)  # 同じイベントが再送された
print("冪等な購読者:", points["c-001"])
```

実行結果:

```text
冪等でない購読者: 40
冪等な購読者: 20
```

注文1件につき20ポイントを付与する購読者です。冪等でない方は、同じ ev-1 が再送されると2回付与して40ポイントになってしまいます。冪等な方は、処理済みのイベント ID を `processed` に記録し、2回目は何もしないので20ポイントのままです。実際のシステムでは、この「処理済みイベント ID」を DB の処理済みテーブルに記録します。ほかに、更新を UPSERT(行がなければ追加し、あれば上書きする SQL)にするのも定石です。

### イベントとコマンドは別物

**コマンド (command)** は「〜してください」という依頼を表すデータです。

| | イベント (event) | コマンド (command) |
|---|---|---|
| 意味 | 起きた**事実** | 依頼・命令 |
| 時制 | 過去形 `OrderPlaced` | 命令形 `PlaceOrder` |
| 拒否 | できない(もう起きた) | バリデーション(入力の検査)で拒否できる |
| 宛先 | 不特定多数が購読 | 1つのハンドラ(受け取って処理する関数)が受理 |

> 💡 コツ: 「〜しろ」はコマンド、「〜した」はイベント。発行側が受信側に処理を**強制**したくなったら、それはイベントではなくコマンドの設計です。混同するとコンテキスト間が密結合に戻ってしまいます。

最後に、1つのイベントに何でも詰め込むと**肥大化**し、受信側が不要な依存を背負います。また「A のイベントで B を更新し、B のイベントで A を更新」する**循環依存**は無限ループの温床です。イベントは小さく、流れは一方向を意識しましょう。

なお、問題の選択肢に出てくる `panic` は、Go でプログラムを異常終了させる仕組みです。

### 確認問題

**問1.** 注文サービスで「注文を保存し、かつ OrderPlaced イベントをメッセージブローカへ発行する」処理を実装します。DB コミットの直後にブローカへ publish する実装にしたところ、まれに「注文は保存されたがイベントが届かない」不整合が起きました。最も適切な対処はどれですか。

1. publish を DB コミットより前に移動し、先にイベントを送ってから注文を保存する
2. 注文の保存とイベントを outbox テーブルへの INSERT として同一トランザクションにまとめ、別のリレーがブローカへ送る
3. publish が失敗したら panic させ、プロセスを再起動して最初からやり直す
4. イベント発行をやめ、購読側が注文テーブルを定期ポーリングして変化を検知する

<details><summary>答えと解説</summary>

正解: **2**

DB とブローカという2つの異なるシステムを1操作で更新しようとすると、どちらかだけ成功する不整合が必ず起こり得ます。アウトボックスパターンは、業務データとイベントを**同じDBトランザクション**で保存し、後段のリレーがブローカへ送ることで原子性を担保します。コミット前に先に送る案は「イベントは飛んだが保存は失敗」という逆の不整合を生みます。panic・再起動は根本解決にならず、保存済みイベントの再送制御もありません。定期ポーリングはイベント駆動の疎結合やリアルタイム性を捨てる後退で、負荷も大きくなります。

</details>

**問2.** アウトボックスパターンのリレーは「イベントをブローカへ送った直後、処理済みマークを付ける前にクラッシュ」することがあります。この性質を踏まえ、購読者 (subscriber) の設計で最も重要なのはどれですか。

1. 購読者を冪等に作り、同じイベントを2回受け取っても結果が変わらないようにする
2. ブローカを exactly-once 配送に設定し、重複が物理的に起きないことに依存する
3. イベントに連番を振り、欠番があったら購読者が処理を停止して管理者に通知する
4. 購読者側ではなく発行側に重複排除を実装し、同じイベントは二度と送らせない

<details><summary>答えと解説</summary>

正解: **1**

リレーが「送信後・マーク前」に落ちると同じイベントを再送するため、現実的な配送保証は at-least-once(重複あり)です。したがって購読者を**冪等**にし、イベントIDの処理済み記録や UPSERT で二重処理を無害化するのが王道です。分散環境での厳密な exactly-once は非常に高コストで、多くのブローカは実質 at-least-once なので「重複は起きない」前提は危険です。欠番検知での停止は可用性を損ね、順序保証も別問題です。発行側だけで重複を完全に消すのは、リレーのクラッシュ再送がある以上不可能で、受信側の冪等性は依然必要です。

</details>

**問3.** ドメインイベントとコマンドの違いの説明として、最も適切なものはどれですか。

1. コマンドは過去に起きた事実を表し、イベントはこれから実行したい依頼を表す
2. イベントとコマンドは本質的に同じもので、名前が違うだけなので区別する必要はない
3. イベントは「起きた事実」で拒否できず不特定多数が購読するが、コマンドは「依頼」でバリデーションにより拒否でき通常は単一のハンドラが受理する
4. イベントは必ず非同期で、コマンドは必ず同期で処理しなければならないという配送方式の違いである

<details><summary>答えと解説</summary>

正解: **3**

イベント (OrderPlaced のような過去形) は既に起きた事実なので取り消せず、複数の購読者が自由に反応できます。コマンド (PlaceOrder のような命令形) は依頼であり、受理側がバリデーションで拒否でき、通常は1つのハンドラが処理します。時制と意味が逆になっている説明や、両者を同一視する説明は誤りで、混同するとコンテキスト間を不要に密結合させます。同期/非同期はあくまで実装上の配送方式で、イベントかコマンドかという概念の定義そのものではありません。

</details>

**問4.** あるコンテキストが発行する OrderPlaced イベントに、注文の全明細・顧客の住所・支払い方法・在庫スナップショットまで詰め込んだところ、購読側が次々と不要な依存を背負い、イベント構造の変更が多数のサービスに波及するようになりました。設計指針として最も適切なのはどれですか。

1. イベントは小さく保ち、識別子と最小限の事実だけを載せ、詳細が必要な購読者は参照して取得する
2. 将来どの購読者が何を必要とするか分からないので、むしろ関連データを可能な限り全て載せておく
3. 購読者ごとに専用の巨大イベントを別々に用意し、各サービス向けに個別最適化する
4. イベントをやめて購読側から発行側のDBを直接 JOIN して読み取るように変更する

<details><summary>答えと解説</summary>

正解: **1**

イベントの肥大化は、購読側に不要な知識と依存を持ち込み、スキーマ変更の影響範囲を広げます。識別子と本質的な事実に絞り、詳細は必要な購読者が別途取得(または別の購読者が補う)構成にすると疎結合を保てます。何でも載せる方針は肥大化そのもので逆効果です。購読者ごとの巨大イベント乱立は発行側の責務を膨らませ保守不能になります。発行側DBへの直接 JOIN はコンテキスト境界を破壊し、最も避けるべき密結合です。

</details>

**問5.** 設計レビューで「在庫コンテキストが StockReserved を発行すると注文コンテキストが受けて注文を更新し、その更新で発行される OrderUpdated を在庫コンテキストが受けてまた在庫を更新する」という双方向のイベント連鎖が見つかりました。最も警戒すべき問題はどれですか。

1. イベント名が英語なので、日本語チームではユビキタス言語と一致しない
2. 相互にイベントで更新し合う循環依存になっており、無限ループや終わらない波及を招きやすい
3. イベントが2種類しかなく、将来の拡張時にイベントの種類が足りなくなる
4. 同期処理になっているため、レスポンスタイムが必ず遅くなる

<details><summary>答えと解説</summary>

正解: **2**

A のイベントで B を更新し、B のイベントで A を更新する双方向連鎖は循環依存であり、条件を誤ると無限ループや止まらない波及更新を引き起こします。イベントの流れは一方向を基本とし、必要なら調整役(プロセスマネージャ/Saga)に流れを集約して終了条件を明示します。イベント名の言語や種類数はこの連鎖の本質的な危険とは無関係です。また、イベント駆動は通常非同期であり「必ず同期で遅くなる」という前提も誤りです。

</details>

**問6.** 「注文1件につき20ポイント付与」する購読者が冪等に作られていません。同じ OrderPlaced イベントが再送され、2回届きました。付与されるポイントはどうなるでしょう？

1. 20ポイント。ブローカが重複を必ず取り除くから
2. 0ポイント。重複したイベントは両方とも捨てられるから
3. 20ポイント。同じイベントは DB が自動で弾くから
4. 40ポイント。届いた回数だけ付与処理が走るから

<details><summary>答えと解説</summary>

正解: **4**

at-least-once 配送では同じイベントが2回以上届くことがあり、冪等でない購読者は届いた回数だけ処理するので40ポイントになります。ブローカや DB が自動で重複を取り除いてくれる前提に頼るのは危険です。対策は購読者を冪等にすることで、処理済みのイベント ID を記録して2回目は何もしなければ、何回届いても20ポイントのままです。

</details>
