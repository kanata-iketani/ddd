# 第10章 ドメインサービスとドメインイベント

エンティティにも値オブジェクトにも置けない操作の受け皿「ドメインサービス」と、集約間を疎結合につなぐ「ドメインイベント」を学びます。この章を終えると「このロジックはどこに置くべきか」「集約をまたぐ連携をどう設計するか」に自分の言葉で答えられるようになります。

## 1. ドメインサービス — 置き場所に困る操作の受け皿

### 置き場所に困る操作

ドメインの操作の多くは、エンティティか値オブジェクトのメソッドとして置けます。しかし、どちらにも自然に置けない操作が残ります。

典型例が**口座間送金**です。「Aの口座から引き落とし、Bの口座に入金する」という操作は、2つの口座エンティティにまたがります。`a.TransferTo(b, amount)` とすると口座Aが口座Bの内部事情を知りすぎますし、逆向きにしても不自然さは消えません。また「ユーザー名の重複チェック」は全ユーザーを見渡す必要があり、1人のユーザーエンティティの中には置けません。

こうした操作の受け皿が**ドメインサービス (Domain Service)** です。

```go
// 2つの口座にまたがる操作はドメインサービスに
type TransferService struct{}

func (s TransferService) Transfer(from, to *Account, amount Money) error {
    if err := from.Withdraw(amount); err != nil {
        return err
    }
    return to.Deposit(amount)
}
```

### ドメインサービスの特徴

| 特徴 | 説明 |
|---|---|
| 状態を持たない (stateless) | 業務データをフィールドに持たず、引数で受け取って操作する |
| ユビキタス言語の動詞 | 「送金する」「割り当てる」など、ドメインの操作そのものを名前にする |
| ドメイン層に属する | DB や外部 API の都合は持ち込まない(それはインフラ層の仕事) |

### 💡 コツ: ドメインサービスは最後の手段

便利なので何でもドメインサービスに置きたくなりますが、やりすぎると**エンティティが貧血化**します(ルールが全部サービスに吸い出され、エンティティはただのデータの袋になる)。判断の順序を固定しましょう。

1. まず**エンティティのメソッド**に置けないか(そのオブジェクト自身の状態で決まるルールか?)
2. 次に**値オブジェクトの関数**に置けないか(値だけで完結する計算か?)
3. どちらも不自然なときだけ**ドメインサービス**へ

この順で考えると、モデルの表現力を保ったまま、置き場所の迷いがなくなります。なお、ユースケースの進行役(トランザクション開始や DTO 変換)は**アプリケーションサービス**の仕事で、ドメインサービスとは別物です。この区別は第12章で詳しく扱います。

### 確認問題

**問1.** ECサイトで「顧客の過去の全注文を横断して集計し、配送料を無料にできるかを判定する」ロジックの置き場所として最も適切なのはどれでしょう?

1. 顧客エンティティのメソッドに置く
2. 配送料を表す値オブジェクトのメソッドに置く
3. ドメインサービスに置く
4. HTTPハンドラ(コントローラ)に置く

<details><summary>答えと解説</summary>

正解: **3**

全注文を横断する判定は、1つの顧客エンティティにも配送料の値にも閉じないため、ドメインサービスが適切です。顧客エンティティに置くと注文の集合を抱え込んで肥大化し、値オブジェクトは自分の値だけで完結する計算にしか向きません。コントローラに置くとドメイン知識がプレゼンテーション層に漏れ、別の入口(バッチやAPI)から呼べなくなります。「複数の集約を見渡す判定はドメインサービス」が目印です。

</details>

**問2.** 「注文は発送前であればキャンセルできる」というルールの置き場所として最も適切なのはどれでしょう?

1. 注文エンティティの Cancel メソッド
2. キャンセル専用のドメインサービス
3. アプリケーションサービス
4. リポジトリ

<details><summary>答えと解説</summary>

正解: **1**

このルールは注文自身の状態(発送済みかどうか)だけで判定できるので、注文エンティティのメソッドに置くのが最適です。わざわざドメインサービスに出すとエンティティが貧血化する第一歩になります。アプリケーションサービスは進行役であってルールの置き場所ではなく、リポジトリは永続化の抽象です。ひっかけ: 「サービス」という言葉の便利さに流されず、まず「エンティティ自身で決められるか」を考えるのがDDDの判断順序です。

</details>

**問3.** ドメインサービスの性質として最も適切なのはどれでしょう?

1. 業務データをフィールドに保持し、状態を管理する
2. DBアクセスを直接実装し、永続化も担当する
3. トランザクションの開始・コミットなどユースケースの進行を司る
4. 状態を持たず、引数で受け取ったドメインオブジェクトに対して操作を行う

<details><summary>答えと解説</summary>

正解: **4**

ドメインサービスは状態を持たない(stateless)のが原則で、操作対象は引数で受け取ります。業務データを抱えるならそれはエンティティであるべきです。DBアクセスの実装はインフラ層(リポジトリ実装)の仕事、トランザクション管理やユースケース進行はアプリケーションサービスの仕事です。「同じサービスという名前でも、ドメインサービスとアプリケーションサービスは役割が別」という区別は実務でも試験的な問いでも頻出です。

</details>

**問4.** 「ユーザー名はシステム全体で一意でなければならない」というルールの表現として最も適切なのはどれでしょう?

1. User エンティティのコンストラクタで全ユーザーを読み込んで重複を確認する
2. 一意性確認をドメインサービスとして表現し、実装ではリポジトリの検索を利用する
3. 画面側(フロントエンド)のバリデーションだけで保証する
4. DBのユニーク制約で守れるので、ドメイン層では何も表現しない

<details><summary>答えと解説</summary>

正解: **2**

全ユーザーを見渡す確認は1人のユーザーエンティティには置けないため、ドメインサービス(例: UserUniquenessChecker)として表現し、検索はリポジトリに任せるのが定石です。コンストラクタで全件読み込みは非現実的で、エンティティが集合全体の知識を抱えてしまいます。フロントのみの検証は API 直叩きで迂回されます。DBのユニーク制約は最後の砦として併用すべきですが、それ「だけ」にするとルールがモデルから消え、ユビキタス言語とコードの対応が失われます。

</details>

**問5.** あるチームが「ロジックはすべて〇〇Service クラスに置く」という方針を続けた結果、エンティティが getter/setter だけになりました。この状態の名前と問題点の組み合わせとして正しいのはどれでしょう?

1. ヘキサゴナルアーキテクチャ — 依存が整理された良い状態
2. 蒸留 — コアドメインが明確になった良い状態
3. 貧血ドメインモデル — ルールがサービスに散在し、重複や検証漏れが生じる
4. CQRS — 読み書きが分離された良い状態

<details><summary>答えと解説</summary>

正解: **3**

ルールがエンティティから吸い出されてデータの袋だけが残った状態を貧血ドメインモデル (Anemic Domain Model) と呼び、代表的なアンチパターンです。同じルールが複数のサービスに重複し、検証漏れの温床になります。ヘキサゴナルは依存方向の整理、蒸留はコアの分離、CQRSは読み書きモデルの分離であり、どれも「エンティティからルールを剥ぎ取ること」ではありません。ドメインサービスは便利ですが「最後の手段」という優先順位を忘れると、この状態に陥ります。

</details>

## 2. ドメインイベント — 起きた事実をモデルにする

### ドメインイベントとは

**ドメインイベント (Domain Event)** は「ドメインで実際に起きた出来事」をオブジェクトにしたものです。名前は必ず**過去形**にします: `OrderPlaced`(注文が確定した)、`PaymentCompleted`(支払いが完了した)。ドメインエキスパートの「注文が確定**したら**、ポイントを付与する」という言葉の「〜したら」の部分がそのままイベントになります。つまりイベント名もユビキタス言語の一部です。

```go
// 過去形で命名し、起きた事実を不変のデータとして持つ
type OrderPlaced struct {
    OrderID    OrderID
    CustomerID CustomerID
    Total      Money
    OccurredAt time.Time
}
```

### イベントに含める情報

- 何が起きたか(イベント名)
- いつ起きたか(発生時刻)
- どの集約で起きたか(集約のID)
- 購読側の判断に必要な**最小限の事実**

### 集約が生成し、ディスパッチャが配る

イベントは**集約のメソッドの中で生成**します。「注文が確定した」という事実がいつ成立するかを知っているのは、確定のルールを持つ注文集約自身だからです。集約は発生したイベントをいったん内部に溜め、保存が成功した後にディスパッチャ(配達係)が購読者へ配ります。

```go
func (o *Order) Place() error {
    if len(o.items) == 0 {
        return errors.New("明細のない注文は確定できません")
    }
    o.status = StatusPlaced
    o.events = append(o.events, OrderPlaced{
        OrderID: o.id, CustomerID: o.customerID,
        Total: o.Total(), OccurredAt: time.Now(),
    })
    return nil
}
```

### 💡 コツ: 集約間の連携はイベントで疎結合に

「注文確定後にポイントを付与」を、注文集約がポイント集約を直接呼んで実現すると、注文がポイントの事情を知りすぎ、さらに1トランザクションで2つの集約を更新する原則違反(第9章)にもなります。`OrderPlaced` を発行してポイント側がそれを購読すれば、お互いの内部を知らずに連携でき、トランザクションも分離できます。「直接呼ぶ代わりに、起きた事実を知らせる」—これがイベントの発想です。

### 確認問題

**問1.** ドメインイベントの命名として最も適切なのはどれでしょう?

1. PlaceOrder
2. OrderPlaced
3. OrderPlacing
4. WillPlaceOrder

<details><summary>答えと解説</summary>

正解: **2**

ドメインイベントは「すでに起きた事実」なので過去形の OrderPlaced が正解です。PlaceOrder は命令形で、これは「依頼」を表すコマンドの命名です(イベントとコマンドの違いは次チャプターで詳しく扱います)。OrderPlacing(進行中)や WillPlaceOrder(未来)は事実が確定していないため、イベントにはなりません。「過去形かどうか」はコードレビューでイベント設計の歪みを見つける簡単で強力なチェックポイントです。

</details>

**問2.** 「注文が確定したら、別集約であるポイント口座にポイントを付与する」の実現方法として最も適切なのはどれでしょう?

1. 注文集約の Place メソッド内でポイント集約を取得し、直接更新する
2. アプリケーションサービスで注文とポイントを同一トランザクションで必ず同時更新する
3. ポイント側が注文テーブルを定期的にポーリングして変化を検出する
4. 注文集約が OrderPlaced イベントを発行し、ポイント側の購読者がそれを受けて付与する

<details><summary>答えと解説</summary>

正解: **4**

イベント経由の連携なら、注文はポイントの内部を知らず(疎結合)、トランザクションも集約ごとに分離できます。直接更新は結合を生むうえ「1トランザクション1集約」の原則に反します。同一トランザクションでの同時更新も同じ原則違反で、ポイント付与は通常、少し遅れても困らない(結果整合性で十分な)処理です。ポーリングは他コンテキストのDBを覗く共有DBアンチパターンで、負荷と遅延も生みます。

</details>

**問3.** ドメインイベントに含める情報として最も適切な組み合わせはどれでしょう?

1. イベント名・発生時刻・関連する集約のID・購読側の判断に必要な最小限の事実
2. 発行元集約が持つ全フィールドの完全なコピー
3. 購読者の一覧と、各購読者が実行すべき処理手順
4. 次に実行すべきコマンドの列

<details><summary>答えと解説</summary>

正解: **1**

イベントは「何が・いつ・どこで起きたか」という事実と、購読側に必要な最小限のデータを運びます。全フィールドのコピーは発行側の内部構造への依存を広げ、変更のたびに全購読者が壊れます(肥大化の問題は次チャプターで扱います)。購読者の一覧や処理手順を含めるのは発行側が購読側を知っていることになり、疎結合という利点を自ら壊します。コマンド列を含めるのはイベント(事実)とコマンド(依頼)の混同です。

</details>

**問4.** OrderPlaced イベントを生成する場所として最も適切なのはどれでしょう?

1. HTTPハンドラ(コントローラ)
2. リポジトリの Save メソッドの内部
3. 確定のルールを持つ注文集約の Place メソッドの内部
4. イベントを受け取る購読者自身

<details><summary>答えと解説</summary>

正解: **3**

「注文が確定した」という事実がいつ成立するかを知っているのは、確定の条件(明細があるか等)を検証する注文集約自身です。だからイベントは集約のメソッド内で生成します。コントローラで生成すると、別の入口(バッチ等)から確定したときにイベントが漏れます。リポジトリは永続化の抽象であり「保存=確定」とは限りません。購読者が自分でイベントを作るのは因果が逆です。

</details>

**問5.** ユビキタス言語とドメインイベントの関係として最も適切なのはどれでしょう?

1. イベント名は RowUpdated のような技術用語で統一すべきである
2. ドメインエキスパートの「〜したら」という表現が、そのままイベント名になる
3. イベントはDBの変更ログなので、ユビキタス言語とは無関係である
4. イベント名には必ず日本語を使わなければならない

<details><summary>答えと解説</summary>

正解: **2**

「注文が確定したら」「支払いが完了したら」というエキスパートの言葉の「〜したら」が OrderPlaced や PaymentCompleted というイベントになります。つまりイベントはユビキタス言語の語彙そのものです。RowUpdated のような技術用語はどの業務の出来事なのかが消えてしまい、DB変更ログ(CDC)とドメインイベントは粒度も目的も別物です。言語(日本語/英語)の指定はDDDにはなく、チームで一貫していることが重要です。

</details>

## 3. イベント駆動の実装パターン

ドメインイベント (domain event) を「生成する」ところまでは前チャプターで学びました。ここでは、そのイベントを**どう配り、どう安全に処理するか**という実装の勘所を押さえます。

### 同一プロセス内 vs 非同期メッセージング

イベントの配送先には大きく2通りあります。

| 方式 | 配送 | 向いている場面 | 注意点 |
|---|---|---|---|
| 同一プロセス内ディスパッチ | メモリ上で即時に購読者を呼ぶ | 同じサービス内の軽い波及処理 | 購読者の失敗が発行側トランザクションを巻き込みやすい |
| 非同期メッセージング | メッセージブローカ (Kafka, SQS 等) 経由 | **境界づけられたコンテキスト (bounded context) をまたぐ連携** | 配送保証・順序・重複を自分で設計する必要がある |

別コンテキストや別サービスへ伝えるなら、疎結合を保てる非同期メッセージングが基本です。

### アウトボックスパターン (Outbox Pattern)

「DB を更新したのにイベント発行だけ失敗した(あるいはその逆)」という不整合は、2つの別々のシステム(DB とブローカ)を1つの操作で更新しようとすると必ず起きます。これを防ぐのが**アウトボックスパターン**です。

```go
// 集約の保存とイベント記録を「同じDBトランザクション」で行う
func (r *OrderRepo) Save(ctx context.Context, o *Order) error {
    return r.db.Tx(ctx, func(tx *sql.Tx) error {
        if err := saveOrder(tx, o); err != nil {
            return err
        }
        // イベントも同じトランザクションで outbox テーブルへ INSERT
        return insertOutbox(tx, o.PullEvents())
    })
}
```

イベントは一旦 `outbox` テーブルに書き、別プロセス(リレー)が後からブローカへ送って `published` に印をつけます。業務データとイベントが**同じコミットで保存される**ため、「片方だけ成功」が起きません。

### at-least-once と冪等な購読者

アウトボックスのリレーは「送った直後にクラッシュ」すると同じイベントを再送します。つまり配送保証は **at-least-once(最低1回、ただし重複あり)** が現実解です。だから購読者 (subscriber) は**冪等 (idempotent)**、すなわち「同じイベントを2回受け取っても結果が変わらない」よう作る必要があります。イベントIDを処理済みテーブルで記録して弾く、更新を UPSERT にする、などが定石です。

### イベントとコマンドは別物

| | イベント (event) | コマンド (command) |
|---|---|---|
| 意味 | 起きた**事実** | 依頼・命令 |
| 時制 | 過去形 `OrderPlaced` | 命令形 `PlaceOrder` |
| 拒否 | できない(もう起きた) | バリデーションで拒否できる |
| 宛先 | 不特定多数が購読 | 1つのハンドラが受理 |

> 💡 コツ: 「〜しろ」はコマンド、「〜した」はイベント。発行側が受信側に処理を**強制**したくなったら、それはイベントではなくコマンドの設計です。混同するとコンテキスト間が密結合に戻ってしまいます。

最後に、1つのイベントに何でも詰め込むと**肥大化**し、受信側が不要な依存を背負います。また「A のイベントで B を更新し、B のイベントで A を更新」する**循環依存**は無限ループの温床です。イベントは小さく、流れは一方向を意識しましょう。

### 確認問題

**問1.** 注文サービスで「注文を保存し、かつ OrderPlaced イベントをメッセージブローカへ発行する」処理を実装します。DB コミットの直後にブローカへ publish する実装にしたところ、まれに「注文は保存されたがイベントが届かない」不整合が起きました。最も適切な対処はどれですか。

1. publish を DB コミットより前に移動し、先にイベントを送ってから注文を保存する
2. 注文の保存とイベントを outbox テーブルへの INSERT として同一トランザクションにまとめ、別のリレーがブローカへ送る
3. publish が失敗したら panic させ、プロセスを再起動して最初からやり直す
4. イベント発行をやめ、購読側が注文テーブルを定期ポーリングして変化を検知する

<details><summary>答えと解説</summary>

正解: **2**

DB とブローカという2つの異なるシステムを1操作で更新しようとすると、どちらかだけ成功する不整合が必ず起こり得ます。アウトボックスパターンは、業務データとイベントを**同じDBトランザクション**で保存し、後段のリレーがブローカへ送ることで原子性を担保します。コミット前に先に送る案は「イベントは飛んだが保存は失敗」という逆の不整合を生みます。panic・再起動は根本解決にならず、保存済みイベントの再送制御もありません。定期ポーリングはイベント駆動の疎結合やリアルタイム性を捨てる後退で、負荷も大きくなります。

</details>

**問2.** アウトボックスパターンのリレーは「イベントをブローカへ送った直後、処理済みマークを付ける前にクラッシュ」することがあります。この性質を踏まえ、購読者 (subscriber) の設計で最も重要なのはどれですか。

1. 購読者を冪等に作り、同じイベントを2回受け取っても結果が変わらないようにする
2. ブローカを exactly-once 配送に設定し、重複が物理的に起きないことに依存する
3. イベントに連番を振り、欠番があったら購読者が処理を停止して管理者に通知する
4. 購読者側ではなく発行側に重複排除を実装し、同じイベントは二度と送らせない

<details><summary>答えと解説</summary>

正解: **1**

リレーが「送信後・マーク前」に落ちると同じイベントを再送するため、現実的な配送保証は at-least-once(重複あり)です。したがって購読者を**冪等**にし、イベントIDの処理済み記録や UPSERT で二重処理を無害化するのが王道です。分散環境での厳密な exactly-once は非常に高コストで、多くのブローカは実質 at-least-once なので「重複は起きない」前提は危険です。欠番検知での停止は可用性を損ね、順序保証も別問題です。発行側だけで重複を完全に消すのは、リレーのクラッシュ再送がある以上不可能で、受信側の冪等性は依然必要です。

</details>

**問3.** ドメインイベントとコマンドの違いの説明として、最も適切なものはどれですか。

1. コマンドは過去に起きた事実を表し、イベントはこれから実行したい依頼を表す
2. イベントとコマンドは本質的に同じもので、名前が違うだけなので区別する必要はない
3. イベントは「起きた事実」で拒否できず不特定多数が購読するが、コマンドは「依頼」でバリデーションにより拒否でき通常は単一のハンドラが受理する
4. イベントは必ず非同期で、コマンドは必ず同期で処理しなければならないという配送方式の違いである

<details><summary>答えと解説</summary>

正解: **3**

イベント (OrderPlaced のような過去形) は既に起きた事実なので取り消せず、複数の購読者が自由に反応できます。コマンド (PlaceOrder のような命令形) は依頼であり、受理側がバリデーションで拒否でき、通常は1つのハンドラが処理します。時制と意味が逆になっている説明や、両者を同一視する説明は誤りで、混同するとコンテキスト間を不要に密結合させます。同期/非同期はあくまで実装上の配送方式で、イベントかコマンドかという概念の定義そのものではありません。

</details>

**問4.** あるコンテキストが発行する OrderPlaced イベントに、注文の全明細・顧客の住所・支払い方法・在庫スナップショットまで詰め込んだところ、購読側が次々と不要な依存を背負い、イベント構造の変更が多数のサービスに波及するようになりました。設計指針として最も適切なのはどれですか。

1. イベントは小さく保ち、識別子と最小限の事実だけを載せ、詳細が必要な購読者は参照して取得する
2. 将来どの購読者が何を必要とするか分からないので、むしろ関連データを可能な限り全て載せておく
3. 購読者ごとに専用の巨大イベントを別々に用意し、各サービス向けに個別最適化する
4. イベントをやめて購読側から発行側のDBを直接 JOIN して読み取るように変更する

<details><summary>答えと解説</summary>

正解: **1**

イベントの肥大化は、購読側に不要な知識と依存を持ち込み、スキーマ変更の影響範囲を広げます。識別子と本質的な事実に絞り、詳細は必要な購読者が別途取得(または別の購読者が補う)構成にすると疎結合を保てます。何でも載せる方針は肥大化そのもので逆効果です。購読者ごとの巨大イベント乱立は発行側の責務を膨らませ保守不能になります。発行側DBへの直接 JOIN はコンテキスト境界を破壊し、最も避けるべき密結合です。

</details>

**問5.** 設計レビューで「在庫コンテキストが StockReserved を発行すると注文コンテキストが受けて注文を更新し、その更新で発行される OrderUpdated を在庫コンテキストが受けてまた在庫を更新する」という双方向のイベント連鎖が見つかりました。最も警戒すべき問題はどれですか。

1. イベント名が英語なので、日本語チームではユビキタス言語と一致しない
2. 相互にイベントで更新し合う循環依存になっており、無限ループや終わらない波及を招きやすい
3. イベントが2種類しかなく、将来の拡張時にイベントの種類が足りなくなる
4. 同期処理になっているため、レスポンスタイムが必ず遅くなる

<details><summary>答えと解説</summary>

正解: **2**

A のイベントで B を更新し、B のイベントで A を更新する双方向連鎖は循環依存であり、条件を誤ると無限ループや止まらない波及更新を引き起こします。イベントの流れは一方向を基本とし、必要なら調整役(プロセスマネージャ/Saga)に流れを集約して終了条件を明示します。イベント名の言語や種類数はこの連鎖の本質的な危険とは無関係です。また、イベント駆動は通常非同期であり「必ず同期で遅くなる」という前提も誤りです。

</details>
